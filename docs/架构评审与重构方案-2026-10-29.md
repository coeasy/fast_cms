## 0. 结论摘要

代码库整体处于**较高工程水位**：分层门禁零违规、模块依赖显式登记、错误码/权限码/契约
三张表有单一事实源、439 个用例全绿、安全响应头与审计日志齐备。前几轮方案已基本消化。

本轮的发现集中在两类：

1. **架构不合理（9 项，A 类）**——不是「写错了」，而是**机制只做了一半或两套机制并存**：
   三张注册表的双轨写入路径、codegen 游离于模块体系之外、事件总线只有进程内同步语义、
   横向扩展约束散落各处（含调度多实例的 `next_run_at` 所有权靠注释约定）、API 缺版本演进机制等。
2. **开发细节需改进（13 项，B 类）**——**数据正确性**（审计日志双写、耗时恒为 0、
   租约竞争型 `skipped` 日志噪音）、**质量门禁强度**（mypy/ruff 规则面窄、白名单只做单向包含校验）、
   **前端工程化**（无行为测试、样板重复、无障碍薄弱）、**供应链与可观测性**缺口。

最值得优先处理的三条（都是「现在就错着」而不是「将来不够用」）：

| 优先级 | 问题 | 影响 |
|---|---|---|
| **P0** | B-1 审计日志双写 + `duration_ms=0` | 「操作记录」页面出现重复行、耗时统计恒 0，直接影响安全审计可信度 |
| **P0** | B-2 门禁单向包含校验导致白名单腐化 | `ALLOWED_MODULE_EDGES` 已有 2 条幽灵条目，门禁无法发现；架构约束会持续漂移 |
| **P1** | A-1 三张注册表双轨并存 | 新人写新模块时「走清单还是走中心表」二选一，极易写错且部分路径是死路 |

## 1. 现状架构梳理

### 1.1 设计定位与不可破坏的约束

Fast CMS 是「**可直接启动、低资源占用的后台管理基座**」。三条硬约束贯穿全库，
重构时不得破坏：

1. **零前端工具链**：Jinja2 服务端渲染 + 原生 ES Module，没有 Node.js / 包管理器 / 构建步骤 / 独立前端进程；
2. **零外部依赖默认可跑**：默认只用 Python + SQLite，MySQL 8 / Redis 7 是**显式开启**的可选能力；
3. **代码与数据分离**：升级只替换源码，数据留在 `DATA_DIR`（SQLite、上传文件、签名密钥、迁移备份、启动锁）。

### 1.2 分层与包结构

```text
                    ┌──────────────────────────────┐
   浏览器 ─────────▶│  app/web   HTML 外壳          │
                    │  templates + static + PAGES   │
                    └──────────────┬───────────────┘
                                   │ 渲染数据 / 页面注册
                    ┌──────────────▼───────────────┐
                    │  app/modules  业务模块（12）  │
                    │  sys/{system,auth,security,   │
                    │       config}                 │
                    │  ops/{audit,monitor,schedule, │
                    │       notify,export,dashboard}│
                    │  content（公告） theme（主题）│
                    └──────┬───────────────┬────────┘
                           │               │
                    ┌──────▼──────┐ ┌──────▼──────┐
                    │ app/kernel  │ │  app/jobs   │
                    │ 身份/凭证/  │ │  任务执行器 │
                    │ 审计/文件   │ └─────────────┘
                    └──────┬──────┘
                    ┌──────▼──────────────────────┐
                    │  app/core  基础设施          │
                    │  config/errors/authz/events/ │
                    │  pagination/upload/csrf/...  │
                    └──────┬──────────────────────┘
                    ┌──────▼──────┐   ┌────────────┐
                    │  app/db     │   │app/bootstrap│
                    │ Base/session│   │ 权限/菜单/  │
                    │ /migrate    │   │ 种子        │
                    └─────────────┘   └────────────┘
```

依赖方向 `web → modules → kernel → core`，由 `scripts/check_modules.py` 的
`check_layering` 用 AST 强制（不被注释/docstring 误伤）。**实测 core/kernel 对
`app.modules.*` 的反向依赖为 0。[事实]**

### 1.3 模块清单与三张注册表

每个模块在 `module.py` 里声明 `ModuleSpec`（`app/core/module.py`）：

| 字段 | 消费方 | 说明 |
|---|---|---|
| `routers` | `main.py` → `module_routers()` | 路由按 `(order, name)` 确定性注册 |
| `permissions` | `bootstrap/seed.py` → `all_permissions()` | **增量**权限码（存量 97 条仍在 `bootstrap/permissions.py`） |
| `pages` | `web/router.py` → `all_pages()` | **增量**页面（存量 30 页仍在 `PAGES`） |
| `menus` | `bootstrap/menus.py` → `all_menu_tree()` | **增量**菜单（存量仍在 `MENU_TREE`） |

这是「**存量集中 + 增量走清单**」的双轨制，理由在 `docs/模块与分层规范.md` §3 有完整论证
（权限码是对外契约、菜单是信息架构而非代码归属）。**但双轨本身是有成本的**，见 A-1。

### 1.4 请求链路与中间件栈

```text
请求
 └─ RequestContextMiddleware      # request_id / 客户端 IP / 上下文绑定
    └─ IpGuardMiddleware          # IP 规则与自动封禁，必须最外层业务闸
       └─ RateLimitMiddleware     # 敏感接口限流（429 + Retry-After）
          └─ OperationLogMiddleware  # 变更类请求写操作日志（缓冲并回放 JSON body）
             └─ FastAPI 路由
                  ├─ Depends(get_current_user)   # JWT / API Key（fck_ 前缀分流）
                  ├─ Depends(require_permission) # RBAC 权限码
                  ├─ get_data_scope / apply_user_scope  # 数据范围裁剪
                  └─ service 层 → kernel/db.commit / log_operation
```

中间件按「后注册先执行」包裹，注释明确 IP 守卫必须最外层。异常处理在
`create_app()` 注册四类：`AppError` / `RequestValidationError` /
`StarletteHTTPException` / `IntegrityError`，外加兜底 `Exception` → 500 + `request_id`。

### 1.5 启动引导链路

```text
create_app() → lifespan
  ├─ 校验 APP_WORKERS>1 时禁止 embedded scheduler
  ├─ configure_logging() / init_cache() / ipgeo.startup()
  ├─ BootLock(data_root/bootstrap.lock)   # 多 worker 首启串行化
  │   ├─ ensure_database()               # Alembic 迁移（可选 SQLite 自动备份）
  │   ├─ _ensure_seed()                  # 种子 + sync_permission_codes（旧库补新增权限码）
  │   └─ load_timezone_from_db()          # 系统时区以库为准，须早于调度器
  └─ scheduler_mode == "embedded" → scheduler_service.start()
```

`fastcms scheduler`（独立进程）走 `cli.py:_scheduler()`，在 `ensure_database()` 后补
`discover_modules()` 以接上事件订阅（上一轮 R-2 修复）。

### 1.6 前端三层结构

| 层 | 文件 | 规模 |
|---|---|---|
| 组件库 | `components/ui.html`（宏）+ `core/*.js` + `ui.js` | ui.html 336 行；ui.js 383 行 |
| 外壳 | `shell/admin.js`（582）/ `shell/portal.js` / `shell/auth.js` | 三套互不越界 |
| 页面 | `pages/**`（24 个页面脚本） | 单文件最大 `system/user.js` 524 行 |

样式按层拆分（`base` / `admin` / `portal` / `public`），页面只加载自己需要的；
`?v={{ asset_v() }}` + `VersionedStaticFiles` 实现可靠缓存。
`check_contract.py` 校验页面继承关系、页面脚本引用的 `#id` 是否真实存在于渲染结果。

### 1.7 数据与事务

- **模型**：`kernel/models.py` 集中身份/凭证/审计/存储四组平台模型（306 行）；
  业务模型分散在各模块 `models.py`；两者都要在 `db/models.py` re-export 给 Alembic（见 A-3）。
- **事务**：`session_scope` 异常回滚、正常提交；`get_db` **不隐式提交**，由端点显式 `commit()`；
  `kernel/db.commit()` 把 `IntegrityError` 统一翻译为 409 `DATA_CONFLICT`。
- **时间**：数据库一律 UTC（`UTCDateTime`），展示层跟随系统参数 `system.timezone`。
- **可移植性**：查询统一用 SQLAlchemy Core/ORM，`like(..., escape=LIKE_ESCAPE)`、
  右前缀 `LIKE 'prefix%'` 走索引；CI 有 MySQL 8 方言回归 job。

## 3. 架构层面不合理之处（A 类）

### A-1【机制半成品】三张注册表都是「双轨制」，缺少存量收敛路径 **[事实]**

权限码、页面、菜单三张表都采用「存量集中 + 增量走清单」：

| 注册表 | 存量位置 | 增量通道 |
|---|---|---|
| 权限码 | `bootstrap/permissions.py`（97 条） | `ModuleSpec.permissions` |
| 页面 | `web/router.py` 的 `PAGES`（30 条） | `ModuleSpec.pages` |
| 菜单 | `bootstrap/menus.py` 的 `MENU_TREE` | `ModuleSpec.menus` |

问题不在「双轨」这个决策本身（理由充分），而在于：

1. **新人要理解三套不同的合并规则**（同路径存量优先、增量去重、权限码去重校验），
   才能确定「我该写在哪一边」；
2. **存量永远不迁移**，双轨不是过渡态而是终态——文档写的是「存量不动」，但没有任何
   工具/脚本可以把存量条目安全下沉到清单；
3. **两条路径的表达能力不对等**：`PAGES` 条目支持 `public` / `subtitle`，`ModuleSpec.pages`
   的字段更窄（`page/path/title/permission`），清单通道声明不了公开页与副标题。

**[建议]** 把双轨明确为**过渡态**：补一个 `migrate-registry` 干跑子命令（挂到统一命令行入口），
按模块把存量条目导出成候选清单片段（人工确认后落地），并在 `check_modules.py`
里加「新增条目必须走清单」的渐进约束；同时把 `ModuleSpec.pages` 的字段补齐到与 `PAGES` 等价。

### A-2【体系外挂件】codegen 不参与模块体系，产物目录约定与分层规范冲突 **[事实]**

- `main.py:254` 用 `app.include_router(codegen_router, prefix=api_prefix)` **硬编码**注册，
  而 `_iter_module_packages()` 只扫描 `app/modules/`——codegen 是唯一游离在模块清单外的路由。
- `codegen/templates/README.md.j2` 第 8 行指引复制到 `backend/app/modules/{{ module }}/`（**顶层**），
  而 `docs/模块与分层规范.md` §2 明确「**域分组只允许一层**：`modules/<域>/<模块>/`」，
  存量 12 个模块全部在 `sys/` `ops/` `content/` `theme/` 之下。
  按生成器指引落地的模块，目录形态与全部存量不一致。

**[建议]** ①codegen 生成器输出 `--domain` 参数，默认按资源类型落到 `sys`/`ops`/新域；
②把 `app/codegen` 收编为一个模块清单（`name="codegen"`，`order=200`），
消除 `main.py` 的硬编码分支；③README 模板的落地路径改为 `app/modules/<域>/<module>/`。

### A-3【中央文件未减反增】新增模型仍要改 2 处，`kernel/models.py` 是单体文件 **[事实]**

`docs/模块与分层规范.md` §6 宣称「新增模块需改的中央文件：**1 个**（models re-export）」。
实际上：新增一个带模型的模块要改 ①自己的 `module.py`（非中央）、②`db/models.py` re-export；
若属于平台能力还要改 ③`kernel/models.py`（当前 306 行塞了身份/凭证/审计/存储**四组**模型）。

`db/models.py` 的 re-export 是纯机械劳动且**漏了就静默失效**：`alembic revision --autogenerate`
看不到新表，`test_schema_drift.py` 也要到运行期才发现。

**[建议]** ①`kernel/models.py` 按职责拆成 `kernel/models/{identity,credential,audit,storage}.py`
（保持 `app.kernel.models` 作为 re-export 面，零迁移）；②把 `db/models.py` 的机械 re-export
改成 `Base.metadata` 自动收集 + 一条 `check_modules` 校验「每个模块的 models 都被 import 到」，
把「漏改即静默失效」变成「漏改即门禁失败」。

### A-4【语义单薄】事件总线只有进程内同步语义，缺 outbox 与投递凭证 **[事实]**

`core/events.py` 的设计约束写得很清楚：单进程、异常隔离、按注册顺序串行 await。
但落到生产语义上是 **at-most-once + 请求内同步**：

| 维度 | 现状 | 后果 |
|---|---|---|
| 投递可靠性 | 订阅方抛异常只记日志，事件即丢失 | 通知没发出去无法追溯「哪个事件、谁订阅、为何失败」 |
| 延迟 | `await handler(**payload)` 在请求/任务关键路径上串行执行 | 慢订阅方（如 Webhook 超时 10s）直接拖慢公告发布接口 |
| 跨进程 | 每个 worker 各自持有订阅表 | 多 worker 下同一事件被 N 个进程各自处理，或某些进程收不到（R-3 只对时区做了轮询补偿） |
| 顺序/去重 | 无 | 重复发布（如重试）会导致重复推送 |

注意 `notice.published` → notify 落库后由**自己的队列 + 指数退避**做可靠投递，所以业务上没丢；
但 `config.timezone_changed`、`job.finished` 的失败只有一行 error 日志。

**[建议]** 分两步：
①**短期**：`publish()` 返回 `handled` 数的同时落一条轻量 `core_event_log`（事件名、payload 摘要、
各订阅者成败），管理端可查，把「静默丢弃」变成「可追溯」；
②**中期**：改成事务性 outbox——发布方在同一事务里写 `event_outbox`，由独立 dispatcher
（可挂进 `jobs/runner` 的轮询）派发，天然获得至少一次投递 + 跨进程一致 + 请求路径非阻塞。
`KNOWN_EVENTS` 与门禁保持不变。

### A-5【约束散落】横向扩展能力没有单一事实源 **[事实]**

横向扩展相关约束散落在 4 处，且互不引用：

- `main.py:75`：`APP_WORKERS>1` 且 `scheduler_mode == "embedded"` → 启动期 `RuntimeError`；
- `core/config.py`：`redis_enabled=False` 时 `get_cache()` 是进程内 `MemoryCache`；
- `core/events.py` 文档字符串：「单进程内，没有跨进程投递」；
- `docs/部署与升级.md`：分散描述各形态。

结果是「多 worker 到底能开哪些功能」必须靠读者自己拼装。**限流在多 worker + 无 Redis 时
是各进程独立计数**这件事，只在代码注释里出现过一次。

**[建议]** 产出 `docs/部署形态与一致性矩阵.md`（内容即 §1.8 那张表的展开版），
并在 `fastcms doctor` / `config_probe.py` 里加一条**组合校验**：
`APP_WORKERS>1` 且 `redis_enabled=false` 时输出明确警告（不是错误，允许单机多进程降级运行），
`APP_WORKERS>1` 且 `scheduler_mode=embedded` 维持硬失败。

### A-6【职责过载】`main.py` 是装配根 + 端点 + 中间件 + 静态挂载的合体 **[事实]**

`main.py` 271 行同时承担：异常处理器注册、CORS、4 层中间件装配、`/healthz` `/readyz`
两个端点（含迁移版本比对与 Redis 复核）、`/meta/version`、模块路由注册、静态资源挂载、
后台/前台前缀装配、根路径重定向策略。

其中还有一处**双轨异常翻译**：`IntegrityError` 既有全局 `integrity_error_handler`
（`core/errors.py`），又有 `kernel/db.commit()` 里的 try/except。两者行为一致但属于
两套写法并存，读代码时难以判断该用哪个。

**[建议]** 拆成 `app/assembly.py`（中间件 + 路由装配）、`app/health.py`（探活端点）、
`app/main.py`（只剩 `create_app()` 与 lifespan）；`IntegrityError` 统一收敛到全局 handler，
`kernel/db.commit()` 只负责「提交 + 语义化异常」，不再重复做 HTTP 层翻译。

### A-7【配置面过宽】60+ 配置项 + 模块级单例，缺最小配置集 **[事实]**

`.env.example` 7,374 字节、60+ 项；`Settings` 在**导入期**实例化为模块级单例 `settings`，
全库 100+ 处直接引用。带来的问题：

1. 测试期换配置需要 `importlib.reload` 或改环境变量（`tests/conftest.py` 已为此做了隔离）；
2. 「最小可跑配置」不明确——新部署要读完整个 `.env.example` 才知道哪些必须改；
3. 配置项之间有隐含约束（如 `APP_WORKERS` × `SCHEDULER_MODE` × `REDIS_ENABLED`），
   只能靠运行期抛异常或注释说明。

**[建议]** ①把 `.env.example` 分组折叠为「必填 / 常调 / 调优 / 实验」四段，顶部给 5 行最小配置；
②新增 `settings.validate_combinations()` 集中表达配置间约束（现在散在 lifespan、
`_check_site_bases`、`_check_cors_origins` 三处）；③测试期提供 `settings.override()` 上下文管理器，
替代 reload。

### A-8【演进缺位】有 `/api/v1` 前缀，但没有版本演进与契约破坏检测 **[事实]**

现状：`api_prefix` 可配置、`Permission.deprecated_at` 有废弃字段、`openapi.json` 是**快照**
参与契约校验。缺的是：

1. **breaking change 检测**：`check_contract.py` 只比对「快照 vs 当前」是否一致，
   不区分「加字段」（兼容）与「删字段/改语义」（破坏）；快照更新一次即可把破坏性变更合法化；
2. **接口废弃流程**：`deprecated_at` 字段存在但没有对应的响应头（如 `Deprecation` / `Sunset`）
   与文档标注；
3. **变更日志**：152 个操作没有任何 CHANGELOG 连接到版本号。

**[建议]** ①`check_contract.py` 增加**结构化 diff**：对删除的 operation / 参数 / 响应字段
报「破坏性变更」，必须显式加 `--allow-breaking` 并在 PR 说明；②废弃接口统一挂
`Deprecation: true` + `Sunset: <date>` 响应头；③`docs/API规范.md` 附一节「版本与废弃策略」。

### A-9【约定代替机制】调度多实例的共享状态靠注释约定，`next_run_at` 存在多写方 **[事实]**

调度模式约束（`embedded` 仅单 worker，`APP_WORKERS>1` 启动硬失败，`main.py:75`）方向正确。
但任何多调度实例形态（放开 embedded 多 worker，或多 API worker + standalone 调度进程并行）
下，有三个共享状态**没有机制化**：

1. `Job.next_run_at` 是共享列，`sync_all()` / `reload_job()` / `refresh_job_state()`
   （调度进程）与 `service.py` 的 `compute_next_run()`（API 进程，创建/暂停/恢复时）都在写。
   `scheduler.py:refresh_job_state` 的注释自陈 *“Another process (standalone scheduler)
   owns next_run_at in this mode”* ——**所有权靠注释约定，不靠机制**。多 API worker 场景下，
   API 写的与调度进程写的会互相覆盖，任务页展示的「下次执行」会抖动。
2. 抢不到租约时每个竞争方各写一条 `skipped` 日志（见 B-13），多实例下该日志的语义未定义。
3. `_recent_skips`（跳过降噪窗口，容量 1024 / 60s）是**进程内 dict**，
   `EVENT_JOB_MISSED` / `EVENT_JOB_MAX_INSTANCES` 是 APScheduler 进程本地事件——
   多实例下「错过执行」只有本进程视角。

**复查确认（健全的部分）**：跨进程去重的地基是好的——`sys_job_lock` 单事务批量申请
（MySQL `FOR UPDATE` / SQLite 单写者）、TTL + 续租 + owner 存活探测、
`recover_interrupted_logs()` 按「活跃租约 + owner 存活」判活，多实例下不会误杀他进程的执行；
`max_instances=1` + 租约保证同一任务绝不并发。**当前形态（多 worker + standalone
独立调度进程）现在就能用**；需要机制化的是「放开 embedded 多 worker」这条路。

**[建议]** ①给 `next_run_at` 明确单一写者：按 `SCHEDULER_MODE` 约束——`standalone` 时
API 进程只读不写（现在 service 层还会写），或引入 `schedule_owner` 字段；
②B-13 修复后，把 `embedded + APP_WORKERS>1` 从硬失败降级为显式配置项
（默认关，开启时打警告），作为「单机简化部署」可选项；③`owner_alive()` 跨主机保守返回
True 导致的死锁只能等 TTL（最长 `timeout+60` 秒）自然过期，在 `docs/定时任务.md`
标注，多机场景可选心跳表。

## 4. 开发细节需改进之处（B 类）

### B-1【数据正确性】审计日志双写，且 `duration_ms` 恒为 0 **[事实]**

两个独立缺陷叠加：

**① 双写**：`OperationLogMiddleware` 对所有**变更类**请求写一条操作日志，
排除前缀只有 `{api_prefix}/auth/{login,refresh,logout}` 与 `{api_prefix}/system/`
（`core/middleware.py:111-115`）。但 `sys/security` 模块的路径是 `/security/**`，
**不在排除列表内**，同时它的 service 层 `_audit()`（`sys/security/service.py:69`）
又调 `kernel/db.log_operation()` 写一条。即：一次
`POST /api/v1/security/ip-rules` 会产生 **2 条**操作日志（中间件一条、服务层一条）。
受影响动作见 `sys/security/service.py` 的 `_commit_audit` / `_audit` 调用点：
`ip-rule.create/update/delete/status`、`user.ban/unban`、`api-key.create/delete/status`（9 处）。
`list_operation_logs` 没有任何去重（`ops/audit/service.py`），管理端「操作记录」会看到重复行。

**② 耗时恒 0**：`duration_ms=0` 硬编码在 4 处——
`kernel/db.py:50`、`ops/audit/service.py:484`、`theme/service.py:82`、`jobs/runner.py:91`；
而中间件写的是真实 `time.perf_counter()` 耗时。同一次请求的两条记录耗时口径还不一致
（一条真实、一条 0），CSV 导出的「耗时(ms)」列统计失真。

**修复建议**：①把中间件的排除列表改为**白名单式**「谁写谁负责」——由各模块通过
`ModuleSpec` 声明 `audit="service"`，中间件据此跳过；或至少把 `/security/` 加入排除前缀；
②`log_operation()` 增加 `started_at` 参数，由调用方传入请求起点，内部算 `duration_ms`；
③补一条断言测试：对每个变更类端点发一次请求，断言 `OperationLog` **恰好新增 1 条**。

### B-2【门禁盲区】模块依赖白名单只做单向包含校验，已有 2 条幽灵条目 **[事实]**

`check_modules.py:170` 只在 `真实边 ∉ ALLOWED_MODULE_EDGES` 时报错，
**从不检查 `ALLOWED_MODULE_EDGES ⊄ 真实边`**。实测（AST 全量扫描 137 文件）：

| 白名单条目 | 真实 import | 结论 |
|---|---|---|
| `config → schedule` | **0 处** | 幽灵条目（事件总线重构后已消灭该边，白名单未同步） |
| `content → notify` | **0 处** | 同上 |
| 其余 12 条 | 各 1~3 处 | 真实存在 |

后果：①审计者看到 14 条边会误判这两个方向仍存在耦合；②白名单会持续腐化——
今天 2 条，半年后可能 8 条，「模块耦合度」这个指标彻底失真。

**修复建议**：`check_modules.py` 增加**双向校验**——`ALLOWED_MODULE_EDGES` 中的每条边
必须有真实 import 对应，否则报「登记了但已不存在的依赖边，请删除」。同时清掉这 2 条。

### B-3【门禁强度】mypy / ruff 规则面过窄 **[事实]**

```toml
[tool.mypy]
python_version = "3.12"
no_implicit_optional = true
warn_redundant_casts = true        # 仅 2 条

[tool.ruff.lint]
select = ["E", "F", "I", "UP"]      # 4 组
ignore = ["E501"]
```

实测：`Any` 出现 **349** 次、`# type: ignore` **25** 处、11 个函数无返回类型标注
（`lifespan` / `healthz` / `readyz` / `meta_version` / `require_permission` 等）。
「mypy 通过」目前的含金量有限。

**修复建议**（分三档推进，不要一次收紧）：
| 档位 | mypy | ruff |
|---|---|---|
| 立即 | `check_untyped_defs=true`、`warn_unused_ignores=true`、`disallow_incomplete_defs=true` | 加 `B`（bugbear）、`C4`、`PIE`、`SIM` |
| 一期 | `disallow_untyped_defs=true`（先对 `core/` + `kernel/`） | 加 `RUF`、`ARG`、`RET` |
| 二期 | `disallow_any_generics`、逐步替换 `Any` 为具体类型 | 加 `ASYNC`、`N` |

### B-4【测试盲区】7,894 行前端 JS 只有语法校验，无行为测试 **[事实]**

现有前端门禁：`check_frontend_imports.py`（导入图 + 217 条导入）、`node --check`（47 个文件语法）、
`check_contract.py`（页面↔模板↔JS 对应、`#id` 存在性）。**没有任何行为断言**。
`DataTable`（取数/渲染/分页）、表单序列化 `serializeForm`/`fillForm`、权限指令、
主题引擎合并逻辑、请求层 401 自动刷新重放——这些都是纯函数或薄 DOM 层，**最容易出回归**
却零覆盖。

**修复建议**：引入 `node --test`（Node 内置测试运行器，**不引入包管理器**，符合零工具链约束）
对纯逻辑模块（`core/format.js`、`core/form.js` 的序列化、`ui.js` 的 DataTable 分页计算）
做单元测试；DOM 相关部分抽纯函数后同法覆盖。

### B-5【前端样板】14 个页面脚本重复 loading / empty / error 三态样板 **[事实]**

全库 47 处三态样板（`loading-block` / `table-empty` / `加载失败` / `暂无…`），分布在 **14 个**页面脚本中，
每处都是 3~6 行几乎相同的 `body.innerHTML = ...`。101 处 `innerHTML` 里，逐条核查后
15 处未走 `esc()` 的插值均为安全上下文（blob URL、数字、编译期常量、已被服务端 `HEX_COLOR`
正则约束的主题色），但**这种安全性依赖人工逐条核查**，没有机制保证新页面不出错。

**修复建议**：抽 `renderState(node, kind, message)` / `emptyRow(colspan, text)` 到 `core/`；
并在 `check_frontend_imports.py` 或新增脚本里加一条**转义哨兵**：`innerHTML` 模板串里的
`${...}` 若不包含 `esc(` 且不是纯数字/常量表达式，报错。

### B-6【无障碍】全站仅 15 个 aria 属性，模态无焦点管理 **[事实]**

实测 `aria-*` 15 处、`role` 2 处。`core/dialog.js` 有初始聚焦与 `Escape` 关闭，
但**没有焦点陷阱（Tab 循环）、没有 `aria-modal`/`role="dialog"`、关闭后焦点未归还触发元素**；
表格无 `<caption>`/`scope`；下拉与树组件无键盘导航；`data-table` 无 `aria-sort`。

**修复建议**：①`dialog.js` 补焦点陷阱 + `aria-modal="true"` + 焦点归还；
②`ui.html` 的 `data_table` 宏补 `<caption class="sr-only">` 与 `scope="col"`；
③新增 `.sr-only` 工具类与 `prefers-reduced-motion` 适配；
④把「新增模板必须带 `aria-label` 或可见文本」写进 `docs/模块与分层规范.md` 前端约定。

### B-7【供应链】无依赖漏洞扫描，无可复现构建 **[事实]**

CI 五个 job（lint/test/contract/docs/mysql）**没有任何** pip-audit / safety / osv-scanner / trivy。
`requirements.txt` 与 `pyproject.toml` 都是范围约束（`fastapi>=0.136,<0.151` 等），
**没有 lock 文件、没有哈希固定**，两次构建可能拉到不同版本。

**修复建议**：①CI 加 `pip-audit` job（`gate.py` 新增 `security` 组）；
②用 `pip-compile` 产出 `requirements.lock`（含哈希），`fastcms init` 优先用 lock 安装；
③`release.py` 发布时输出依赖清单（SBOM 简版）。

### B-8【可观测性】有结构化日志，但没有指标与慢请求视角 **[事实]**

`core/logging.py` 已具备 JsonFormatter、敏感键脱敏、异常分级、`request_id` 串联。
缺的是**度量**：

- 无 Prometheus / OTel 指标端点（QPS、延迟直方图、DB 连接池占用、任务队列深度）；
- 无慢请求/慢查询阈值记录（`OperationLog.duration_ms` 又因 B-1 恒 0，等于没有慢请求视角）；
- `/monitor/server` 的 psutil 数据只反映**当前进程**，多 worker 下看到的不是整机全貌。

**修复建议**：①先修 B-1（耗时数据可信是前提）；②加 `/metrics`（可选开启，Prometheus 文本格式，
用 `prometheus-client` 或手写极简实现以保持零强依赖）；③`OperationLogMiddleware` 对
`duration_ms > 阈值` 额外打一条 WARNING 结构化日志。

### B-9【细节隐患】keyset 分页未强制唯一键 **[事实]**

`core/pagination.py: keyset_paginate` 用 `next_cursor = getattr(rows[-1], key_col.key)`，
文档只说「要求 statement 选择单一实体」。**若 `key_col` 非唯一**（如 `created_at`），
同值行会被游标跳过（漏行）或重复。当前唯一调用点
`ops/audit/service.py:195` 用的是 `LoginLog.id`（唯一主键），所以线上没有问题；
但函数签名没有任何约束，下一个人复用就可能踩坑。

**修复建议**：签名改成 `key_col: InstrumentedAttribute[int]`（收窄到主键），
或在函数内断言 `key_col` 属于 `__table__.primary_key.columns`；docstring 补反例说明。

### B-10【国际化】中文硬编码贯穿全栈 **[事实]**

前端字符串、后端 `AppError` 文案、`ERROR_CODE_STATUS` 同名的中文消息、
CSV 导出表头、通知模板、日志消息全部硬编码简体中文。目前是产品定位使然，
但**没有任何抽取点**——将来要出海或做繁体，改动面是 17,646 + 7,894 行全量。

**修复建议**：现在只做「留缝」不做翻译：①错误响应统一走 `error_payload(code, message_key)`，
message 从一张 `MESSAGES` 表取；②前端加 `t(key, fallback)` 极简函数（默认返回中文 fallback），
新代码用它；③CSV 导出表头从 `ExportColumn` 的 `label` 字段取（已是结构化，只需确认无散落）。

### B-11【测试深度】缺性能基线、并发竞态与属性测试 **[事实]**

439 用例覆盖很广（迁移演练、schema drift、CLI、脚本静态检查都有），但：

- **无性能基线**：列表接口 10 万行数据下的耗时没有任何断言，`total=false` 与 keyset 的收益无从回归；
- **并发竞态专项只有一个**（`test_job_lease_atomic.py`）：刷新令牌轮换、约束冲突转 409、
  限流并发计数都没有并发测试；
- **无属性测试**：`safe_title()`、`neutralize_cell()`、`contains()/LIKE_ESCAPE`、
  `ancestors` 前缀匹配这类「输入空间大、规则简单」的函数最适合 hypothesis 式 fuzz。

**修复建议**：①加 `tests/perf/`（默认跳过，`--run-perf` 时跑）给 5 个核心列表接口做基线；
②对刷新轮换与 `IntegrityError` 路径补 `asyncio.gather` 并发测试；
③对 `neutralize_cell` / `safe_title` 补属性测试（用 `hypothesis`，dev 依赖）。

### B-12【文档债】架构类文档 6 份并存，`docs/` 无索引 **[事实]**

`docs/` 现有 15 个文件（含本文），其中**架构类 6 份**：`开发计划.md`、
`架构梳理与优化方案.md`、`架构评审与重构方案输入.md`、
`架构优化与重构方案-2026-10-27.md`、`架构优化与重构方案-2026-10-28.md` 与本文。
没有 `docs/README.md` 索引，
新人无法判断「哪份是当前真相」。`check_docs.py` 的白名单里
`new-module`、`dev-all` 两条豁免到 **2027-06-30**，是已知的长期债。

**修复建议**：①新建 `docs/README.md` 索引，按「当前真相 / 专题 / 历史归档」三栏组织，
并在每份历史文档头部标注「历史文档，路径以 git 历史为准」；
②`new-module` 脚手架要么在 Phase 2 实现、要么把豁免到期提前到下个版本；
③本文落地后，把 2026-10-27 / 10-28 两份移入 `docs/history/`。

### B-13【日志噪音】租约竞争型 `skipped` 每次落库，且不在空转清理范围 **[事实]**

`jobs/runner.py: _write_skipped_log()`（约 ：70-91）：抢不到租约就写一条 `status="skipped"`
的 `JobLog`；而高频任务的日志自净机制 `_is_idle_noop()`（`runner.py:45-58`）
**只清理持锁方的成功空转**，`skipped` 永不清理。后果：

- 多调度实例下，N 个进程同时触发同一任务 → 1 条 `success` + **(N-1) 条 `skipped`**。
  3 worker + 10s 间隔任务 ≈ 每天约 1.7 万条垃圾日志，任务日志页被刷爆，真正的失败被淹没；
- **单实例现在就有此噪音**：手动「立即执行」与调度触发重叠时同样落一条 `skipped`——
  与多 worker 无关，独立成立。

调度器的 `_recent_skips` 聚合只作用于 `log_scheduler_skip`（MISSED / MAX_INSTANCES 事件），
不覆盖租约竞争路径，两条降噪机制互不相通。

**修复建议**：①竞争型 `skipped` 按 `(job_id, reason)` 做窗口聚合（进程内窗口表，
或复用「近期已跳过」标记），窗口内重复跳过只计数不落库；②或把竞争型 `skipped` 降级为
结构化日志，任务日志页改为聚合展示计数；③补断言测试：同一任务并发触发两次，
`JobLog` 新增 ≤ 2 条且 `skipped` 恒 ≤ 1 条。此修复**与多 worker 无关也有价值**，
应先于任何调度多实例放开落地。

## 5. 优化改进重构方案

### 5.1 目标与原则

**目标**：把「机制半成品」补完、把「两套并存」收敛成一套、把「靠人工核查」换成「门禁守护」。

1. **不破坏硬约束**（零前端工具链 / 零外部依赖可跑 / 数据代码分离）——任何方案若要求引入

1. 本机 `PYTHONPATH` 若包含其它 Python 环境（如 WPS 灵犀的 `python-env`），venv 里的
   `pytest` 会因 stdlib 被遮蔽报 `AssertionError: SRE module mismatch`。
   跑测试前用 `env -u PYTHONPATH -u PYTHONHOME PYTHONNOUSERSITE=1` 清理，或在
   `fastcms doctor` 里加一条 `PYTHONPATH` 污染探测（建议纳入 Phase 0）。
2. 本机批量删除保护会拦截 `.pytest_cache` 写入（`WinError 5`）与 pytest 临时目录清理，
   表现为「测试全绿但退出码异常」。用唯一 `--basetemp` 并加 `-p no:cacheprovider` 即可。
3. 本机 venv 实为 **Python 3.13.14**，而 `pyproject.toml` 与 CI 目标是 **3.12**；
   建议 CI 增加 `3.12 / 3.13` 双版本矩阵（纳入 Phase 4）。
