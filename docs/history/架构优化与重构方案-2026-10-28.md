## 2. 新发现问题清单

### P0-A【架构断层】代码生成器与模块清单机制脱节，产物是「死代码」 **[事实]**

模块清单重构后，模块靠 `app/modules/**/module.py` 被 `discover_modules()` 自动发现并挂载。但 codegen 的产物完全不兼容这套机制，存在**三个断点**：

1. **不生成 `module.py`**：`codegen/generator.py:244-250` 生成 8 类文件（model/schemas/service/router/page.html/page.js/README/manifest.json），没有模块清单。落地指引 `README.md.j2:7` 只说「复制到 `backend/app/modules/{{ module }}/`」——复制后没有清单，`discover_modules()` 扫不到，**模块永远不注册，接口全部静默 404**。
2. **产物落在 app 包之外**：`GENERATED_ROOT = parents[2] / "generated"` 即 `backend/generated/`，在 `app/` 包外，即使补了清单也进不了发现范围。
3. **权限码无出生地**：生成的路由声明 `permission="{{ module }}:list"` 等 5 个码（`router.py.j2:15` 等），但 97 条基线不含它们，生成的 `module.py`（如果将来有）也不声明增量权限——按文档「新模块自行声明」的路径走不通，因为**声明字段存在但没人消费**（见 P1-A）。

**影响**：`tool/codegen` 页面与 `fastcms gen` 是对外宣传的核心生产力功能（docs/代码生成器.md 整篇），但按当前指引走完流程得到的是零效果。这是「完善现有功能」的首要目标。

### P1-A【死代码 + 文档误导】`ModuleSpec.pages/menus` 字段声明了但没有消费方 **[事实]**

- `core/module.py:47-52` 定义 `menus`、`pages` 字段，文档字符串明确说「新模块可自行声明」。
- 全库 grep：`module_pages()` / `module_menus()` **零调用**。唯一被消费的清单函数是 `module_permissions()`（`bootstrap/permissions.py:127-130`）。
- 页面注册仍走 `web/router.py` 的中心化 `PAGES` 元组（38 条，`web/router.py:29-248`）；菜单仍走 `bootstrap/menus.py`（127 行）。
- 后果：新模块作者按 `docs/模块与分层规范.md` 声明 `pages=(...)` 后不会有任何效果——文档承诺了不存在的机制。

### P1-B【模型归属】文件存储是平台能力，却住在 content 业务模块 **[事实]**

`FileObject` 模型与 `is_safe_image` 函数住在 `app/modules/content/`，被 4 个模块跨模块依赖：

| 依赖方 | 引用位置 | 用途 |
|---|---|---|
| auth | `sys/auth/router.py:18-19` | 头像上传落库 + 图片校验 |
| system | `sys/system/services/sessions.py:17-18` | 个人中心头像同上 |
| export | `ops/export/service.py:15`（Notice 模型，另一处） | 导出公告 |
| dashboard | `ops/dashboard/service.py:11`（Notice） | 统计公告数 |

`content` 实际是两个东西捏在一起：**「文件存储」是 kernel 级平台能力**（与 User/Role 同级的基础设施），「公告」才是业务。当前耦合造成 16 条白名单边里有 4 条（auth→content、system→content、export→content、dashboard→content）本质是在借道业务模块拿平台服务。

### P1-C【循环规避】三处函数内 import 暴露了依赖方向反置 **[事实]**

| 位置 | 依赖 | 避让原因 |
|---|---|---|
| `sys/config/service.py:335` | `from app.modules.ops.schedule.scheduler import scheduler_service` | config ↔ schedule 循环 |
| `content/service.py:106` | `from app.modules.ops.notify import hooks` | content ↔ notify 循环（通知订阅公告发布事件） |
| `sys/auth/router.py:111` | `from app.modules.sys.security import service as security_service` | auth ↔ security 循环 |

函数内 import 是循环依赖的标准遮蔽手法——它把「事件通知」「服务账号约定」这类**横切关注点**硬编码进了业务调用方。正确方向是**被依赖方注册回调**（hooks 注册制），调用方只发事件不认识订阅者。notify 模块已有 `hooks.py` 雏形（86 行），但反转不彻底。

### P1-D【文档漂移】两份文档落后于重构后架构 **[事实]**

1. `docs/代码生成器.md`：全文未提 `module.py` / 模块清单（grep 零命中），落地指引会把用户带进 P0-A 的坑。
2. `docs/数据库与工程治理审计.md`：所有证据位置使用重构前路径（`app/modules/schedule/service.py` 等），实际文件已在 `app/modules/ops/schedule/`。作为「带证据的审计文档」，路径失效=证据失效。

### P2-A【可追踪性】`sys/system/service.py` 是 6 路 `import *` 聚合器 **[事实]**

`sys/system/service.py:3-13` 用 6 个星导入聚合 users/roles/menus/depts/sessions/_common。下游 `sys/auth/router.py` 依赖 `system_service.write_login_log` 等 6 个符号（router.py:64,194,228,237,243…），`ops/monitor/router.py:11` 依赖 `kick_session`。星导入让「谁用了哪个函数」无法静态追溯，也是 `revoke_user_sessions` 双名导入坑（上轮修复记录）的根源。

### P2-B【口径不一】`check_api_coverage.py` 硬编码 API 前缀 **[事实]**

`scripts/check_api_coverage.py:25` 写死 `API_PREFIX = "/api/v1"`，而 `check_contract.py` 动态取 `settings.api_prefix`。用户改 `API_PREFIX` 配置后，coverage 检查与前缀相关的判定口径分裂（旧审计 P2-6，本轮复核仍未修）。

### P2-C【重复逻辑】公告分页 count 复制了 core 实现 **[事实]**

`content/service.py:409` 手写 `select(func.count()).select_from(statement.order_by(None).subquery())`，与 `core/pagination.py` 的实现重复；`content/service.py:204,266` 另有两处直接 count（公开列表场景，语义不同，可接受）。核心问题是 409 这处没有复用统一入口，`total=false` 降级特性在公告列表上不可用。

### P2-D【小项】`settings.secret_key` 无缓存 + Windows chmod 静默降级 **[事实]**

`core/config.py:338-351`：`secret_key` 是 property，未显式配置时每次访问都读 `.secret` 文件；`path.chmod(0o600)` 在 Windows 上抛 OSError 被吞（旧审计 P1-10，仍存在）。影响小（文件系统缓存兜底），列为顺手修复。

### 观察项（不计入本轮施工）

- **端点测试薄区**：dashboard/monitor/export 的 API 有基本覆盖（`test_api.py` 内 403/200 断言、`test_export_*.py` 两文件），但无独立专项；codegen 写入链路有 2 个用例。在 P0-A 修复时需**新增**「生成→注册→可访问」闭环测试，此项随 Phase A 一并完成。

## 4. 总体验收标准

1. `fastcms gen --table <t> --module <m> --write` 后，按 README 三步落地，**重启即可在 OpenAPI 看到新路由、权限页看到新码、前端页面可访问**（端到端手测 + A-4 自动化测试双保险）。
2. `grep -rn "module_pages\|module_menus" app/` 有真实消费方，或字段被删除——**不允许死字段**。
3. `ALLOWED_MODULE_EDGES` 条目数 **≤ 14**（auth→content、system→content 消失后）。
4. 模块间函数内 import **0 处**（AST 门禁新增规则护航）。
5. 全量门禁维持绿色：pytest（预期 370+N 通过）、mypy、ruff、contract 组（含 modules 检查）。
6. `check_modules.py` 输出的「增量权限码」在 codegen 演进场景下 > 0 且可解释。

## 5. 刻意不做（本轮）

- **MCP 接口 / 独立 mcp_server 进程**：用户明确本轮不做。可行性结论已给出：独立进程纯 HTTP + API Key（`fck_` 前缀）可行，`mcp` 包不在清华镜像（需 `pypi.org/simple` 或换镜像），方案存档于本文件历史语境，后续单独开题。
- **权限码 97 条基线搬迁**：维持「存量集中、增量走清单」策略（理由见 `core/module.py` 文档字符串）。
- **fastcms new-module 脚手架命令**：Phase A 的 README 三步落地已覆盖 80% 价值，独立命令待 codegen 闭环稳定后再评估。
- **浏览器 E2E / MySQL 备份 CLI**：维持上轮「刻意不做」决策不变。
- **审计日志软删除**：产品策略维持硬删除 + 权限门 + 留痕。

## 8. 运行期潜在问题与修复（第二轮审计）

第 1~3 节解决的是「结构不合理」，本节解决的是「结构对但运行时会咬人」的问题：
静态门禁全绿、测试全绿，仍然存在只在并发、多进程或特定输入下才暴露的缺陷。

### 8.1 已修复

| 编号 | 问题 | 触发条件 | 后果 | 修复 |
|---|---|---|---|---|
| R-1 | 约束冲突被当成服务器错误 | 并发插入同 `username` / 同 `code`：先查后插的预检挡不住竞态 | 客户端拿到 500 `INTERNAL_ERROR`，把「数据重复」当成系统故障 | `core/errors.py` 新增 `integrity_error_handler` → 409 `DATA_CONFLICT`，日志只记异常类名、不回显 SQL；`main.py` 注册 |
| R-2 | 独立调度器没有事件订阅 | `fastcms scheduler` 不走 `create_app()`，各模块 `module.py` 从未导入 | `job.finished` 无订阅者，任务失败通知被静默丢弃 | `cli.py:_scheduler()` 在 `ensure_database()` 后调用 `discover_modules()` |
| R-3 | 跨进程时区不同步 | 事件总线是进程内的：Web 进程改时区，独立调度器收不到 | 改完时区必须重启调度器，否则任务按旧时区触发 | 每轮同步前取 `before = current_timezone()`，再读库比对，变了就 `resync_timezone()` |
| R-4 | CSV 公式注入 | 公告标题、用户名、User-Agent 等用户可控字段以 `=` `+` `-` `@` 开头 | 导出文件在 Excel/WPS 打开即执行公式（数据外泄、老版本 DDE 命令执行） | `core/export.py` 新增 `neutralize_cell()`，在 `csv_response` 这唯一出口中和表头与每一行；真数字与科学计数法不误伤 |
| R-5 | 事件名拼错静默丢弃 | `events.publish("job.finshed")` 之类笔误 | 事件发出去没人收，且没有任何报错 | `publish()` 对未登记事件记 error 日志；`check_modules.py` 新增 `check_event_publishers()`，扫描 `publish("字面量")` 必须在 `KNOWN_EVENTS` 里 |
| R-6 | 生成代码被标题打断 | `--title '他说"你好"'`：标题直接插进 `description="..."`、docstring 与前端 JS 字符串 | 产物是 `SyntaxError`，用户复制进 `app/modules` 后启动即崩，报错指向生成文件 | `codegen/generator.py` 新增 `safe_title()`，在生成器边界统一中和；8 个模板一处不改 |
| R-7 | 注释与实现不符 | `core/export.py` 注释写「流式响应」，实际是把整份 CSV 编码成一个分片 | 读者会以为内存与表大小无关，误判大数据量导出行为 | 改注释：说明是「有界物化」，上界由 `limit` 决定，以及要支持百万行时该怎么改 |

R-6 的实现细节值得单独记一笔：`"` 不能替换成 `'`。Python 模板用双引号、JS 模板
用单引号，换一种引号只是把语法错误从 `.py` 挪到 `.js`（`frontend.page.js.j2` 里
`'新建{{ title }}'` 会被标题里的单引号截断）。所以两种引号一律删掉，反斜杠换成
`/`，换行压成空格，空标题兜底「未命名」。回归测试同时覆盖两侧：对每个恶意标题
`compile()` 所有生成的 `.py`，并检查生成的 `.js` 里标题所在行单引号成对。

### 8.2 复查过、确认没有问题的点

避免「只报问题不报结论」，下面这些是特意查过并确认设计正确的：

| 关注点 | 结论 |
|---|---|
| 刷新令牌轮换 | 有 reuse detection（命中 `previous_refresh_token_hash` 即撤销会话）+ 条件更新做轮换锁，并发刷新只有一方成功 |
| 多进程重复执行任务 | `schedule/locks.py` 的 DB 租约（TTL + owner 存活探测 + 续租），拿不到锁写「跳过」日志 |
| 上传落盘 | 异步读分片、`asyncio.to_thread` 写盘、超限/类型不符时删半成品；去重按上传者隔离，不跨用户 |
| 下载响应头 | 文件名走 `quote(name, safe="")`，并带 `nosniff` + `CSP: sandbox`，避免存储型 XSS |
| 路径穿越 | `storage_file()` 用 `is_relative_to(STORAGE_ROOT)` 兜底 |
| 内存缓存无上限 | `MemoryCache` 有 `CACHE_MAX_ITEMS` 兜底，先清过期再按插入顺序淘汰 |
| 限流在多进程下失效 | 限流计数走 `get_cache()`，`REDIS_ENABLED=true` 时是共享计数 |
| 登录爆破 | 按来源 IP 累计失败次数，达阈值自动生成临时封禁规则并重置计数 |
| 导出泄露敏感列 | 列白名单由调用方显式给出，不允许整体序列化 ORM 对象 |
| 会话事务语义 | `session_scope` 异常回滚、正常提交；`get_db` 不隐式提交，由端点显式 commit |
