## 0. 结论摘要

Fast CMS 的技术选型（FastAPI + Jinja2 直出 + 原生 ES Module）是**真实有效的差异化**：没有 Node、没有构建、没有独立前端进程，单进程单端口即可交付后台 + 前台 + API。这套取舍应当作为不可动摇的约束保留。

当前的问题不是"架构错了"，而是**能力已经长到 15.5k 行 Python / 7.1k 行 JS，而工程化配套还停留在原型阶段**：

1. **工程基线缺失**：无 `.gitignore`、无 `.dockerignore`、无 CI。仓库直接 `git init && git add .` 会把 `backend/data/.secret`（自动生成的签名密钥）、SQLite 库、上传文件、虚拟环境一起提交；README 却已在"工程能力"里宣称具备 CI。
2. **入口过多**：安装有 `install.cmd` / `install.sh` / `install.py` / `make install` 四个入口，启动有 `start.cmd` / `start.sh` / `start.py` / `make dev` / `make preview` 五个入口，同一个动作平均 4 份实现。
3. **配置太散**：`Settings` 有 **53** 个字段，`.env.example` 原先只列了 **47** 个键，其中 `IP2REGION_*` 三项与 `AUTH_IP_BAN_MINUTES` 完全没有出现；路径归一化逻辑在 `config.py`、`env_check.py`、`start.py` 里**各写了一遍**。**（配置面已收敛，见第 7 节）**
4. **扩展成本高**：新增一个业务模块要手改 **6 个中枢文件**（`main.py`、`db/models.py`、`bootstrap/permissions.py`、`bootstrap/menus.py`、`web/router.py`、外加模板与页面 JS），目前有 **30 处** `from app.modules` 的显式 import 承担注册职责。
5. **升级体验有坑**：静态资源引用不带版本号（`base.css` 无 `?v=`），`StaticFiles` 也不发 `Cache-Control`，升级后浏览器可能继续用旧 CSS/JS，表现为"升级完页面错乱"。
6. **文档漂移**：`docs/部署与升级.md` 引用的 `make dev-all`、`docs/开发计划.md` 引用的 `make check`，在 Makefile 中都不存在。

优化方向明确：**收敛入口、收敛配置、补齐工程基线、把注册改为自动发现**。预计 P0 项 1~2 人天即可把"新机器到能登录"压缩到一条命令，P1 项 1~2 周把"新增模块"从 6 处手改压缩到 1 条命令。

## 1. 现状架构梳理

### 1.1 设计定位与取舍

| 维度 | 选择 | 代价 | 评价 |
|---|---|---|---|
| 前端 | Jinja2 服务端渲染 + 原生 ES Module | 无组件生态、复杂交互要手写 | 换来零构建、零 Node，**保留** |
| 进程模型 | 单进程单端口承载后台 + 前台 + API | 前后端无法独立扩缩 | 后台场景足够，**保留** |
| 默认存储 | SQLite（`aiosqlite`） | 单写者、不适合多 worker | 开箱即用，**保留** |
| 缓存/锁 | 进程内实现，Redis 可选且默认关闭 | 多 worker 需显式开启 | 显式失败优于静默降级，**保留** |
| 调度 | APScheduler + 数据库租约去重 | 依赖 DB 表做协调 | 无需 Redis，**保留** |
| 形态 | 模块化单体、单租户 | 无租户隔离 | 与定位一致，**保留** |
| 契约 | OpenAPI 导出 + 双向校验脚本 | 每次改接口要重导 | 强护栏，**保留并加强** |

### 1.4 请求链路

```text
HTTP 请求
  → RequestContextMiddleware  注入 request_id、记录耗时
  → IpGuardMiddleware         查 IP 规则（封禁优先于放行）
  → RateLimitMiddleware       敏感接口窗口限流（429 + Retry-After）
  → OperationLogMiddleware    写操作审计（脱敏后入库）
  → 路由匹配
      ├─ 页面路由（app/web）→ Jinja2 渲染，注入 window.__FASTCMS__
      └─ API 路由（modules/*）→ require_admin → require_permission(code)
                              → get_current_user（每次请求重载权限与数据范围）
                              → service（按 ctx 裁剪数据范围）
                              → success(data) 统一信封
```

关键设计：**权限与数据范围每请求从数据库重载**，因此改角色/菜单/部门无需重新登录，也无需吊销会话。这是很强的体验优势，应在文档里显式写明为"卖点"。

### 1.5 启动引导链路

```text
lifespan
  ├─ 校验 APP_WORKERS>1 与 embedded 调度器冲突（直接拒绝启动）
  ├─ configure_logging()           JSON 日志 → stdout（容器友好）
  ├─ init_cache()                  内存 或 Redis（显式启用失败即启动失败）
  ├─ ipgeo.startup()               xdb 缺失只告警
  ├─ BootLock(data/bootstrap.lock) 多 worker 串行化引导
  │    ├─ ensure_database()        Alembic 迁移（SQLite 自动备份）
  │    ├─ _ensure_seed()           种子 + 权限码补齐
  │    └─ load_timezone_from_db()  系统参数优先于环境变量
  └─ scheduler_service.start()     仅 embedded 模式
```

## 2. 核心功能盘点

| 能力 | 成熟度 | 说明 | 易用性缺口 |
|---|---|---|---|
| 认证与会话 | 强 | JWT + 轮换 refresh + HttpOnly Cookie + 登录锁定 + 强制改密 + 会话撤销 | 默认口令固定，无"首次启动打印一次性口令"引导 |

| 部署与升级 | 中 | 一键脚本、Docker、Compose profiles、发布包 | 入口重复、镜像单阶段、无依赖锁、迁移并发无协调 |

## 3. 问题诊断

编号规则：`U` 易用性 / `D` 部署 / `A` 架构。优先级 `P0` 立即 / `P1` 近期 / `P2` 中期。

### 3.1 易用性问题

| 编号 | 问题 | 证据 | 影响 | 优先级 |
|---|---|---|---|---|
| U-01 | **无 `.gitignore`** | 仓库根目录仅 9 个条目，无 `.gitignore` | `git add .` 会提交 `backend/data/.secret`（签名密钥）、`fastcms.db`、`uploads/`、`.venv/`。**安全事故级** | P0 |
| U-02 | **无 `.dockerignore`** | 同上 | 构建上下文包含 `.venv`、`data/`、260KB `openapi.json`，构建变慢且可能把本地密钥打进镜像层 | P0 |
| U-03 | **无 CI** | 无 `.github/`，但 README 第 22 行宣称具备 CI | 门禁只能靠人工 `make contract-check`；PR 无自动回归 | P0 |
| U-04 | **配置面与示例不一致**（已修复） | 原 `Settings` 53 字段 vs `.env.example` 47 键，`IP2REGION_*` 三项与 `AUTH_IP_BAN_MINUTES` 未出现 | 使用者不知道这些开关存在，遇到 IP 归属地或自动封禁问题时无从下手 | P0 |
| U-05 | **路径归一化四处重复** | `core/config.py` `_normalize_api_prefix` / `_normalize_site_base`；`scripts/env_check.py` `DEFAULT_*`；`scripts/start.py` `resolve_api_prefix` / `resolve_site_base`；`scripts/install.py` 复用 env_check | 改一次规则要改三处，脚本算出的 URL 可能与后端实际挂载不一致 | P0 |
| U-06 | **入口过多** | 安装 4 个（`install.cmd`/`install.sh`/`install.py`/`make install`）、启动 5 个（`start.cmd`/`start.sh`/`start.py`/`make dev`/`make preview`） | 文档要解释 9 条路径；`.cmd` 里硬编码了 10 个 conda 候选路径，难维护 | P1 |
| U-07 | **CLI 需要手工拼路径** | `python -m app.cli` 必须 `cd backend` 且用 venv 里的解释器 | 用户经常 `python -m app.cli` 报 `ModuleNotFoundError` | P1 |
| U-08 | **静态资源无版本号** | `templates/base.html` 第 10 行 `href="{{ base }}static/css/base.css"`，无 `?v=`；`StaticFiles` 不发 `Cache-Control` | 升级后浏览器可能用旧 JS/CSS，出现"页面错乱/按钮失效"，用户误判为升级失败 | P0 |
| U-09 | **文档漂移** | `docs/部署与升级.md:9` 引用 `make dev-all`，Makefile 无此目标；`docs/开发计划.md:1382` 引用 `make check`，同样不存在 | 照文档操作直接报错 | P0 |
| U-10 | **README 过长** | `README.md` 409 行，`docs/开发计划.md` 1425 行；无架构总览文档 | 新人需读 400 行才知道"从哪开始"；无一张全局架构图 | P1 |
| U-11 | **`core.js` 单文件 1000 行** | 请求/会话/表单/弹窗/时区/主题全在一个文件 | 改一处要读全文件，冲突概率高 | P2 |
| U-12 | **`system/service.py` 1287 行** | 用户+角色+菜单+部门+权限全在一个 service | 认知负荷高，测试难聚焦 | P2 |
| U-13 | **前端失败无兜底 UI** | `app.js` 中页面模块 `import` 失败仅 `console.error` | 用户看到空白页，无错误提示、无重试入口 | P1 |
| U-14 | **代码生成无开箱样例** | `start.py:256` `ensure_demo_table()` 仅在 test 模式用裸 `sqlite3` 建 `demo_article` | 首次打开"代码生成"页无表可选，功能看起来是坏的 | P1 |
| U-15 | **前台近乎占位** | `static/css/portal.css` 43 行，`build_portal_router` 只有首页 + 404 | 若定位是"后台基座"应在文档明说；若定位含官网，则明显不足 | P2 |

### 3.2 部署问题

| 编号 | 问题 | 证据 | 影响 | 优先级 |
|---|---|---|---|---|
| D-01 | **镜像单阶段 + editable 安装** | `docker/Dockerfile`：`COPY backend/ /app/backend/` 后 `pip install -e /app/backend` | 任一 `.py` 改动都会让依赖层缓存失效、全量重装；生产镜像里是 editable 安装（依赖源码路径） | P1 |
| D-02 | **无依赖锁定** | `pyproject.toml` 只有 `>=x,<y` 区间 | 不同时间构建的镜像依赖版本不同，无法复现线上；升级排查困难 | P1 |
| D-03 | **compose 文件不在根目录** | `docker/compose.yml` | `docker compose up` 在根目录直接失败，必须记 `-f docker/compose.yml` | P1 |
| D-04 | **compose 关键变量默认空** | `APP_SECRET_KEY: ${APP_SECRET_KEY:-}`、`INITIAL_ADMIN_PASSWORD: ${INITIAL_ADMIN_PASSWORD:-}` | 生产环境留空时：密钥自动落到卷里（卷重建即失效、全员掉线）；初始口令为空会让 `init` 直接失败，报错信息不指向 compose 配置 | P1 |
| D-05 | **迁移在多副本下无协调** | `entrypoint.sh` 每次启动跑 `db upgrade` + `seed`；`main.py` 的 `BootLock` 在 uvicorn 进程内，覆盖不到 entrypoint | 多副本同时启动时 Alembic 并发执行，SQLite 下可能 `database is locked` | P1 |
| D-06 | **无启动依赖编排** | `compose.yml` 中 `app` 未 `depends_on` mysql/redis 健康状态 | 启用 mysql profile 时 app 可能先于 MySQL 就绪而启动失败 | P1 |
| D-07 | **无 `/metrics`** | 仅有 `/healthz`、`/readyz` | 无法接入 Prometheus 做容量与错误率监控 | P2 |
| D-08 | **发布门禁不含 mypy** | `scripts/release.py:152-156` 只有 ruff/pytest/openapi/契约/覆盖；`make lint` 才有 mypy | 类型问题可能进入发布包 | P1 |

## 4. 优化方案

### 4.1 设计原则（不可破坏的约束）

任何改动必须同时满足以下五条，否则方案作废：

1. **零构建**：`git clone` 后不需要任何前端工具链，改模板/CSS/JS 刷新即生效。
2. **单进程**：默认形态仍是一个 `uvicorn` 进程承载页面 + API，不引入独立前端服务。
3. **零外部依赖可跑**：默认 SQLite、无 Redis、无 MySQL、无 Node。
4. **失败要响**：配置错误、依赖缺失、迁移不一致必须启动即失败并给出可执行提示，不静默降级。
5. **契约不放松**：OpenAPI、权限码、页面连通性校验只能加强，不能因为重构而跳过。

### 4.2 目标架构（演进后）

│ app/core/config.py  （唯一配置事实源）                           │

### 4.4 P1：易用性与部署主攻（1~2 周）

目标：把"新增模块"和"上线部署"这两条最常走的路压到一条命令。

#### P1-1 统一 CLI 入口 `fastcms`

```toml
# backend/pyproject.toml
[project.scripts]
fastcms = "app.cli:main"
```

| 命令 | 等价动作 | 收益 |
|---|---|---|
| `fastcms doctor` | `env_check` + `/readyz` + 迁移版本 + 权限码 + 契约 | 一条命令输出全部问题 |

| `fastcms upgrade` | 备份 → 迁移 → 种子 → 打印版本差异 | 升级步骤固化为代码 |

#### P1-2 模块自动发现 + 脚手架

```python
# app/modules/crm/module.py
from app.core.module import ModuleSpec

MODULE = ModuleSpec(
    name="crm",
    router=router,                    # 自动 include，prefix=/crm
    models=[Customer, Contact],        # 自动进 metadata
    permissions=[("crm:customer:list", "客户列表"), ...],
    menus=[{"name": "客户管理", "path": "/crm/customer", ...}],
    pages=[{"path": "/crm/customer", "template": "pages/crm/customer.html"}],
)
```

- `main.py` 遍历 `pkgutil.iter_modules(app.modules.__path__)`，导入各 `module.py` 的 `MODULE`，统一注册；**30 处显式 import 收敛为 1 处遍历**。
- `bootstrap/permissions.py` 与 `bootstrap/menus.py` 改为"内置基线 + 模块声明"合并，保留现有种子兼容。
- `fastcms new-module crm --resource customer` 生成完整 6 件套：`module.py` / `models.py` / `schemas.py` / `service.py` / `router.py` + 模板 + 页面 JS + 迁移骨架 + 权限码 + 菜单项。
- **验收**：从零到 `/admin/crm/customer` 可打开、可 CRUD，全程 ≤ 2 条命令、≤ 5 分钟，`make contract-check` 通过。

#### P1-3 代码生成器升级为"模块落地器"

- 在现有 `codegen/generator.py` 产物基础上补 `module.py`，使生成结果**可被自动发现**。
- 新增 `--apply`：写入 `backend/generated/<module>/` 后，打印"下一步执行 `fastcms new-module --from-generated`"的一行提示；或直接落到 `app/modules/<name>/` 并自动注册（需二次确认）。
- 内置演示表：把 `start.py` 里裸 `sqlite3` 建 `demo_article` 的逻辑移入 `app/cli.py` 的 `seed --demo`，供 `fastcms doctor --demo` 使用。

#### P1-4 镜像与依赖可复现

```dockerfile
# 多阶段：依赖层与代码层分离，代码改动不再重装依赖
FROM python:3.12-slim AS builder
COPY backend/pyproject.toml backend/requirements.lock /tmp/build/
COPY backend/app /tmp/build/app
RUN pip wheel --no-cache-dir -w /wheels -r /tmp/build/requirements.lock \
 && pip wheel --no-cache-dir -w /wheels --no-deps /tmp/build

FROM python:3.12-slim AS runtime
COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir --no-index --find-links=/wheels fastcms-backend \
 && rm -rf /wheels
COPY backend/app /app/backend/app
```

| 项 | 动作 |
|---|---|
| 依赖锁 | 用 `pip-compile` 或 `uv lock` 生成 `backend/requirements.lock`，`pyproject.toml` 保留区间作为约束 |
| 安装方式 | 生产镜像改 `--no-editable`，`app` 目录整体 COPY，避免 editable 依赖源码路径 |
| 元数据 | `LABEL org.opencontainers.image.version` 由构建参数注入 |
| 迁移协调 | `entrypoint.sh` 的 `db upgrade` 改为 `fastcms db upgrade --wait-lock`（复用 `BootLock`，超时退出并给出提示），或 compose 增加一次性 `migrate` 服务 + `depends_on: {migrate: {condition: service_completed_successfully}}` |
| 启动编排 | `app` 增加 `depends_on`，mysql/redis 用 `condition: service_healthy` |
| 根目录 compose | 新增根 `compose.yaml`（`docker compose up` 直接可用），原 `docker/compose.yml` 保留为高级形态 |
| 变量校验 | `entrypoint.sh` 在 `APP_ENV=production` 时断言 `APP_SECRET_KEY` 与 `INITIAL_ADMIN_PASSWORD` 非空，缺失时打印生成命令并退出 |

#### P1-5 前端可用性兜底

| 问题 | 方案 |

| 迁移加锁 | 启动变慢或锁超时 | 锁超时默认 60s 并打印持有者 PID；`AUTO_MIGRATE=false` 时完全跳过 |
| 静态资源 immutable 缓存 | 若版本号计算失误，用户永久拿旧文件 | 版本号含 mtime 哈希；提供 `ASSET_VERSION` 环境变量强制覆盖；`/readyz` 输出版本号便于核对 |
| 文档重构丢信息 | 老用户找不到旧内容 | 旧 README 全文归档为 `docs/README-full.md`，新 README 顶部链接 |

**总回滚策略**：P0/P1 每项独立可回退，无数据迁移、无表结构变更（除 P1-2 的 `module.py` 属新增文件）。P2 的 `system` 拆分保留 `service.py` re-export，可随时回切。
