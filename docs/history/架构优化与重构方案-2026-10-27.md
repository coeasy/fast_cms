## 0. 执行结论

Fast CMS 的架构底座是清楚的：FastAPI 模块化单体承载后台页面、前台页面与 API；Jinja2 直出 HTML + 原生 ES Module 保持零构建交付；权限码 `{module}:{resource}:{action}` 作为菜单、按钮、路由和接口的共同事实源；OpenAPI 与脚本门禁约束前后端契约；数据库为任务、会话、审计和配置的唯一事实源，APScheduler 仅作为执行器。这个取舍符合低资源管理后台的定位，**不建议推倒重来，也不建议改成微服务或引入独立 SPA 前端**。

当前风险主要集中在四个方面：一是“安全承诺与实现不一致”，包括 CSRF、密钥存储、CORS 与导出边界；二是“数据权限覆盖不完整”，通用导出、审计响应与部分业务语句没有统一走数据范围；三是“工程基线不够硬”，MySQL 矩阵、迁移回滚、发布门禁、缓存一致性、调度租约原子性和测试隔离仍存在缺口；四是“大模块与大前端文件带来维护阻力”，`system/service.py` 与 `core.js` 等文件需要按聚合拆分。

因此推荐采用 **P0 止血、P1 加固、P2 演进** 的三阶段路线：先修安全与契约/事务边界，再补数据与部署可靠性，最后做模块拆分、性能治理与可观测性升级。P0 阶段应优先于新功能开发。

## 1. 当前架构梳理

### 1.1 运行架构

```text
浏览器
  ├─ GET /admin/**          Jinja2 SSR 页面 + 原生 ES Module
  ├─ GET /front/**          前台 SSR 页面
  └─ /api/v1/**             JSON envelope，Bearer JWT / API Key
          │
FastAPI 应用工厂（backend/app/main.py）
  ├─ 中间件：RequestContext → IpGuard → RateLimit → OperationLog → CORS
  ├─ 路由：auth / system / config / audit / monitor / dashboard /
  │        export / schedule / security / content / notify / codegen / theme
  ├─ 页面挂载：VersionedStaticFiles + admin/portal/blank layouts
  └─ 生命周期：cache → ipgeo → BootLock → Alembic → seed → timezone → scheduler
          │
业务服务层（backend/app/modules/*）
          │
SQLAlchemy 2 async + Alembic（backend/app/db、backend/migrations）
          │
SQLite（默认）/ MySQL 8（可选）+ 本地上传目录
```

### 1.2 后端分层

| 层 | 位置 | 责任 | 主要约束 |
|---|---|---|---|
| 入口 | `backend/app/main.py` | 应用工厂、中间件、生命周期、页面/API 挂载 | 统一异常处理、启动前迁移检查 |
| 核心 | `backend/app/core/*` | 配置、鉴权、权限、数据范围、安全原语、缓存、日志、分页、导出 | 方言差异只允许在 `db`/核心适配层出现 |
| 业务 | `backend/app/modules/*` | 13 个业务域的 models/schemas/service/router | Service 不接收 FastAPI Request/Response |
| 任务 | `backend/app/jobs/*` | 注册表任务、Python 子进程、租约执行、中断恢复 | 任务定义以 `sys_job` 为准 |
| 基线 | `backend/app/bootstrap/*` | 权限码、菜单树、种子数据 | 权限码变更需与 OpenAPI 同步 |
| 数据 | `backend/app/db/*`、`backend/migrations/*` | ORM、引擎、迁移、备份 | SQLite/MySQL 可移植 |
| 前端 | `backend/app/web/*` | Jinja2 模板、静态资源、原生 JS 页面 | 无 Node 构建链 |

### 1.3 前端架构

前端采用三层结构：

1. 组件层：`templates/components/ui.html`、`static/css/base.css` 和主题 CSS 变量。
2. 骨架层：`templates/layouts/admin.html`、`portal.html`、`blank.html` 与 `static/js/shell/*`。
3. 页面层：`templates/pages/**`、`static/js/pages/**`（后台）与 `templates/portal/**`、`static/js/portal/**`（前台），通过 `page_key` 动态加载；请求层集中在 `static/js/core/`（request/session/form/theme/time/… 分模块），统一处理 envelope、401 单飞刷新、弹层、表单、时区与主题。

**前台与后台基座边界（P2-10）**：`/front/**`（`build_portal_router` + `layouts/portal.html` + `shell/portal.js`）是**公开站点外壳**——无登录守卫、无侧边栏、不加载任何后台资源（`admin.css`/`shell/admin.js`），只消费匿名可读的公开接口（已发布公告等）。`/admin/**`（`build_admin_router` + `layouts/admin.html` + `shell/admin.js`）是**后台基座**——登录态、菜单树、权限按钮、审计与通知铃铛。两者共享的只有 `base.html`（组件层 `base.css` + `core/` JS 基建），互不加载对方的页面/外壳资源，由 `tests/integration/test_web_mount.py` 强制隔离。前台新增页面 = 在 `build_portal_router` 加路由 + `templates/portal/*.html` + `static/js/portal/*.js`，`app.js` 按 `page_key.startswith('portal/')` 自动分发。

前端不引入构建步骤的取舍应继续保留，`core.js` 已按职责拆成 request/session/form/theme/time 等模块（`core.js` 仅作 re-export 兼容入口），页面权限判断以服务端下发的权限集合为准。

### 1.4 核心链路

#### 认证与会话

`POST /auth/login` 校验用户状态、封禁、密码与登录失败计数，创建数据库会话并签发 access JWT；refresh token 只以 hash 形式保存，写入 HttpOnly Cookie。刷新时对旧 refresh hash 做重放检测，并通过条件更新轮换令牌。鉴权依赖在每个请求上重新加载用户状态、会话状态、token_version、权限码和数据范围。

#### 权限与数据范围

`bootstrap/permissions.py` 声明权限码，菜单和路由引用同一套权限码，`PermissionAPIRouter` 将 `x-permission` 写入 OpenAPI 并注入权限依赖。超级管理员绕过权限码但仍走会话与审计；普通用户通过角色绑定获得权限码。数据范围由 `get_data_scope`、`apply_user_scope`、`user_in_scope` 和 `scope_user_ids` 统一裁剪。

#### 定时任务

`sys_job` 是任务定义事实源，APScheduler 只负责触发。执行前申请 `sys_job_lock` 数据库租约，执行期间续租，结束后释放；`running` 日志和 `run_token` 记录单次执行生命周期；重启时根据活跃租约恢复中断日志。任务模式包括 `embedded`、`standalone`、`disabled`，多 worker 场景应使用独立调度进程。

#### 数据与迁移

迁移链通过 Alembic 维护，`ensure_database` 在启动时检查迁移版本并按环境策略升级；SQLite 升级前自动备份到 `data/backups/`。`test_schema_drift.py` 目前主要守护模型列级覆盖，索引、唯一约束和 downgrade 路径仍需补强。

#### 契约与门禁

现有门禁包括 `scripts/check_contract.py`、`scripts/check_api_coverage.py`、`scripts/check_docs.py`、`app.cli check-permissions`、`pytest`、`ruff`/`mypy` 和 `scripts/release.py`。问题不在于缺少概念，而在于不同入口的门禁内容不一致，且部分能力只有文档承诺、没有自动化验证。

## 2. 架构设计不合理之处

### 2.1 架构层面的判断

| 编号 | 不合理点 | 证据 | 影响 | 处理方向 |
|---|---|---|---|---|
| A-01 | 模块注册依赖大量显式 import，缺少模块契约或自动发现 | `main.py`、`db/models.py`、`bootstrap/seed.py` 存在多处模块导入；旧架构文档也记录了约 30 处注册入口 | 新增模块需要改多个中枢文件，漏注册会导致路由 404、模型不建表或种子不完整 | 保留模块化单体，但引入轻量 `ModuleSpec`/注册清单；不要引入运行时插件系统 |
| A-02 | 服务层职责过度集中 | `backend/app/modules/system/service.py` 约 1288 行，涵盖用户、角色、菜单、部门、权限、会话、导入 | 单文件耦合高，测试难聚焦，事务边界容易混杂 | 按聚合拆成 user/role/menu/dept/permission/import 等服务，保留顶层 re-export 兼容导入 |
| A-03 | 前端核心脚本职责过载 | `backend/app/web/static/js/core.js` 超过 1000 行，集中请求、会话、表单、弹层、时区、主题 | 修改局部功能容易引入跨页面回归，合并冲突频繁 | 拆分 request/session/form/theme/time/dialog，保留统一入口 |
| A-04 | 契约与实现存在多处口径漂移 | 导出上限、任务 code 唯一性、主题/代码生成器文档术语、发布门禁内容均有不一致 | 开发者可能按错误契约实现调用方或自动化测试，生产行为难以预测 | 建立“一个常量/一个事实源/一个门禁清单”，由脚本自动校验 |
| A-05 | 数据权限只覆盖部分资源，导出链路与查询链路不是同一套语义 | 用户导出走 `apply_user_scope`，角色/字典/公告/任务日志导出语句直接忽略数据范围 | 权限模型在列表接口上有效，在批量下载上失效，形成越权泄露面 | 数据范围必须在所有导出、审计和批量读取语句中统一收口 |
| A-06 | 审计/日志写入与请求事务边界不清 | `write_login_log`、`write_export_audit` 内部 commit，且审计导出存在连续两次 commit | 业务回滚与审计留存的关系不可预期，可能出现半提交语义 | 审计写入使用独立 session/事务，业务请求事务与审计事务明确分离 |
| A-07 | 缓存、锁与多进程一致性依赖部署约定，缺少运行时强校验 | MemoryCache/RedisCache 双轨；`AUTH_IP_BAN`、配置、字典、限流在多 worker 下可产生最长数分钟不一致 | 多进程部署时权限/配置/封禁行为不可预测 | 多 worker 强制 Redis 或明确降级策略；启动时打印缓存后端并校验配置 |
| A-08 | 安全承诺与代码实现不完全一致 | `docs/认证与权限.md` 描述 Origin/CSRF 防护，但 auth 路由主要依赖 `SameSite=Lax`；文档与代码对导出上限也有差异 | 文档会误导安全评审；调用方无法建立正确威胁模型 | 先实现安全控制，再让文档由同一配置/测试生成或校验 |

### 2.2 架构上应保留的部分

以下部分不是问题，重构时必须保持：

- 模块化单体与单进程单端口交付；
- Jinja2 SSR + 原生 ES Module 的零构建前端；
- 权限码注册表、菜单、按钮、路由、OpenAPI `x-permission` 的统一事实源；
- 数据库作为任务、会话、审计、配置事实源；
- APScheduler 只做执行器，任务执行依赖数据库租约；
- OpenAPI、接口连通性、页面/脚本/文档静态校验门禁；
- 不为多租户、插件化、微服务等未明确需求预留半成品抽象。

## 3. 详细开发细节需要改进的问题

### 3.1 P0：安全、事务与数据边界

| 编号 | 位置 | 当前问题 | 风险 | 建议 | 验收 |
|---|---|---|---|---|---|
| P0-1 | `backend/app/modules/auth/router.py`、`docs/认证与权限.md` | refresh/logout 主要依赖 `SameSite=Lax`，未见完整 Origin/Referer 校验，文档却承诺更强防护 | 跨站请求防护与文档安全承诺不一致 | 对 refresh/logout 等 Cookie 认证接口增加同源校验；明确 CORS、Cookie 与 CSRF 的组合策略 | 跨源 refresh 被拒绝；同源刷新正常；文档与实现一致 |
| P0-2 | `backend/app/main.py` CORS 配置 | `allow_credentials=True` 与宽泛 methods/headers/origins 组合存在扩大攻击面的风险 | 配置为 `*` 或宽泛来源时，凭据暴露面扩大 | 配置校验禁止 `allow_origins=*` 与 credentials 同开；methods/headers 白名单化 | 非法配置启动失败或明确告警；预检只返回实际允许项 |
| P0-3 | `backend/app/modules/notify/models.py`、`backend/app/core/config.py` | 通知渠道 `secret` 明文入库；`.secret` 文件权限在 Windows 下不可控 | 数据库或备份泄露即可拿到第三方签名密钥 | 使用应用密钥派生的对称加密存储 secret；Windows 明确 ACL 处理；备份策略说明加密边界 | DB dump 不显示明文；解密、轮换、失败告警可测试 |
| P0-4 | `backend/app/modules/export/router.py`、`core/export.py`、`modules/export/service.py` | 导出上限存在 `50000`、`10000` 和文档 `10000` 多套口径 | 调用方按错误上限取数，截断行为不可预测 | 建立唯一 `MAX_EXPORT_ROWS`，路由、服务、响应头和文档统一引用 | 超限请求稳定截断并回传 `X-Export-Truncated`/`X-Export-Limit` |
| P0-5 | `backend/app/modules/export/service.py` | 角色、字典、公告、任务日志等导出语句没有统一 `apply_user_scope` | 受限数据范围用户可导出范围外数据 | 所有批量导出语句统一走数据范围；确实全局可见的资源必须有权限码与显式白名单说明 | 受限用户导出结果不包含范围外数据；越权用例通过 |
| P0-6 | `backend/app/modules/audit/service.py` | 导出审计存在连续两次 commit；audit 自建 CSV 响应与 `core/export.py` 不一致 | 事务边界混乱，导出响应头/截断语义双份维护 | 删除重复 commit；审计导出复用统一 CSV 响应组件 | 审计导出与业务导出响应头一致；一次操作只产生一条审计记录 |

## 4. 目标重构架构

### 4.1 目标原则

1. **保留单体，不拆微服务**：当前规模下，模块化单体的运维成本和交付速度优于微服务。
2. **保留零构建前端**：继续 Jinja2 SSR + 原生 ES Module；只做模块化拆分，不引入 Node 构建链。
3. **契约先行**：OpenAPI、权限码、页面脚本、文档和测试必须由同一套校验驱动。
4. **数据范围全链路一致**：查询、导出、审计、下载、通知、任务日志使用同一套授权语义。
5. **事务边界显式化**：业务事务、审计事务、任务执行事务分别定义，禁止隐式 commit。
6. **失败可见、可定位、可恢复**：配置错误、迁移失败、缓存降级、任务中断必须有日志和操作路径。
7. **迁移可回滚、发布可验证**：升级前备份、迁移 up/down 演练、发布包校验必须自动化。

### 4.2 目标模块边界

```text
app/
  core/         配置、鉴权、数据范围、错误码、缓存、日志、导出、分页
  db/           engine、session、migrate、方言适配
  modules/
    auth/       登录、会话、改密、头像
    system/     用户、角色、菜单、部门、权限、导入
    content/    公告、文件
    audit/      登录/操作日志、导出审计
    schedule/   任务、模板、日志、调度
    notify/     渠道、记录、重试
    security/   IP 规则、封禁、API Key
    theme/      主题配置
    codegen/    代码生成
    ...
  jobs/         registry、runner、python_runner、builtin
  bootstrap/    permissions、menus、seed
  web/          templates、static、页面路由
```

模块间规则：

- `modules/*` 不直接处理数据库方言；
- `core/authz.py` 是数据范围裁剪唯一入口；
- `core/export.py` 是 CSV/下载/截断语义唯一入口；
- `db/migrate.py` 是 schema 演进唯一入口；
- `jobs/runner.py` 是任务执行、租约和生命周期唯一入口。

## 5. 分阶段施工方案

### 阶段 P0：安全、契约与事务止血

**范围**：CSRF/CORS、密钥加密、导出上限与数据范围、审计事务、登录失败计数、测试隔离、文档术语清理。

**施工顺序**：

1. 统一安全策略：明确 Cookie、Origin、CORS、CSRF Token 的组合方式；补齐 refresh/logout 防护和测试。
2. 统一 `MAX_EXPORT_ROWS`，让路由参数、服务常量、响应头和文档引用同一来源。
3. 将所有导出语句接入数据范围；为确实全局可见的资源建立显式白名单和权限码。
4. 统一 CSV 响应组件，删除 audit 重复实现；修正审计连续 commit 和隐式事务。
5. 修正登录失败计数、成功清理、IP 封禁异常日志。
6. 通知 secret 加密存储，补充迁移和回滚路径。
7. 每个测试使用独立数据库，禁止共享测试库污染。
8. 清理 React/ProTable/ProLayout/antd token 等历史文档术语。

**DoD**：

- 跨源 refresh/logout 被拒绝；
- 导出上限只有一处定义；
- 受限用户导出无越权数据；
- 审计一次操作一条记录，审计写入不影响业务回滚；
- 登录封禁、计数清零、失败日志可测试；
- secret 不以明文出现在数据库导出中；
- `make check`、文档校验和关键集成测试全绿。

**回滚**：安全配置与导出行为先用特性开关；secret 迁移保留旧密钥解密窗口；测试改造不改运行时。

### 阶段 P1：数据、调度、部署与门禁加固

**范围**：任务 code 语义、迁移治理、MySQL CI、迁移并发锁、调度租约、缓存一致性、分页/搜索性能、发布门禁。

**施工顺序**：

1. 选定并统一 `sys_job.code` 唯一性语义。
2. 修正迁移 docstring，补 up/down/up 演练和 `server_default` 清理。
3. entrypoint 加迁移协调锁，compose 补健康依赖。
4. CI 增加 MySQL 8 矩阵，覆盖建库、迁移、种子、核心集成、回滚。
5. `acquire_locks` 改单事务原子申请；多实例任务恢复增加可观测日志。
6. 多 worker 场景强制 Redis 或明确缓存降级边界。
7. 列表增加 `total=false`/keyset 分页；搜索统一入口并治理前置通配 LIKE。
8. 统一 make/CI/release 门禁清单，发布包增加 verify 命令。

**DoD**：

- 多副本启动只执行一次迁移；
- SQLite/MySQL 迁移与核心 API 双矩阵通过；
- 任务租约并发、崩溃恢复、跳过日志可验证；
- 配置/字典/限流在多 worker 下的行为符合文档；
- 发布、CI、本地 `make check` 执行同一套门禁。

**回滚**：迁移逐项可降级；keyset 分页用特性开关回退；Redis 强制策略可通过配置回到单机 MemoryCache。

### 阶段 P2：模块化、性能与可观测性演进

**范围**：拆分大 service/大 JS、错误码治理、前端权限下发、覆盖率和 E2E、文件引用完整性、API 演进策略。

**施工顺序**：

1. 拆 `system/service.py`，把校验、查询、写入、导入分开。
2. 拆 `core.js`，页面脚本按需加载。
3. 错误码到 HTTP 状态建立唯一映射并纳入契约检查。
4. 前端权限由服务端下发，移除静态 `ROUTE_PERMISSIONS` 双份维护。
5. 补覆盖率门禁和少量浏览器 E2E（登录、菜单、分页、弹窗、主题、上传、任务触发、登出）。
6. 补头像/文件 FK 或引用清理任务，增加归档/软删除策略。
7. 增加 API deprecated 标记、Sunset 头和弃用统计。

**DoD**：

- 大文件规模明显下降且测试全绿；
- 权限码变更不需要同步前端静态表；
- 覆盖率与 E2E 有稳定基线；
- 文件引用、审计留存、API 演进策略有文档和测试。

## 6. 运行验证与风险

本次审查基于当前工作树静态代码、迁移、脚本和文档。以下事项必须在具备执行环境的机器上验证，不能仅凭静态审查视为已完成：

1. `make lint`、`make test`、`make contract-check`、`make docs-check` 是否全绿。
2. `pytest` 在隔离测试库下是否存在顺序依赖。
3. `alembic upgrade head`、`alembic downgrade -1`、再次 `upgrade` 是否在 SQLite 与 MySQL 8 均可执行。
4. `scripts/mysql_smoke.py` 是否覆盖真实 MySQL 迁移、默认值、索引和锁行为。
5. `docker compose --profile mysql up` 的启动时序、healthcheck 与多副本迁移竞争是否复现。
6. Redis 多 worker 下配置、字典、限流、IP 封禁一致性。
7. CSRF、CORS、API Key、secret 加密、审计脱敏在真实请求链路中的完整行为。
8. 发布包 `release.py` 产物是否可通过独立校验命令验证 SHA256 与完整性。

主要风险：

- 密钥加密迁移若改变派生方案，会造成历史通知渠道无法解密；必须保留旧密钥解密回退窗口。
- 测试隔离改造可能暴露此前被共享测试库掩盖的顺序依赖，需要一轮全量回归。
- MySQL CI 首次接入可能暴露迁移兼容问题，应先在副本库演练。
- 性能治理不能通过删除审计字段或弱化数据权限换取速度。
- 不应把文档中“CI/E2E/覆盖率已具备”的表述继续当作现状；未自动化的能力要明确标注为计划项。

## 10. 模块分层与包结构改造（2026-10-28）

方案落地后追加的一轮结构治理，解决「包划分」与「新模块接入」两件事。详细规范见
`docs/模块与分层规范.md`。

**问题**：`system` 被 8 个模块依赖、59 处导入，其中 37 处（63%）是 `User`/`UserSession`
模型、`user_out` 序列化、`_commit`/`_user_scope` 这类平台级能力。结果 `app/core`
（authz / ipguard / middleware / upload）反向依赖业务模块，底座依赖上层。

**做了什么**：

1. **内核下沉**：新增 `app/kernel/`（`models` / `serializers` / `db` / `scope` / `api_key`），
   承载身份模型、访问凭证、审计记录与通用事务/数据范围工具。`core` 与 `kernel` 对
   `app.modules` 的依赖降为 **0**。
2. **模块清单**：新增 `app/core/module.py` 的 `ModuleSpec` 与 `discover_modules()`，
   每个模块在自己的 `module.py` 声明 `routers` / 增量 `permissions` / 可选 `menus`、`pages`；
   `main.py` 改为遍历注册，不再逐个 import 16 个路由。
3. **域分组**：`modules/sys/{system,auth,security,config}`、
   `modules/ops/{audit,monitor,schedule,notify,export,dashboard}`，`content` / `theme`
   保持顶层叶子。域分组只允许一层。
4. **分层门禁**：`scripts/check_modules.py` 并入 `contract` 组，用 AST 校验
   底座不依赖模块、模块间依赖必须登记在 `ALLOWED_MODULE_EDGES` 且带理由。

**结果**：模块间依赖 24 条（未登记）→ 16 条（全部登记并带理由）；新增模块需改的中央
文件从 4 个降到 1~2 个；`pytest` 364 → **370 passed**；OpenAPI 仍是 152 操作 / 97 权限码 /
30 页面，对外契约零变化。

**刻意没做**：

- 存量 97 条权限码没有逐条搬进各模块（`module` 字段与 Python 模块并非一一对应，
  搬迁只产生 review 噪音），清单的 `permissions` 是增量通道。
- 菜单树与页面注册仍集中：菜单是信息架构，「系统管理」一个目录横跨三个模块，
  按模块硬拆会让菜单碎片化。
- MCP 接口本轮不做，设计方向见 `docs/模块与分层规范.md` §7。
