# 模块与分层规范

本文描述 Fast CMS 后端的分层、包结构与模块扩展方式。新增模块、调整目录、评审
依赖方向时以本文为准；与代码不一致时以 `scripts/check_modules.py` 的输出为准。

## 1. 分层

```text
app/core       无状态地基：配置、错误码与消息表、响应信封、分页、搜索、缓存、
               上传安全、时区、客户端地址解析（net.py）
app/kernel     有状态底座：身份模型、访问凭证、鉴权上下文、数据范围、事务、
               审计记录、文件存储、请求上下文与操作日志中间件、IP 守卫、事件总线
app/modules    业务模块：按域分组，模块之间不直接依赖
app/web        HTML 外壳：Jinja2 模板、静态资源、页面路由
app/db         SQLAlchemy Base / 会话 / 迁移
app/bootstrap  种子数据：权限码基线、菜单树、初始账号
```

依赖方向是**单向**的：

```text
web → modules → kernel → core
```

`core` 与 `kernel` **不得** import `app.modules.*`。这条由门禁强制
（`scripts/check_modules.py` 的 `check_layering`，AST 解析，不会被注释或 docstring 误伤）。

### 底座内部的方向：`kernel → core` 单向

`core` 与 `kernel` 都是「底座」，但它们不是一个平面：

| | `app/core` | `app/kernel` |
|---|---|---|
| 状态 | 无状态（纯函数、配置、常量表） | 有状态（持有 ORM 模型与连接） |
| 依赖 | 只用标准库 + Pydantic / FastAPI | `app.core` + `app.kernel.models` |
| 能否被模块层绕过 | 可以，模块可直接用 | 可以，模块可直接用 |
| 新增代码的判据 | **不碰数据库**就放这里 | **要读写表**就放这里 |

因此方向只能是 `kernel → core`：`core` 一旦反向 import `app.kernel`，两者就退化成
「都是底座」的一团，方向无从校验。这条现在是**门禁规则**（`check_core_direction`），
不是文档约定：

```text
$ grep -rn "from app.kernel" backend/app/core/
backend/app/core/authz.py:16:from app.kernel.authz import (        # 兼容 shim
backend/app/core/events.py:14:from app.kernel.events import (      # 兼容 shim
backend/app/core/ipguard.py:12:from app.kernel.ipguard import (    # 兼容 shim
backend/app/core/middleware.py:12:from app.kernel.middleware import (  # 兼容 shim
```

这四个是第五轮重构（Phase 8）搬家时留下的**过渡 shim**，精确登记在
`check_modules.py::CORE_KERNEL_SHIMS`，每条都写明理由。下一轮把调用点改成
`app.kernel.*` 后应清空该清单并删除这四个文件；清单与实际不符（登记了但已不再
import、或文件已删除）同样会让门禁失败，防止白名单变成豁免垃圾场。

> **搬家清单**：`core/authz.py`、`core/events.py`、`core/ipguard.py`、`core/middleware.py`
> 四个模块都要读表，已上移到 `app/kernel/`。其中 `client_ip` / `client_ip_from_scope`
> 是纯函数，单独下沉到新增的 `core/net.py`——否则 `core/request_context.py` 为了拿
> 一个纯函数就得反向 import `app.kernel`，刚建立的单向又破掉了。

### 两个 `serializers` 的分工

`app/core/serializers.py` 与 `app/kernel/serializers.py` 同名不同职责，曾被反复搞混：

| | `app/core/serializers.py` | `app/kernel/serializers.py` |
|---|---|---|
| 输入 | 标量（`datetime` 等） | ORM 实体（`User` / `Role` / `UserSession`） |
| 输出 | 标量（ISO 字符串） | 可直接进响应模型的 dict |
| 职责 | **纯格式化**：时区归一、精度截断 | **实体投影**：挑字段、拼关联、按权限置空 |
| 依赖 | 无（只用标准库） | `app.kernel.models` + `core.serializers` |
| 典型调用 | `iso(row.created_at)` | `user_out(user, include_roles=False)` |

判据：**需要拿到整行实体才能决定输出什么 → kernel；只处理手上这一个值 → core**。
放在 core 的好处是模块层可以放心 import 而不引入 ORM 依赖。

### 为什么要有 kernel

改造前，`User` / `UserSession` / `Dept` / `Role` 住在 `app/modules/system`，
结果 `app/core/authz.py`、`app/core/ipguard.py`、`app/core/middleware.py` 全部
反向依赖业务模块——底座依赖了上层，任何模块调整都可能把鉴权打挂。

统计上：`system` 被 8 个模块依赖、59 处导入，其中 37 处（63%）是
`User`/`UserSession` 模型、`user_out`/`session_out` 序列化、`_commit`/`_user_scope`
这类**平台级能力**，而不是「系统管理业务」。把它们下沉到 `app/kernel` 后，
`core` 与 `kernel` 对业务模块的依赖降为 **0**。

但 `core` 与 `kernel` **之间**当时仍有双向依赖，四个文件各欠一笔：

| 文件 | 反向依赖 | 为什么当时留在 core |
|---|---|---|
| `core/authz.py` | `app.kernel.models`（User/Role/Permission/UserSession）、`kernel.api_key` | 「鉴权是基础设施」的直觉 |
| `core/events.py` | `app.kernel.models`（EventLog/EventOutbox） | 「事件总线是基础设施」的直觉 |
| `core/ipguard.py` | `app.kernel.models`（IpRule） | 同上 |
| `core/middleware.py` | `app.kernel.models`（OperationLog） | 同上 |

判据不是「听起来像不像基础设施」，而是**要不要读写表**：四个文件全都要，所以全是
kernel。第五轮把这四个搬到 `app/kernel/`，`core` 只留 re-export shim，方向从此单向。

## 2. 目录结构

```text
app/
  core/                     # 无状态地基（不碰数据库）
    module.py               # ModuleSpec 与自动发现
    errors.py / messages.py # AppError + 151 条错误码文案表
    envelope.py             # Envelope / Page / KeysetPage / StrictModel
    pagination.py           # PageParams / count_rows
    net.py                  # client_ip / client_ip_from_scope（纯函数）
    serializers.py          # iso()：值 -> 值
    authz.py                # 兼容 shim -> kernel.authz（下一轮删除）
    events.py               # 兼容 shim -> kernel.events（下一轮删除）
    ipguard.py              # 兼容 shim -> kernel.ipguard（下一轮删除）
    middleware.py           # 兼容 shim -> kernel.middleware（下一轮删除）
  kernel/                   # 有状态底座（core + ORM）
    models/                 # identity / credential / audit / events / storage
                            # User/UserSession/Dept/Role/Permission/Menu
                            # ApiKey/IpRule/LoginLog/OperationLog/FileObject
    authz.py                # AuthContext / require_permission / DataScope
    events.py               # 进程内事件总线 + 事务性发件箱
    ipguard.py              # IP / CIDR 访问控制守卫
    middleware.py           # RequestContext + OperationLog 中间件
    serializers.py          # user_out / user_brief / role_brief / session_out
    db.py                   # commit / log_operation
    scope.py                # user_scope / ensure_user_access / revoke_user_sessions
    api_key.py              # hash_api_key / resolve_api_key
    files.py                # 文件上传/下载/删除/孤儿清理（平台能力）
  modules/
    sys/                    # 系统域
      system/               # 用户、角色、部门、菜单、权限、字典、系统参数
      auth/                 # 登录、刷新、登出、自助改密
      security/             # IP 访问控制、用户封禁、API Key
      config/               # 运行期配置
    ops/                    # 运维域
      audit/ monitor/ schedule/ notify/ export/ dashboard/
    content/                # 内容域：公告（顶层叶子）
    theme/                  # 主题模板（顶层叶子）
```

**域分组只允许一层**：`modules/<域>/<模块>/`。再深一层会让导入路径变成
`app.modules.a.b.c.services.x`，收益递减而可读性下降。

## 3. 模块清单

每个模块在自己的 `module.py` 里声明能力：

```python
from app.core.module import ModuleSpec
from app.modules.content.router import admin_router, router

MODULE = ModuleSpec(
    name="content",
    order=110,
    description="公告与文件管理",
    routers=(router, admin_router),
)
```

字段：

| 字段 | 作用 | 是否必需 |
|---|---|---|
| `name` | 模块名，必须与目录名一致 | 是 |
| `order` | 注册顺序（升序），沿用改造前的显式顺序 | 否（默认 100） |
| `description` | 一句话说明，清单要能自解释 | 建议 |
| `routers` | API 路由，按声明顺序 include | 是 |
| `permissions` | **增量**权限码，格式 `<域>:<资源>:<动作>` | 否 |
| `menus` / `pages` | 增量菜单/页面声明，由 `all_menu_tree()` / `all_pages()` 合并 | 否 |

`main.py` 不再逐个 import 路由，而是：

```python
for router in module_routers():        # app/core/module.py
    app.include_router(router, prefix=api_prefix)
```

发现逻辑用 `Path.rglob("module.py")`，天然支持域分组；结果按 `(order, name)` 排序，
保证注册顺序确定。

### 权限码为什么没有全部搬进模块

存量的 98 条权限码留在 `app/bootstrap/permissions.py` 基线表。它们是既有对外契约，
且 `module` 字段与 Python 模块并非一一对应（例如 `tool` 不是模块），逐条搬迁只会
制造 review 噪音。清单里的 `permissions` 是**增量**通道：新模块在自己的 `module.py`
声明即可，种子通过 `all_permissions()` 合并基线与增量。

### 菜单与页面：存量集中、增量走清单

菜单树是**信息架构**，不是代码归属：「系统管理」一个目录就横跨 `system`、`config`、
`theme` 三个模块，按模块硬拆会让菜单碎片化。因此存量 31 页与菜单树留在
`web/router.py` 的 `PAGES` 与 `bootstrap/menus.py` 的 `MENU_TREE`，与权限码 98 条基线
同样的取舍。

但清单字段**必须真的生效**：`all_pages()` 合并 `PAGES + module_pages()`，
`all_menu_tree()` 合并 `MENU_TREE + module_menus()`，同路径以存量优先。
`check_modules.py` 会校验「清单里声明的页面/菜单确实出现在合并结果里」，
杜绝「声明了但没人读」的死字段。

### 事件总线：事后通知不要写成调用

有三处依赖本质是单向广播，早期写成函数体内 import（延迟导入），实际遮蔽的是循环
依赖，要等运行到那一行才炸：

| 原写法 | 现在 |
|---|---|
| `content` 直接调 `notify.hooks.notice_published` | `content` 发 `notice.published`，`notify` 订阅 |
| `config` 直接调 `scheduler_service.resync_timezone` | `config` 发 `config.timezone_changed`，`schedule` 订阅 |
| `jobs.runner` 直接调 `notify.hooks.job_finished` | `jobs.runner` 发 `job.finished`，`notify` 订阅 |

订阅在各模块的 `module.py` 里注册（`discover_modules()` 是启动必经之路，保证订阅
先于任何请求就位）。`kernel/events.py` 的 `KNOWN_EVENTS` 列出全部事件，
`check_modules.py` 校验每个事件都有订阅方。调用方仍写 `from app.core import events`
（走 `core/events.py` 的兼容 shim，下一轮改直连 `app.kernel.events`）。

## 4. 新增一个模块

```text
app/modules/<域>/<name>/
  __init__.py
  module.py      # 必需：ModuleSpec
  models.py      # 数据模型（记得在 app/db/models.py 里 re-export 给 Alembic）
  schemas.py
  service.py
  router.py
```

1. 建目录与 `module.py`，声明 `routers`（和可选 `permissions` / `menus` / `pages`）；
2. 模型在 `app/db/models.py` 补一行 re-export，否则 `alembic revision --autogenerate` 看不到；
3. 需要页面时，在 `module.py` 里声明 `pages`，再补模板与页面 JS
   （路径 `pages/<module>/<resource>.html`、`pages/<module>/<resource>.js`）；
4. 跑 `python -m app.cli sync-rbac`（权限码与菜单入库）、`python scripts/check_modules.py`、`make test`。

**不需要改** `app/main.py`、`bootstrap/permissions.py`、`bootstrap/menus.py`、`web/router.py`。
代码生成器产出的 `module.py` 就是按这个模板生成的。

## 5. 门禁

`scripts/check_modules.py`（已并入 `scripts/gate.py` 的 `contract` 组）：

1. 每个叶子包必须有 `module.py`，`MODULE` 必须是 `ModuleSpec`；
2. `name` 必须与目录名一致；
3. 清单声明的每个 router 必须出现在 OpenAPI 里（防止漏挂载）；
4. 增量权限码格式正确、不与基线重复；
5. `core`/`kernel` 不得依赖 `app.modules.*`；
6. **`core/` 不得 import `app.kernel`**（`check_core_direction`，白名单
   `CORE_KERNEL_SHIMS` 精确到 4 个 shim 文件，且带反向校验）；
7. 模块间依赖必须登记在 `ALLOWED_MODULE_EDGES`，且每条都带**理由**；
8. **函数体内不得 import 其它模块**（AST 级检查）：这是循环依赖的遮蔽手法；
9. 清单声明的 pages / menus 必须真的出现在合并后的注册表里；
10. `KNOWN_EVENTS` 里的每个事件都必须有订阅方；
11. **`app/modules` 下不得直接调用会话的 `commit()`**（`check_commit_boundary`，
    见 §7）。

另有三道非 Python 门禁并列在 `gate.py` 里：

- **`check_contract.py`**（contract 组）：前端 JS 里写的 DOM id / 权限码 / 错误码
  必须与后端模板、注册表对得上（`check_dom_ids` 现在同时扫描页面 JS 里的
  `form: { id / titleId / submitId / filters }` 配置）；
- **`node --test tests/frontend/*.test.mjs`**（test 组）：纯前端逻辑（分页窗口、
  消息文案注册表、表格多选、表单序列化等）65 个用例，零第三方依赖；
- **`tsc --noEmit -p tsconfig.json`**（lint 组，Phase 10-2）：`core/**`、`ui/**`、
  `ui.js` 开启 `// @ts-check` 后必须零类型错误。typescript 是纯开发期工具
  （`npm install --no-save typescript@5`，node_modules 已 gitignore）：
  本地未装时门禁**跳过并提示**，CI 的 lint job 会先安装再跑，始终硬校验。

第 7 条是有意为之：模块间依赖不追求「零」，但要求每一条都是显式决策。当前 12 条
全部是真实业务耦合（如 `export → content` 导出公告、`dashboard → schedule` 统计任务），
没有一条是「顺手 import」。

第 6 条与第 7 条都做了**反向校验**：登记了但实际已不存在的边 / 已不再 import kernel 的
shim 同样报错。单向校验只能发现「新增未登记」，发现不了「已消灭未同步」——架构漂移
就是这么积累起来的（事件总线重构后就留下过 2 条幽灵边）。

## 7. 事务边界与副作用时机

三件工具，各管一件事。写新代码时先判断自己属于哪一类，再挑工具。

### 7.1 `kernel.db.commit(db)` —— 默认选择

```python
from app.kernel.db import commit

await commit(db)                                   # 普通提交
await commit(db, conflict_code="THEME_CODE_EXISTS") # 唯一约束冲突有专属错误码
```

它只比裸提交多做一件事：把 `IntegrityError` 翻译成语义化的 `AppError`（默认
`DATA_CONFLICT`，409）。**裸提交的代价**是唯一约束冲突会以原始异常冒到全局处理器，
变成一个没有上下文的 500；而 `commit()` 至少能告诉前端「这个编码已被占用」。

`conflict_code` 由调用方给：唯一约束冲突的真实原因只有调用方知道（主题编码重复、
用户名重复、角色编码重复），让它留在 kernel 里猜只能得到含糊的「数据冲突」。

门禁：`app/modules` 下出现 `db.commit()` / `session.commit()` 直接失败
（`check_modules.py::check_commit_boundary`）。

### 7.2 `@transactional` —— 「全成功或全失败」

```python
from app.kernel.db import transactional

@transactional
async def assign_user_roles(db: AsyncSession, ctx: AuthContext, ...) -> dict:
    ...
```

正常返回提交，抛异常整事务回滚。当前用在 3 个单次多写动作上：

| 场景 | 为什么必须原子 |
|---|---|
| `assign_user_roles` | 角色集合是覆盖写，半套角色 = 没人设计过的权限边界 |
| `assign_role_permissions` | 同上，越权的温床 |
| `reset_user_password` | 改 hash + 清锁定 + 提 `token_version` + 吊销会话 + 写审计，缺一步就留下后门 |

**两条使用边界**（都踩过）：

1. **不要用在批量循环里**。批量语义是「逐条提交 + 返回失败明细」，原子事务会让
   第 37 条失败把前 36 条一起回滚。
2. **不要在「调用方 catch 后继续用同一 session」的地方用**。整事务 `rollback()`
   会让 session 里**所有**对象过期，调用方再读 `ctx.user.id` 就触发同步刷新，
   在 async 环境里直接 `MissingGreenlet`。`batch_users` 逐条调用 `delete_user`，
   正是这种形态，所以 `delete_user` 用显式 `commit(db)`。

### 7.3 `after_commit()` —— 副作用必须晚于提交

```python
from app.kernel.db import after_commit, commit

after_commit(lambda: _emit_published(item, ctx.user.username))
await commit(db)
```

「发事件 / 推送通知」这类副作用必须在事务提交之后发生，否则会出现
「收到通知但点进去 404」——排查成本最高的一类不一致。以前靠注释提醒顺序，
现在是机制：回调登记在 `ContextVar` 里，`commit()` 成功后才按登记顺序执行；
事务失败或回滚时直接丢弃，一个都不会发。

单个回调抛异常只记日志，不影响已提交的业务结果，也不影响后续回调。

> **注意**：`config/service.py::apply_timezone` 没有走 `after_commit`，因为它还要求
> 「在 `_invalidate_config_cache()` 之后」——`schedule` 的订阅方重排任务时会重新读
> 配置，缓存没失效就会按旧时区排任务。这类有额外顺序要求的场景，显式写调用顺序
> 比塞进钩子更清楚。

### 7.4 批量 vs 原子：怎么选

| | 批量（`batch_users` / `import_users`） | 原子（`@transactional`） |
|---|---|---|
| 语义 | 部分成功 | 全成功或全失败 |
| 提交 | 每一条独立提交 | 末尾一次 |
| 失败 | 收集失败明细返回，继续下一条 | 回滚，抛给调用方 |
| 用户预期 | 「能导的都导进去了，这几行有问题」 | 「要么都改了，要么都没改」 |

判断标准只有一句：**用户能不能接受「一半生效」**。能接受就是批量，不能就是原子。

### 7.5 环境陷阱：pysqlite 的 SAVEPOINT 不可靠

Phase 9 一度用 `begin_nested()` 给导入的每一行套 SAVEPOINT，实现「行级原子 +
整批不原子」。在 SQLite 上测试直接失败：**当 SAVEPOINT 是事务里的第一条语句时，
`RELEASE SAVEPOINT` 会被 pysqlite 退化成提交**，后续 `rollback()` 不再生效。

```python
# 复现（prior_dml=False 时 'x' 会留下来）
sp = await session.begin_nested()
await session.execute(text("INSERT INTO t VALUES ('x')"))
await sp.commit()
await session.rollback()     # 期望丢弃，实际没丢
```

结论：**不要在这个栈上用 SAVEPOINT 表达「局部回滚」**。需要行级隔离就老老实实
「每行一次 commit + 失败行 rollback」，语义一样，且在所有方言上都成立。

## 8. 响应契约：一套信封走天下

第三条规则（Phase 12-4 收口）：**HTTP 层的形状只有一个，错误码只有一个出处。**

1. **成功与失败共用 `Envelope[T]`**（`core/envelope.py`）：`{code, message, data}`。
   成功走 `core/errors.success()`（code 固定 `"OK"`），失败走 `AppError` → 全局异常
   处理器 → `error_payload()`。路由函数里**不允许**手拼 `{"code": ..., "data": ...}`
   字典，也不允许直接 return ORM 对象——响应模型一律 `Envelope[XXXOut]`，
   `XXXOut` 是 `StrictModel`（extra="forbid"，字段漂移在测试期就红）。
2. **错误码单一事实源 `ERROR_CODE_STATUS`**（`core/errors.py`）：码 → HTTP 状态码
   的映射只登记在这一处。`AppError("XXX")` 的码必须是常量字面量（`check_contract`
   AST 校验；`kernel/db.py::commit` 这类「码作参数」的调用点登记在
   `DYNAMIC_ERROR_CODE_CALLERS` 白名单，并要求运行时自查 `ERROR_CODE_STATUS`）。
   前端拿码做文案路由（`core/messages.js`），拿状态码兜底——码拼错等于文案丢失。
3. **前端只认信封**（`core/request.js`）：`request()` 解析信封取 `data`，
   非 2xx / `code != "OK"` 抛 `ApiError`（含码与文案）；二进制响应（导出下载）
   出错时同样解析信封抛错。任何页面不允许自己 `fetch()` 后手写 JSON 解析——
   绕过这一层就绕过了鉴权失效跳转、错误 toast、信封容错三件事。

门禁配套：`check_contract.py` 校验错误码登记与 DOM id；`check_api_coverage.py`
校验「每个端点都有前端调用点」；`tsc --noEmit`（lint 组）锁前端类型。三层合起来
保证「后端改了形状/码，前端没跟上」在 CI 就失败，而不是等用户点出空白页面。
