> 范围：`backend/app` 全量（153 个 Python 文件 / 20,194 行）、前端 49 个 ES Module（8,255 行）、

> 所有结论都带证据位置；「实测」标记的结论可用附录 B 的命令复现。

### 0.3 总体判断

架构主体是健康的：模块边界清晰、门禁密度高于同规模项目、没有框架魔法。剩下的问题集中在
**四条「只做了一半」的接缝**上：

1. **层次没有方向**：`core` 与 `kernel` 互相依赖，底座内部无法再分层；
2. **契约只有一个方向**：响应模型挡住「出站形状」，但服务层产出的字段多了会被**静默丢弃**；
3. **事务没有边界**：提交点散落在 69 处 service 内部，跨步骤业务无法原子，封装有三套；
4. **成功路径没有契约**：错误文案已收敛到 `MESSAGES`，成功文案仍是 68 处硬编码且前端基本不消费。

此外前端 8,255 行 JS 没有类型与边界约束、14 个实现细节存在可复现缺陷或口径不一致。
本轮给出 6 项 A 类（架构）+ 14 项 B 类（细节）+ 6 个施工阶段（Phase 7–12）。

## 1. 现状架构梳理

### 1.1 定位与不可破坏的约束

Fast CMS 是「可直接启动的后台管理基座」，四条硬约束决定了所有方案的上限：

1. **零前端工具链**：没有 Node 构建、没有包管理器、没有 dist 产物；
2. **零外部依赖可跑**：默认只依赖 Python 与 SQLite，MySQL/Redis 是显式可选；
3. **数据与代码分离**：`DATA_DIR` 一处搬迁即整体迁移；
4. **单进程可跑**：`uvicorn` 起一个进程就是完整系统（调度器 embedded）。

> 本方案所有建议都不触碰这四条。凡是需要「引入构建」「强制 Redis」「拆分前端服务」的方案，
> 一律否决，即使它能解决某个具体问题。

### 1.2 包结构与依赖

```text
backend/app/
├── core/        跨领域基础设施：config / errors / messages / cache / crypto / csrf /
│                tz / search / export / pagination / envelope / routing / authz /
│                ipgeo / ipguard / events / middleware / metrics / logging
├── kernel/      平台能力：ORM 模型（identity/credential/audit/storage）、files、
│                api_key、scope、serializers、schemas、db（commit/log_operation）
├── db/          Base / 会话 / 迁移 / 模型收集面
├── modules/     12 个业务模块（sys/{auth,config,security,system}、ops/{audit,dashboard,
│                export,monitor,notify,schedule}、content、theme），每个含
│                module.py + router.py + service.py + schemas.py(+models.py)
├── web/         页面路由 + 模板 + 静态资源（Jinja2 + 原生 ES Module）
├── codegen/     代码生成器（已收编进模块清单）
├── bootstrap/   权限表、菜单树、种子
└── jobs/        任务注册表与执行器
```

**依赖方向（实测）**：

| 方向 | 模块数 | 说明 |
|---|---|---|
| `modules → core/kernel` | 全部 | 业务模块只依赖底座，符合预期 |
| `kernel → core` | 4（`db`/`files`/`scope`/`serializers`） | 使用 `core.authz`、`core.errors`、`core.pagination` 等 |
| `core → kernel` | 4（`authz`/`events`/`ipguard`/`middleware`） | 使用 `kernel.models` 的 ORM 实体 |
| `core/kernel → modules` | 0 | 门禁 `check_layering` 守护，无违规 |

`modules` 之间的依赖有 12 条白名单边（`check_modules.py::ALLOWED_MODULE_EDGES`），
带双向校验：新增未登记边报错，登记了但已消失的「幽灵边」也报错。

### 1.3 一次请求的完整链路

```text
uvicorn
  └─ RequestContextMiddleware    request_id、安全响应头、指标、慢请求、请求上下文
      └─ IpGuardMiddleware       封禁/放行规则匹配（内存快照）
          └─ RateLimitMiddleware 登录/敏感接口限流
              └─ OperationLogMiddleware  非 GET 请求体捕获 + 响应后写审计
                  └─ CORSMiddleware
                      └─ Router → 权限依赖 → 处理器 → Service → DB
```

> **实测**：`add_middleware` 是「后注册者在外层」，实际栈序为
> `RequestContext → IpGuard → RateLimit → OperationLog → CORS → app`。
> 这与 `assembly.py` 注释「IP 守卫必须最外层」相反（见 B-3）。

鉴权有两条身份路径，最终都收敛到 `AuthContext`：

- **浏览器会话**：`Authorization: Bearer <JWT>` → 校验 `sid` 会话、`ver` 令牌版本、封禁、强制改密；
- **API Key**：`fck_` 前缀 → 哈希查表 → 派生服务账号 → `scopes` 即权限集（`*` 表示全部）。

### 1.4 模块与三张注册表

| 注册表 | 存量位置 | 增量通道 | 门禁 |
|---|---|---|---|
| 路由 | 各模块 `module.py` 的 `routers` | 同左（已统一） | `check_modules` |
| 权限码 | `bootstrap/permissions.py`（98 条） | `ModuleSpec.permissions`（当前 0 条） | `check_contract` + `check-permissions` |
| 菜单树 | `bootstrap/menus.py` | `ModuleSpec.menus` | `check_contract` 路径可达性 |
| 页面 | `web/router.py::PAGES`（31 条） | `ModuleSpec.pages`（当前 0 条） | `check_contract` 三向配对 |

路由已完全收敛；权限、菜单、页面仍是「集中表 + 模块声明」双轨（上一轮 A-1 的遗留，见 A-5）。

### 1.5 数据、事务与事件

- **数据**：SQLAlchemy 2 async；SQLite 开 WAL + `foreign_keys=ON` + `busy_timeout=5000`；
  MySQL 用连接池；`db/models.py` 自动收集所有模块 `models.py`，漏收集即门禁失败。
- **事务**：`get_db()` 每请求一个会话，`close()` 隐式回滚；提交点分布在 service 内部
  （69 处裸 `await db.commit()`、23 处 `_commit()`、`theme/service.py` 还有一份本地 `_commit`）。
- **事件**：`publish()` 同步派发（订阅方异常隔离）+ `enqueue_event()` 事务性 outbox，
  outbox 由 `jobs/runner` 轮询派发；投递结果落 `core_event_log` 可查。
- **审计**：默认由中间件兜底写；声明 `audit="service"` 的模块由 service 在同事务内写。

### 1.6 前端三层

```text
Jinja2 模板（HTML 骨架 + <thead> + 筛选表单 + 弹窗结构）
  └─ app.js（按 body[data-page] 动态 import 外壳与页面脚本）
      ├─ shell/{admin,auth,portal}.js   登录守卫 / 导航 / 顶栏 / 心跳
      └─ pages/<page>.js                页面控制器（28 个，平均 196 行）
          └─ ui.js（DataTable / 分页 / 树 / 批量条）+ core/*（请求、表单、弹窗、主题、i18n）
```

设计取舍：**表格结构与筛选表单留在 HTML，JS 只负责取数与填 `<tbody>`**。好处是模板可读、
无虚拟 DOM 开销；代价是「列定义在 JS、表头在 HTML」两处必须对齐（由 `check_contract`
的 `data-*` 与 `#id` 校验部分兜底）。

### 1.7 质量门禁现状

| 组 | 检查项 | 拦住的问题类型 |
|---|---|---|
| lint | ruff、mypy（`core`+`kernel` 全量注解） | 风格、未用导入、类型漂移 |
| test | pytest、`node --test` | 行为回归 |
| contract | openapi 导出、权限校验、契约 diff、接口覆盖、前端导入、转义哨兵、分层 | 前后端断链、破坏性变更、未转义插值 |
| docs | 文档中的命令必须真实存在 | 文档漂移 |

**覆盖盲区**：契约检查只看「路由/权限/schema 是否存在」，不看「服务层实际吐出的字段是否与
模型一致」；测试没有覆盖率度量；前端只有 4 个纯逻辑模块有行为测试。

## 2. 架构层不合理之处（A 类）

### A-1【层次无向】`core` 与 `kernel` 双向依赖，底座内部没有方向 **[实测]**

**事实**：`core` 有 4 个模块 import `app.kernel`（`authz`/`events`/`ipguard`/`middleware`，
都在用 `kernel.models` 的 ORM 实体），`kernel` 有 4 个模块 import `app.core`
（`db`/`files`/`scope`/`serializers`，用 `core.errors`/`core.pagination`/`core.authz`）。

**为什么是问题**：

- 两个包互相依赖，意味着**谁都不是底座**：`core/authz.py` 需要 `User`/`Role`/`UserSession`
  这些业务实体，它其实是「认证领域服务」，不是「基础设施」；
- `check_modules.py` 只禁止 `core/kernel → modules`，**没有约束底座内部方向**，所以这条边
  会继续长：任何新代码都可以往任意一侧塞；
- 结果是「共享代码该放哪」没有答案。上一轮已经出现过这种情况：`serializers.py` 同时存在于
  `core/`（`iso`）和 `kernel/`（`user_out`），`db/session.py` 与 `kernel/db.py` 职责交叉。

**证据**：`core/authz.py:22`、`core/events.py:52`、`core/ipguard.py:35`、`core/middleware.py:22`；
`kernel/db.py:12-15`、`kernel/files.py:33-39`、`kernel/scope.py:12-13`、`kernel/serializers.py:12-13`。

**结论**：需要给底座定一条单向边（建议 `kernel → core`，因为 `kernel` 依赖 `core` 的模块更多、
且 `core` 的 `errors`/`config`/`pagination` 本来就是更底层的原语），然后把 4 个「需要 ORM」的
`core` 模块上移到 `kernel`。

### A-2【契约单向】响应模型只挡出站，服务层产出多了会被**静默丢弃** **[实测]**

**事实**：153 个操作已全部声明 `response_model=Envelope[...]`。但服务层返回的是**普通 dict**
（24 个 `*_out()` 函数手工拼字段），Pydantic 默认 `extra="ignore"`。

实测：服务层返回 `{"id": 1, "new_field": "..."}`，模型只有 `id` 时，响应体是 `{"id": 1}` ——
**新字段无声消失，HTTP 200，无日志、无告警**。

```python
# 实测（附录 B「A-2」段）
class Out(BaseModel):
    id: int
class Env(BaseModel):
    data: Out | None = None
# 返回 {"id":1,"new_field":"x"} → 实际响应 {"id":1}
```

**为什么是问题**：

- 上一轮补响应模型的**目的**是「防响应结构漂移」，但现在只防住了「类型不对」，
  防不住「字段被吞」——而后者才是更常见的漂移形态（服务层加字段、忘了改模型）；
- 一份字段清单存在两处（`notice_out()` 的 dict 字面量 + `NoticeOut` 的字段声明），
  没有门禁比对，靠人眼 review；
- 与 `exclude_unset=True` 叠加后更难察觉：模型有、dict 没有的字段会被省略（正常），
  dict 有、模型没有的字段会被丢弃（异常），两种「缺字段」在响应里长得一样。

**证据**：`core/envelope.py:1-17` 的设计说明、`modules/content/service.py:26-41` 与
`modules/content/schemas.py:21-34` 的双份字段清单、24 个 `*_out` 函数。

### A-3【事务无界】提交点散在 service 内部，三套封装并存，跨步骤业务无法原子 **[实测]**

**事实**：

| 提交方式 | 处数 | 位置 |
|---|---|---|
| `await db.commit()` | 69 | `config` 9、`auth` 7、`schedule` 7、`content` 7、`security` 6、`notify` 6、`audit` 4、`theme` 3、`files` 3、`seed` 3、`ipguard` 1、`api_key` 1、`cli` 1 … |
| `await _commit(db)`（`kernel.db.commit`） | 23 | `system/services/*` |
| 本地 `_commit()`（`theme/service.py:82`） | 1 | 自己实现了一遍 `IntegrityError → AppError` |

**为什么是问题**：

1. **业务组合无法原子**：`create_user` 有 `commit: bool = False` 这个参数，专为「导入时先校验
   再统一提交」而加——这是事务边界不在正确层级的直接症状。同类需求（批量操作、跨模块联动）
   每来一次就要加一个开关；
2. **语义分裂**：`kernel.db.commit` 把 `IntegrityError` 翻成 `DATA_CONFLICT`，裸 `commit()`
   依赖全局 handler 兜底，`theme` 又自己翻成 `THEME_CODE_EXISTS`。同一个「唯一键冲突」在三个
   地方给出三种错误码；
3. **提交时机与事件顺序耦合**：`create_notice` 先 commit 再 emit，靠人记住顺序；
   顺序写反就是「消息发出去了、数据没落库」或「数据落库了、消息没发」。

**证据**：`kernel/db.py:19-31`、`theme/service.py:82-86`、`users.py:158-176`（`commit=False`）。

### A-4【成功路径无契约】143 处 `success()`、68 处中文文案硬编码，前端基本不消费

**事实**：

- `return success(...)` 143 处，其中 68 处显式传中文文案（`success(data, "公告已创建")`）；
- 前端只有 2 处读 `message`：`ui.js:397`（批量结果）、`user.js:472`（导入失败行），
  其余 126 处 toast 调用用的是前端自己的字符串；
- 错误文案已收敛到 `MESSAGES`（151 条），并有 5 条门禁规则守着；成功文案没有任何约束。

**为什么是问题**：

- **同一个「提示文案」有两套治理**：错误走表、成功走调用点。改一次成功提示要全局搜索，
  多语言更无从下手（前端 `t()` 只用了 7 处，其中 5 处是真调用）；
- **68 处文案是「写了但没人看」的负载**：前端不读，等于给 API 增加了一个不受约束的自由字段；
- 契约层面 `Envelope.message` 默认 `"success"`，与「业务成功提示」语义混在一起。

**证据**：`core/errors.py:235-241`、`ui.js:397`、`core/i18n.js`、`core/request.js:128-144`。

### A-5【注册表三轨】权限/菜单/页面仍是「集中表 + 模块声明」，收敛路径只有 dry-run

**事实**：路由已完全收敛到 `ModuleSpec`；但

- 权限码：98 条**全部**在 `bootstrap/permissions.py`，`ModuleSpec.permissions` 实际使用 0 条；
- 菜单树：全部在 `bootstrap/menus.py`（`all_menu_tree()`），`ModuleSpec.menus` 实际使用 0 条；
- 页面：31 条在 `web/router.py::PAGES`，`ModuleSpec.pages` 实际使用 0 条。

（实测：`len(module_permissions()) == 0`、`len(module_menus()) == 0`、`len(module_pages()) == 0`。）

上一轮补了 `ModuleSpec.pages` 的字段等价校验和 `migrate-registry` 干跑命令，但**没有真正迁移**。

**为什么是问题**：新增模块要改 4 个地方（`module.py` + 权限表 + 菜单树 + 页面表），
任何一处漏改都是静默故障（路由 404 / 菜单不出现 / 页面 403）。门禁只能事后发现，
不能事前阻止——而「新增模块」正是代码生成器的主要场景。

**证据**：`core/module.py:27-35` 的设计说明、`bootstrap/menus.py`、`web/router.py:30-256`。

### A-6【前端无类型边界】8,255 行 JS，28 个页面脚本靠约定

**事实**：

- 49 个 JS 文件、8,255 行，无类型、无接口定义；后端 153 个操作的响应形状只存在于 OpenAPI；
- 28 个页面脚本 5,500 行，其中 19 个用 `DataTable`、17 个重复同一套
  「筛选表单 submit → `table.search(serializeForm(...))`」、43 处 `openModal`、32 处 `serializeForm`；
- `node --test` 只覆盖 `format`/`form`/`ui`/`i18n`/`datatable`/`theme-boot` 6 个纯逻辑模块，
  页面控制器零测试；
- `app.js:64-69` 页面脚本加载失败只 `console.error`，用户看到空白页（见 B-14）。

**为什么是问题**：

- 后端契约做得越细，前端「靠约定」的落差越大：字段改名后端有契约 diff，前端只会静默变
  `undefined`；
- 28 个页面脚本的初始化流程高度同构，但没有抽象点，改一处交互要改 28 处；
- 没有类型不等于不能检查：`// @ts-check` + JSDoc 可以在**不引入构建**的前提下做类型校验
  （`tsc --noEmit` 只在 CI 跑，不进运行时、不进发布包）。

**证据**：`app/web/static/js/` 目录、`tests/frontend/` 6 个文件、`ui.js:23-219`。

## 3. 开发细节需改进（B 类）

### B-1【正确性】Update 模型允许把非空列显式置 `null`，落到 409「数据重复」 **[实测复现]**

16 个 `*Update` 模型、88 个 `X | None = None` 字段，服务层统一用
`model_dump(exclude_unset=True)` + `setattr` 落库。当客户端显式传 `null`（不是省略）时：

```http
PUT /api/v1/content/notices/1   {"title": null}
→ 409 {"code":"DATA_CONFLICT","message":"数据重复或违反约束，请检查后重试"}

PUT /api/v1/system/users/2      {"nickname": null}
→ 409 {"code":"DATA_CONFLICT","message":"数据重复或违反约束，请检查后重试"}
```

真实原因是 `NOT NULL` 约束被违反，语义应该是 **422「标题不能为空」**。用户看到「数据重复」
会去查重名，永远查不到。

**修法**：区分「未设置」与「显式 null」。`Update` 基类增加 `model_dump_for_update(nullable={...})`：
非空列显式 null → 抛 `AppError("VALIDATION_ERROR")`（422）；可空列保留 null 语义（用于清空备注等）。

---

### B-2【性能】`psutil` 与密码哈希在事件循环里同步执行 **[实测]**

- `modules/ops/monitor/service.py:113` `psutil.cpu_percent(interval=0.1)`：**实测阻塞 100.3ms**，
  每次打开「服务器监控」页面事件循环停 100ms，并发 10 个请求就是 1 秒全站卡顿；
- `hash_password`/`verify_password`（argon2）：**实测 17.7ms / 18.3ms**，登录、改密、建用户、
  重置密码路径都在 async 函数里直接调用。

对照：`ipgeo` 与 `kernel/files.py` 已经正确用了 `asyncio.to_thread`，说明团队知道这个模式，
只是这两处漏了。

**修法**：`psutil` 相关调用整体包 `asyncio.to_thread`（或改用 `interval=None` 读上次采样）；
哈希统一走 `run_in_threadpool`。两者都不改语义，只换执行线程。

---

### B-3【一致性】中间件顺序的注释与实现相反 **[实测]**

`assembly.py:76-96` 注释写「IP 守卫必须最外层」，但代码按
`OperationLog → RateLimit → IpGuard → RequestContext` 顺序 `add_middleware`，
而 Starlette 是「后注册者在外层」，实际栈序是 **RequestContext 最外、IpGuard 第二**。

行为上 RequestContext 在最外层是对的（被封禁的请求也要有 `request_id` 和安全响应头），
但注释会误导后来者：按注释「调整」顺序就会把安全头挪到内层，被封禁的响应就没有 CSP。

**修法**：把注释改成「RequestContext 最外层（保证拒绝响应也带 request_id/安全头），
IpGuard 紧随其后（被封禁请求不进限流与业务）」，并补一条断言中间件栈序的测试。

---

### B-4【一致性】三套提交封装（A-3 的具体表现）

`kernel.db.commit` / `theme` 的本地 `_commit` / 69 处裸 `commit()`。同一个唯一键冲突
分别产生 `DATA_CONFLICT`、`THEME_CODE_EXISTS`、以及依赖全局 handler 的 `DATA_CONFLICT`。

**修法**：先做机械统一（全部换成 `kernel.db.commit`），再加门禁「`app/modules` 下不得出现
`await db.commit()`」；`theme` 的特化错误码通过 `commit(db, conflict_code="THEME_CODE_EXISTS")`
参数表达，而不是重写一份。

---

### B-5【可维护】`*_out()` 与 `*Out` 是两份字段清单，没有门禁（A-2 的具体表现）

24 个 `*_out()` 函数拼 dict，对应 24 个 Pydantic 模型。两者只能靠人眼对齐。
`exclude_unset=True` 让「模型有、dict 没有」表现为字段缺失（正常），
「dict 有、模型没有」表现为字段被吞（异常），二者在响应里无法区分。

**修法**：Out 模型加 `model_config = ConfigDict(extra="forbid")`，让「多字段」变成
**显式校验失败**；配套把只读端点冒烟测试扩到全部 69 个 GET，让漂移在 CI 就红。

---

### B-6【口径】分页参数在个别端点被忽略

`content/service.py:174-179` 的 `list_published_notices` 无条件执行 `count(*)`，
忽略 `params.total=false`；而 `paginate()` 会跳过 count。同一个 `PageParams`，
两种行为，前端无法预判 `total` 是否存在。

**修法**：统一走 `paginate()` 或显式判断 `params.total`。

---

### B-7【性能】审计中间件为每个写请求额外开一个会话并提交

`middleware.py:237-255` 在响应后 `async with async_session_factory()` 新开会话写
`OperationLog` 并 `commit()`。对 SQLite 意味着每个写请求多一次连接获取 + WAL 提交；
高并发下与业务事务争锁。

**修法**：短中期改为「进程内队列 + 批量落库」（每 200ms 或 50 条批量提交），
长期与 `audit="service"` 的模块统一到同一写入通道。注意：审计**不允许丢失**，
队列必须有上限与降级直写。

---

### B-8【一致性】i18n 只留了缝，没有铺路

`core/i18n.js` 提供 `t(key, fallback)`，实际只有 5 处真调用（`dialog.js` 3 处、`request.js` 3 处，
含重复），前端仍有 89 处硬编码中文 toast、模板里大量中文标题。

**修法**：不追求全量翻译，但把「通用动词/状态/错误」抽成一份 `MESSAGES_ZH`（约 40 条），
页面脚本改用 `t()`；新增代码由 `check_frontend_imports` 拦「toast 里直接写中文」。

---

### B-9【测试】无覆盖率度量，前端页面控制器零测试

`pytest-cov` 不在依赖里，CI 不产出覆盖率；`node --test` 只测 6 个纯模块。
结果是「585 个测试」这个数字无法回答「哪块没测到」。

**修法**：加 `pytest-cov`（只统计不设阈值，先出报告），对 `core`/`kernel` 设 80% 门槛；
前端用 `jsdom` 之外的轻量 DOM 桩（已有 `tests/frontend/_dom.mjs`）覆盖 2–3 个代表性页面
控制器的初始化与错误分支。

---

### B-10【可维护】3 个 500+ 行 service 与 515 行 CLI

`schedule/service.py` 660 行 24 函数（任务 + 模板 + 日志三类聚合）、`security/service.py` 589 行
28 函数（IP 规则 + 封禁 + API Key）、`audit/service.py` 553 行 23 函数（三类日志 + 导出）。

对照：`sys/system` 已经拆成 `services/{users,roles,menus,depts,sessions}.py`，
说明拆分模式是成熟的，只是这三个模块没跟上。

**修法**：按现有 `services/` 目录模式拆包，纯移动 + 门面 re-export，零行为变更。

---

### B-11【可靠性】`SEED_VERSION` 靠人工递增

`bootstrap/seed.py:34` 的 `SEED_VERSION = "1.8.0"` 是「内置数据是否需要重新播种」的开关，
注释明确要求「改了菜单/权限必须递增」。这是一条**没有门禁守护的人工约定**：
忘记递增 → 新菜单永远不出现，且没有任何报错。

**修法**：对 `MENU_TREE`/`PERMISSIONS`/`DEFAULT_*` 的内容做稳定指纹（排序后哈希），
指纹变化即视为需要重新播种，`SEED_VERSION` 仅作为人工强制重播的覆盖开关。

---

### B-12【性能】dict → Pydantic 双重序列化

服务层产出 dict，`response_model` 再校验并序列化一次。对 100 条的分页列表，
等于两遍字段遍历 + 两遍类型校验。当前规模下不是瓶颈，但它是 B-5 的根因：
「两份字段清单」正是为了「服务层不必知道模型」而付出的代价。

**修法**：与 B-5 合并处理——让 `*_out()` 直接返回 Out 模型实例，服务层只依赖
`schemas.py`（同模块内，不产生跨层依赖），dict 路径保留给内部调用。

### B-13【文档】文档与代码存在可核对的漂移

- `assembly.py` 中间件顺序注释与实现相反（B-3）；
- `docs/README.md` 评审时仍把 `架构评审与重构方案-2026-10-29.md` 标为「第四轮（当前）」
  （本文档落地时已更新为第五轮）；
- `docs/开发计划.md` 1,427 行，与当前实现的对应关系没有标注。

**修法**：`check_docs.py` 增加一条「文档中引用的文件/类/函数存在性」校验（当前只校验命令），
并把本轮文档补进索引。

### B-14【可用性】页面脚本加载失败静默降级为空白页

`app.js:64-69`：

```js
try {
  const module = await import(`./pages/${pageKey}.js`);
  await module.init?.();
} catch (error) {
  console.error(`[fastcms] 页面 ${pageKey} 初始化失败`, error);
}
```

脚本语法错误、`init` 抛异常、模块 404，用户看到的都是「页面空白、控制台有日志」。
门禁能拦住「页面声明了但脚本不存在」，拦不住运行期异常。

**修法**：`catch` 里渲染统一的错误态（复用 `renderState(el, {state:'error'})`），
并把 `error.message` + `request_id` 显示出来，便于用户反馈。

## 4. 优化改进重构方案

### 4.1 目标与原则

**目标**：把四条「只做了一半」的接缝补成完整机制——**层次有方向、契约有双向、事务有边界、
成功路径有契约**；顺手清掉 14 个细节缺陷。

**四条原则**（延续上一轮，已被验证有效）：

1. **不破坏硬约束**：零前端工具链、零外部依赖可跑、数据代码分离、单进程可跑；
2. **门禁先行**：每修一项，先补一条会失败的断言，再改实现；
3. **机械变更与行为变更分开提交**：拆包、改名、换封装走一个 PR；语义调整走另一个；
4. **存量保留 re-export 面一个版本**：所有移动都留兼容导入，避免一次性断链。

### 4.2 Phase 7：契约双向（1–2 人天，最高性价比）

| 编号 | 内容 | 验收 |
|---|---|---|
| 7-1 | 24 个 `*Out` 模型加 `model_config = ConfigDict(extra="forbid")` | 服务层多出字段时，测试环境立刻失败而不是静默丢弃 |
| 7-2 | `test_read_endpoints_smoke.py` 增加断言：响应体键集合 ⊆ 模型字段集合；并把覆盖从 48 个无参 GET 扩到全部 69 个 GET（带参端点用夹具构造） | 新增/改名字段必须在模型里同步 |
| 7-3 | 补一条「模型字段全部出现过」的软检查（按端点采样，输出覆盖率报告，不设硬门槛） | 能看出「模型声明了但从来没赋值」的死字段 |
| 7-4 | `docs/API规范.md` §2.4 补「响应模型即契约，服务层不得返回模型外字段」 | 规范与门禁一致 |

> 风险：`extra="forbid"` 在**生产**环境会让漂移变成 500。缓解：先用 7-2 的测试把现有漂移
> 清干净（预计 0–3 处），再开 forbid；`Envelope` 保持 `ignore`，只对 `*Out` 生效。

### 4.3 Phase 8：层次定向（2–3 人天）

| 编号 | 内容 | 验收 |
|---|---|---|
| 8-1 | 定义底座方向：**`kernel → core` 单向**，写进 `docs/模块与分层规范.md` | 规范有明确方向，不再是「都是底座」 |
| 8-2 | 把 4 个依赖 ORM 的模块上移：`core/authz.py → kernel/authz.py`、`core/events.py → kernel/events.py`、`core/ipguard.py → kernel/ipguard.py`、`core/middleware.py → kernel/middleware.py`；`core/` 保留同名 shim 做 re-export | 全量测试绿；`grep "from app.kernel" app/core` 为空 |
| 8-3 | `check_modules.py` 增加规则：`core/` 不得 import `app.kernel`（shim 除外，用白名单精确到 4 个文件并在下一轮删除） | 新增反向依赖即门禁失败 |
| 8-4 | 收敛重复概念：`core/serializers.py` 的 `iso()` 与 `kernel/serializers.py` 的 `user_out()` 明确分工（纯格式化 vs 实体投影），文档写清 | 不再出现「两个 serializers」的困惑 |

> 风险：`authz` 是引用最广的模块（142 处 `Depends`）。缓解：shim 保留 `AuthContext`、
> `get_current_user`、`require_permission`、`DataScope` 全部符号；只改文件位置，不改导入路径。
> 预计改动：4 个文件移动 + 4 个 shim + 0 处调用点修改。

### 4.4 Phase 9：事务收敛（3–4 人天）

| 编号 | 内容 | 验收 |
|---|---|---|
| 9-1 | 机械统一：69 处裸 `await db.commit()` 改 `await kernel.db.commit(db)`；删除 `theme/service.py` 的本地 `_commit`，改 `commit(db, conflict_code="THEME_CODE_EXISTS")` | 全量测试绿；`grep -c "await db.commit()" app/modules` = 0 |
| 9-2 | 门禁：`app/modules` 下禁止出现 `await db.commit()`，只允许 `kernel.db.commit` | 新代码无法绕开统一语义 |
| 9-3 | 引入显式工作单元：`kernel/db.py` 增加 `@transactional` 装饰器（进入时 `begin`，正常返回 `commit`，异常 `rollback`），先用于 3 个「多写」场景：用户导入、批量操作、角色授权 | 这三个场景不再需要 `commit=False` 开关 |
| 9-4 | 事件与事务的顺序写成机制：`enqueue_event()` 与业务写同事务（已有），`publish()` 只在「事务已提交」后调用，用一个 `after_commit` 钩子表达 | 顺序不再靠注释提醒 |

> 风险：9-3 改变提交时机，可能影响「部分成功」语义（批量操作希望逐条提交）。
> 缓解：批量场景保留「逐条提交 + 失败明细」语义，`@transactional` 只用于「全成功或全失败」
> 的场景；两者在文档里写清边界。
>
> **落地状态（2026-11-01）**：9-1 ~ 9-4 全部完成。54 处裸 `await db.commit()` 收敛到
> `kernel/db.commit()`（IntegrityError → 语义化 AppError，`conflict_code` 运行时校验）；
> `@transactional` 用于角色/权限授权、改密、重置密码 4 个「全成功或全失败」场景
> （`import_users` / 批量删除保留逐条提交语义——`@transactional` 的整事务 rollback 会把
> session 里所有对象过期，调用方再读 `ctx.user.id` 直接 `MissingGreenlet`，这条边界
> 写进了 `docs/模块与分层规范.md` §7）；`after_commit()` 用于公告发布的「提交后才发事件」；
> `check_commit_boundary` 门禁上线（modules 下出现 `db.commit()` 即失败）。

## 5. 刻意不做（本轮）

- **引入前端框架或构建工具**：违反硬约束 1，收益不覆盖成本；
- **强制 Redis / 强制 MySQL**：违反硬约束 2；
- **浏览器 E2E（Playwright）**：仍需额外运行时，DOM 层继续由门禁 + 冒烟兜底；
- **i18n 全量翻译**：只做「通用文案表 + 新代码强制 `t()`」，不做多语言落地；
- **响应模型自动生成**（从 ORM 推导 Out 模型）：会让「契约」变成「实现的镜像」，
  失去「显式声明对外形状」的意义；
- **把 `kernel` 再拆成 `domain` / `platform`**：当前 1,062 行，拆了只会增加层级；
- **审计日志软删除**：延续产品策略（硬删除 + 权限门 + 留痕）。

## 附录 C：环境坑（与项目无关，避免复诊）

1. **本机 Python 注入了 safe-delete shim**：单次删除 ≥50 个文件需确认，pytest 会话启动时
   批量清理临时目录会被拦下，表现为「测试全过但退出码 1」。验证门禁时用
   `CODEBUDDY_SAFE_DELETE_ENABLED=0` 临时绕过，**不要**把它写进仓库脚本（那是宿主策略）。
2. **heredoc 会破坏正则里的 `\s`**：用 `<<'PY'` 写含 `\s` 的脚本时，`:\s` 会被写成 `:/s`，
   脚本静默产出「0 个问题」。写探针脚本请用文件写入工具，不要用 heredoc。
3. **仓库混用 CRLF/LF**：用 `write_text` 会把 `\n` 二次翻译成 `\r\r\n`，整个文件看起来都改了。
   批量改写用 `write_bytes`。
4. **Windows 下 `.venv/Scripts/python.exe`** 与系统 python 的依赖不同：
   跑 `scripts/check_*.py`（会 import `app.*`）必须用 venv 解释器。
