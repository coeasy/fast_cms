# 部署与升级

本文覆盖三种运行形态：本机开发、裸机生产（SQLite）、容器化部署（Compose profiles）。默认形态不依赖 MySQL 与 Redis；两者只在显式开启后参与启动。

## 1. 运行形态

| 形态 | 数据库 | 调度器 | 适用场景 |
|---|---|---|---|
| 本机开发 | SQLite | `embedded` | `make dev` / `make dev-all` |
| 单机生产 | SQLite 文件 | `embedded`（单 worker） | 低资源单实例 |
| 单机生产（扩展） | MySQL 8 | `standalone` 或 `embedded` | 多 worker、数据量较大 |
| 容器默认 | SQLite（卷） | `embedded` | `docker compose up` |
| 容器 `mysql` | MySQL 容器 | `embedded` | 验证/迁移 MySQL |
| 容器 `scheduler` | SQLite 或 MySQL | 独立 `scheduler` 服务 | API 多 worker |
| 容器 `full` | MySQL + Redis | 独立 `scheduler` 服务 | 完整扩展形态 |

页面由 FastAPI 用 Jinja2 直接渲染，静态资源（CSS / 原生 JS）随后端源码一起发布，**没有前端构建产物，也没有独立的前端服务**。后台挂载在 `ADMIN_BASE`（默认 `/admin`）下，前台站点挂载在 `PORTAL_BASE`（默认 `/front`）下，两者与 API 同源同端口；`GET /` 307 重定向到 `{PORTAL_BASE}/`，`ADMIN_BASE=/` 时退到 `{ADMIN_BASE}/dashboard`，保证老书签仍可用。改挂载路径或 API 前缀只需要改 `.env` 并重启，页面渲染时会重新算出所有地址。

## 2. 配置与生产基线

配置优先级：环境变量 > 仓库根 `.env` > `backend/.env` > 代码默认值。敏感信息（数据库连接、密钥、Cookie 安全开关）只通过环境变量或 `.env` 注入，不写入数据库。完整键位见 [.env.example](../.env.example)。

生产环境建议至少确认：

| 配置 | 建议值 | 说明 |
|---|---|---|
| `APP_ENV` | `production` | 非 dev 时迁移落后会拒绝启动 |
| `APP_SECRET_KEY` | 显式注入强随机值 | 留空会生成并持久化到 `backend/data/.secret` |
| `APP_DOCS_ENABLED` | `false` | 关闭 `/docs`、`/openapi.json` |
| `AUTH_COOKIE_SECURE` | 留空（自动） | 非本地环境默认下发 `Secure`，仅当 TLS 在代理处统一终止、回源为明文 HTTP 时才显式设 `false` |
| `TRUST_PROXY` | 有反代时 `true` | 默认 `false`：只信任直连来源 IP。开启后限流与审计日志采用 `X-Forwarded-For` 首跳，必须确保只有代理可达应用，否则客户端可伪造该头 |
| `RATE_LIMIT_ENABLED` | `true` | 关闭后登录、导出、上传、改密等限流全部失效，仅建议在压测环境临时使用 |
| `LOGIN_RATE_LIMIT` / `LOGIN_RATE_WINDOW` | `30` / `60` | 单 IP 登录尝试上限，遭遇撞库时可收紧 |
| `CACHE_MAX_ITEMS` | `4096` | 无 Redis 时进程内缓存的兜底上限，按并发访客量放大 |
| `APP_CORS_ORIGINS` | 留空（同源） | 仅在前后端分域部署时填写 |
| `AUTO_MIGRATE` | `false` | 推荐用 CLI 显式迁移 |
| `APP_WORKERS` | `1` | 大于 1 时必须改用 `SCHEDULER_MODE=standalone` 或 `disabled` |
| `SCHEDULER_MODE` | `embedded` / `standalone` | 多实例只能有一个调度来源 |
| `APP_TIMEZONE` | `Asia/Shanghai` | 系统时区初值；首次种子后由系统参数 `system.timezone` 接管（后台「系统参数」可改，即时生效、重启读回），日志时间戳、CSV 导出、通知正文与前端展示都按它换算 |
| `SCHEDULER_TIMEZONE` | 留空 | 留空 = 任务默认时区跟随系统时区；只有调度时区需要与展示时区分开时才填 IANA 时区名 |
| `LOG_RETENTION_DAYS` | 按合规要求 | 审计日志保留天数，清理接口有下限校验 |
| `UPLOAD_MAX_MB` | 按业务调整 | 同时调整反向代理的上传限制 |

口令强度不走环境变量，而是系统参数 `security.password_min_length`（存于 `sys_config`，默认与下限均为 8，参数管理页可直接修改）：创建用户、管理员重置密码、自助改密与 CLI 共用同一校验，且会经公开参数下发给前端表单。除长度外还强制“同时包含字母和数字”“不能包含用户名”“不在弱口令黑名单内”。

`APP_WORKERS>1` 且 `SCHEDULER_MODE=embedded` 时，应用会在启动阶段直接抛出 `RuntimeError`，不会带病运行。多 worker 时：

- 调度器改为 `standalone`：`python -m app.cli scheduler` 单独运行；
- 只读/测试节点可设为 `disabled`；
- 多个调度进程之间依赖数据库任务状态和锁；开启 Redis 后锁与缓存跨进程生效，未开启 Redis 时锁仅在本进程内有效。

## 3. 裸机部署

### 3.1 一键安装（推荐）

新机器不必先确认装了什么，脚本自己探测：

```bash
python scripts/env_check.py          # 只探测：Python、Miniconda/Anaconda/Miniforge、数据库、端口、页面资源
python scripts/install.py --prod     # 探测 → 后端环境 → 依赖 → .env → 迁移与基线数据
```

Windows 直接双击 `install.cmd`。包装脚本按「已有 `backend/.venv` → conda 环境 → 系统 Python」挑选解释器；系统 Python
低于 3.12 但装了 Miniconda/Anaconda 时，会自动改用 conda 里满足 3.12 的环境，也可以用
`python scripts/install.py --use-conda --conda-env fastcms` 显式创建一个专用环境（此时不再叠加 venv）。
探测输出的 `✗` 是阻塞项（Python 缺失、页面模板或静态资源缺失），`!` 只是提醒（没有 conda、端口被占用、Redis 已启用等）。

改完 `.env`（见第 2 节）后启动：

```bash
python scripts/start.py preview      # 监听 .env 的 APP_HOST / APP_PORT，单进程同时输出 API、后台页面与前台站点
```

### 3.2 手动安装

```bash
python3 -m venv backend/.venv
backend/.venv/bin/pip install -e "backend[dev]"
cp .env.example .env
# 编辑 .env：APP_ENV=production、APP_SECRET_KEY、INITIAL_ADMIN_PASSWORD、AUTH_COOKIE_SECURE、APP_DOCS_ENABLED 等
cd backend
.venv/bin/python -m app.cli init        # 迁移 + 基线数据 + 初始管理员
.venv/bin/python -m app.cli db current  # 确认迁移版本
```

`APP_ENV=production`（或 `prod`）下 `INITIAL_ADMIN_PASSWORD` 不能留空或使用内置默认口令 `fast_cms_123`，`init` 会直接失败并提示；这样才不会出现“公网实例用文档里的口令”。本地开发不设置该变量即可用 `admin / fast_cms_123` 直接登录。

Windows（Git Bash）把 `.venv/bin/python` 换成 `.venv/Scripts/python.exe`。

页面模板与静态资源在 `backend/app/web/` 下，随 Python 包一起分发，**装完依赖即可访问，没有任何构建步骤**：

```text
backend/app/web/
├── router.py          # PAGES 页面清单 + 后台/前台路由
├── templates/         # base.html + components/（组件宏）+ layouts/（三套外壳）+ pages/**
└── static/            # css/{base,admin,portal,public}.css、js/{app,core,ui,icons}.js、js/shell/**、js/pages/**
```

改完模板或静态文件刷新浏览器即可；静态资源由 `StaticFiles` 挂在 `{ADMIN_BASE}/static` 与 `{PORTAL_BASE}/static` 下，
不需要额外的 web 服务器。生产环境建议给这两个前缀加上长缓存（文件名不含哈希，升级后需要 `Cache-Control: no-cache` 或主动刷新）。

启动：

```bash
cd backend
.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

生产环境不要使用 `--reload`。若设置 `APP_WORKERS`，需同步在 Uvicorn 使用 `--workers`，并切换调度模式。

### 3.3 systemd 示例

```ini
[Unit]
Description=Fast CMS Admin
After=network.target

[Service]
Type=simple
User=fastcms
WorkingDirectory=/opt/fast_cms/backend
EnvironmentFile=/opt/fast_cms/.env
ExecStart=/opt/fast_cms/backend/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

数据目录 `/opt/fast_cms/backend/data` 必须可写（SQLite、上传文件、密钥、备份）。服务用户不应拥有源码以外的系统权限；代码目录建议只读。

### 3.4 反向代理与 HTTPS

```nginx
server {
    listen 443 ssl;
    server_name cms.example.com;
    client_max_body_size 25m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

- 生产启用 HTTPS 后无需再手工设置 `AUTH_COOKIE_SECURE`（非本地环境默认 `Secure`）；只有 TLS 在代理终止、回源走明文 HTTP 时才需要显式 `AUTH_COOKIE_SECURE=false`，此时 Cookie 将不再带 `Secure`，属于已知取舍；
- refresh cookie 的路径限定为 `${API_PREFIX}/auth`（默认 `/api/v1/auth`），代理不要重写该前缀；
- 客户端 IP 取用顺序：uvicorn 的 `FORWARDED_ALLOW_IPS`（默认 `127.0.0.1,::1`）会先对来自本机代理的 `X-Forwarded-For` 做改写，因此与 nginx 同机部署时开箱即用；代理与应用不同机（或代理地址不在可信集合内）时设 `TRUST_PROXY=true`，并务必只允许代理访问 `8000`，否则限流与审计日志的来源 IP 可被客户端伪造；
- 登录限流按客户端 IP，其余敏感接口（导出、上传、改密、重置密码、日志清理、代码生成写库）按登录用户限流，详见 [认证与权限](认证与权限.md#接口限流)；
- 上传大小同时受代理 `client_max_body_size` 与 `UPLOAD_MAX_MB` 限制。

### 3.5 子路径与自定义前缀

只有两个旋钮，默认值（`/api/v1` + 后台 `/admin` + 前台 `/front`）不需要任何配置：

| 目标 | 配置 |
|---|---|
| 业务 API 换前缀 | `API_PREFIX=/cms/api`，重启即可（页面渲染时把新前缀注入到 `window.__FASTCMS__`） |
| 管理后台换挂载路径 | `ADMIN_BASE=/console`（默认 `/admin`）；页面路由、静态资源地址、顶栏链接都跟着变 |
| 前台换挂载路径 | `PORTAL_BASE=/site`（默认 `/front`）；首页的后台入口由模板按 `ADMIN_BASE` 拼出 |
| 后台仍占根路径（老部署习惯） | `ADMIN_BASE=/`；此时前台不挂载，启动日志会给出警告 |
| 网关重写路径 | 后端 `API_PREFIX` 保持不变（refresh cookie 的 `Path` 依赖它），由网关把对外前缀映射到它 |

示例：把后台挂在 `https://example.com/console/`，API 走 `https://example.com/console/api/v1/`：

```bash
# 后端 .env：ADMIN_BASE=/（后台占根路径，由网关把 /console 前缀剥离后回源；API 保持默认 API_PREFIX=/api/v1）
```

```nginx
location /console/ {
    proxy_pass http://127.0.0.1:8000/;   # 去掉 /console 前缀后转发给后端
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

注意：
- 后端 `API_PREFIX` 决定 refresh cookie 的 `Path`，网关重写前缀时必须同时改写 `Set-Cookie` 的 `Path`，否则 Cookie 不会随刷新请求发出；
- 页面的 catch-all 只挂在 `ADMIN_BASE` / `PORTAL_BASE` 下，不会吞掉 `API_PREFIX` 开头的请求，改前缀后旧前缀的请求拿到的是 JSON 404；
- 不需要重新构建任何东西：`ADMIN_BASE`、`PORTAL_BASE`、`API_PREFIX` 都在渲染时读取，改完重启进程即可。

## 4. Docker 与 Compose

### 4.1 默认 SQLite 形态

```bash
make docker-build
make docker-up                     # docker compose -f docker/compose.yml up -d --build
docker compose -f docker/compose.yml ps
curl http://127.0.0.1:8000/readyz
```

- 镜像只有 Python 运行时一层：页面模板与静态资源随 `backend/` 一起进镜像，没有 Node 构建阶段，也没有需要单独拷贝的产物目录；
- 非 root 用户、只读根文件系统、`no-new-privileges`；
- 可写路径只有命名卷 `fastcms_data`（挂载到 `/app/backend/data`）与 `tmpfs /tmp`；
- 入口脚本在 `AUTO_MIGRATE=true` 时执行 `db upgrade` 与 `seed`，SQLite 迁移前自动备份；备份保留在 `backend/data/backups/`，默认最多 `DB_BACKUP_KEEP=20` 份（按时间清理最旧的，设 0 表示不清理）；
- 健康检查调用 `/healthz`，Dockerfile 与 Compose 均已配置。

### 4.2 Profiles

```bash
# MySQL
DB_URL='mysql+aiomysql://fastcms:fastcms@mysql:3306/fastcms?charset=utf8mb4' \
  docker compose -f docker/compose.yml --profile mysql up -d --build

# Redis
REDIS_ENABLED=true REDIS_URL=redis://redis:6379/0 \
  docker compose -f docker/compose.yml --profile redis up -d --build

# API + 独立调度器
SCHEDULER_MODE=standalone \
  docker compose -f docker/compose.yml --profile scheduler up -d --build

# 完整形态
DB_URL='mysql+aiomysql://fastcms:fastcms@mysql:3306/fastcms?charset=utf8mb4' \
REDIS_ENABLED=true REDIS_URL=redis://redis:6379/0 SCHEDULER_MODE=standalone \
  docker compose -f docker/compose.yml --profile full up -d --build
```

Profile 只决定“启动哪些服务”，不会自动改写 `DB_URL` / `REDIS_ENABLED`。启用对应组件时必须显式传入配置，否则应用仍按 SQLite、无 Redis 运行。

使用 `scheduler` 或 `full` profile 时，`app` 服务的 `SCHEDULER_MODE` 必须是 `standalone` 或 `disabled`，否则两个进程都会调度任务。独立调度容器设置 `AUTO_MIGRATE=false`，迁移与种子只由 `app` 容器执行，避免并发迁移竞争。数据库与应用卷共享；MySQL 形态下两个服务使用同一个 `DB_URL`。

MySQL / Redis 服务带有健康检查，但应用未声明 `depends_on`。首次启动时应用可能先于依赖就绪而失败，`restart: unless-stopped` 会在依赖健康后自动拉起；观察 `docker compose logs -f app` 确认。

## 5. 可选组件

### 5.1 MySQL 8

```sql
CREATE DATABASE fastcms CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'fastcms'@'%' IDENTIFIED BY 'change-me';
GRANT ALL PRIVILEGES ON fastcms.* TO 'fastcms'@'%';
```

```bash
DB_URL='mysql+aiomysql://fastcms:change-me@127.0.0.1:3306/fastcms?charset=utf8mb4' \
  make db-upgrade
```

- 连接串必须使用 `mysql+aiomysql` 驱动与 `utf8mb4`；
- `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` 仅对 MySQL 生效；
- 从未迁移过的新库直接 `db upgrade`，会创建全部表；不要对已有业务表的库跳过迁移直接启动；
- 迁移后可用冒烟脚本验证健康检查、登录、受保护接口与版本信息：

```bash
cd backend
DB_URL='mysql+aiomysql://...' INITIAL_ADMIN_PASSWORD='一次性的初始密码' \
  .venv/bin/python ../scripts/mysql_smoke.py
```

脚本会以 `TestClient` 启动应用，读取 `INITIAL_ADMIN_PASSWORD` 并断言 `meta.version.database == "mysql"`。

### 5.2 Redis 7

```bash
REDIS_ENABLED=true REDIS_URL=redis://127.0.0.1:6379/0 make dev
```

- 默认 `REDIS_ENABLED=false`，此时不会导入或连接 Redis；
- 显式开启后启动阶段执行 `PING`，连接失败会使启动失败，而不是静默退化为内存实现；
- 开启后用于登录限流、缓存与跨进程任务锁；
- 未开启时使用进程内实现，重启即清空，多进程之间不共享。

## 6. 数据、备份与恢复

### 6.1 数据位置

| 数据 | 默认位置 |
|---|---|
| SQLite 数据库 | `backend/data/fastcms.db` |
| 上传文件 | `backend/data/uploads/` |
| 自动生成的密钥 | `backend/data/.secret` |
| SQLite 备份 | `backend/data/backups/` |

Docker 中以上内容统一位于卷 `fastcms_data`。`.secret` 丢失会导致已签发的 token 全部失效（用户需重新登录），但数据不丢失。

### 6.2 备份

```bash
make backup
# 等价于
cd backend && .venv/bin/python -m app.cli backup
# 或指定输出
cd backend && .venv/bin/python -m app.cli backup --output /backup/fastcms.db
```

- 备份通过 SQLite 在线备份 API 完成，运行中执行也能得到一致快照（包含 WAL 中已提交数据）；
- 每次 SQLite 迁移前会自动备份一次；
- 备份只包含数据库，不包含上传文件。完整备份需要同时归档 `backend/data/uploads/`；
- 建议外部定时任务每日执行备份并复制到异机，保留期按合规要求设定。

Docker：

```bash
docker compose -f docker/compose.yml exec app python -m app.cli backup
docker compose -f docker/compose.yml cp app:/app/backend/data/backups ./backups
docker compose -f docker/compose.yml cp app:/app/backend/data/uploads ./backups/uploads
```

### 6.3 恢复演练

恢复会覆盖当前数据库，先停止应用。CLI 会在覆盖前清理目标库遗留的 `-wal`/`-shm` 文件，避免旧 WAL 被回放导致恢复失效；应用进程未停止时这些文件会被占用，恢复会失败：

```bash
# 1. 当前库先留一份
make backup

# 2. 停止后端
#    systemd: systemctl stop fastcms
#    docker:  docker compose -f docker/compose.yml stop app

# 3. 恢复（CLI 会先自动做一次安全备份）
make restore FILE=backend/data/backups/fastcms-YYYYmmdd-HHMMSS.db

# 4. 校验迁移版本并启动
cd backend && .venv/bin/python -m app.cli db current
curl http://127.0.0.1:8000/readyz

# 5. 使用管理员登录，抽查用户、角色、公告与任务日志
```

Docker 恢复（入口脚本先跳过迁移，再执行恢复）：

```bash
docker compose -f docker/compose.yml stop app
docker compose -f docker/compose.yml run --rm --no-deps -e AUTO_MIGRATE=false \
  app python -m app.cli restore /app/backend/data/backups/fastcms-YYYYmmdd-HHMMSS.db --yes
docker compose -f docker/compose.yml start app
```

上传文件单独恢复：把备份的 `uploads/` 放回 `backend/data/uploads` 或卷内对应目录。恢复后如访问旧附件 404，优先检查该目录。

## 7. 升级

### 7.1 升级前检查

1. 阅读变更说明，确认数据库迁移、配置键和 API 契约变化；
2. 执行完整备份（数据库 + 上传文件）；
3. 在预发环境演练迁移与登录；
4. 确认当前 `/readyz` 返回 200 且迁移版本正确；
5. 如涉及前端契约，先执行 `make contract-check` 确认前后端一致。

### 7.2 裸机升级

```bash
# 1. 备份并停止服务
make backup
# systemctl stop fastcms

# 2. 更新代码与依赖
# git pull / 解压新版本
make setup            # 安装后端依赖；init 幂等

# 3. 显式迁移
make db-upgrade

# 4. 启动并验证（页面与 API 同一个进程，无需构建）
# systemctl start fastcms
curl http://127.0.0.1:8000/readyz
```

顺序要求：先停旧进程，再迁移，再启动新代码。非 dev 环境且未设置 `AUTO_MIGRATE=true` 时，代码先启动会因迁移版本落后而拒绝服务。

### 7.3 Docker 升级

```bash
# 先按第 6.2 节完成数据库与上传文件备份
docker compose -f docker/compose.yml down
docker compose -f docker/compose.yml build --pull
docker compose -f docker/compose.yml up -d
docker compose -f docker/compose.yml logs -f app
```

入口脚本会自动执行 `db upgrade` 与 `seed`。使用 MySQL/Redis/scheduler profile 时，升级命令需带相同的 profile 与配置环境变量。

### 7.4 回滚

- 优先回滚应用镜像/代码到上一版本；若新迁移不向前兼容，必须同时恢复升级前备份；
- 不建议依赖 Alembic `downgrade` 作为生产回滚手段；
- 回滚后检查 `/readyz`、登录、关键业务读写，并保留故障期日志与 `request_id`。

### 7.5 发布包

```bash
python scripts/release.py check      # 只跑门禁
python scripts/release.py all        # 门禁 + 打包，默认 zip
python scripts/release.py package --format tar.gz
```

门禁顺序固定为：环境探测 → `ruff` → `pytest` → 导出 `openapi.json` → `check_contract.py` → `check_api_coverage.py --strict`。任一步失败即中止，不会产出半成品包。页面是后端源码的一部分，没有构建步骤需要纳入门禁。

`check_contract.py` 校验三件事：OpenAPI 里每个路径都在当前 `API_PREFIX` 下、`operationId` 不重复、受保护路由都声明了已注册的 `x-permission`；同时把 `bootstrap/menus.py` 的菜单路径、`app/web/router.py` 的 `PAGES` 与 `static/js/pages/**` 三方对齐——菜单点进去必须有页面、页面必须有模板与脚本、孤儿页面也会被报出来。此外还校验**前端分层**：后台页必须继承 `layouts/admin.html`、前台首页继承 `layouts/portal.html`、登录/错误页继承 `layouts/blank.html`，并把每个页面渲染一遍，核对页面脚本里的 `#id` 选择器在渲染结果中确实存在、`data-modal-*` 指向的弹层真的存在。

`check_api_coverage.py` 是前后端连通性闸门：把 `openapi.json` 的每个端点与前端真实调用点（页面脚本里的 `api.get/post/put/patch/del/upload/download`、`static/js/shell/*.js` 外壳里的登录态与公告调用）按 HTTP 方法逐一比对，反向还会报告调用了不存在路径的死链。仅“单条详情 GET”（列表已回整行数据）允许没有前端调用方，白名单写在脚本的 `REST_DETAIL_ENDPOINTS`，且脚本会校验这些端点仍存在于契约、并被 `backend/tests` 请求过，避免白名单变成藏污纳垢的口子。

产物 `dist-release/fastcms-<版本>-<时间>.zip` 只包含可运行的源码：后端 `app`（含 `app/web` 的模板与静态资源）/`alembic`/`pyproject.toml`、`scripts/`、`docs/`、`docker/`、`openapi.json`、`.env.example`、`install.*` 与 `start.*`；不含 `backend/.venv`、`backend/data`（数据库、上传文件、密钥）。同目录 `manifest.txt` 记录文件清单与 SHA256，并列出 `.env` 中仍为开发默认值的项（`APP_ENV`、`APP_SECRET_KEY`、`INITIAL_ADMIN_PASSWORD`、限流开关、SQLite、多 worker 未开 Redis 等），供发布前复核。

目标机器解包后：`install.cmd` / `./install.sh --prod` → 编辑 `.env` → `start.cmd preview`。

## 8. 健康检查、日志与保留

- `GET /healthz`：进程存活，返回版本；
- `GET /readyz`：数据库可连接且迁移版本等于代码目标版本；未就绪返回 503，响应体只含 `status`/`database`/`migration`，驱动异常细节只写服务端日志；
- `GET /api/v1/meta/version`：匿名可见，只返回应用名、版本、时区与服务器时间；
- `GET /api/v1/monitor/server`（需 `monitor:server:read`）：Git SHA、Python、数据库类型、调度模式等运行时环境信息，公开接口不再暴露环境指纹；
- 日志输出到 stdout/stderr，由 systemd/journald 或容器运行时收集；
- 审计日志清理按 `LOG_RETENTION_DAYS` 执行，接口层还有更严格的下限校验；
- 过期会话按 `SESSION_RETENTION_DAYS` 清理；
- 所有响应带 `X-Request-ID`；错误响应包含 `request_id`，排查时优先索要该值。

## 9. 安全清单

- [ ] `APP_SECRET_KEY` 使用强随机值并通过环境变量注入
- [ ] 全站 HTTPS（非本地环境 refresh cookie 默认带 `Secure`，仅在 TLS 由代理终止且回源明文时显式关闭）
- [ ] 生产关闭 API 文档，或通过网关限制来源
- [ ] `APP_CORS_ORIGINS` 只填写受信域名，默认留空使用同源
- [ ] 生产环境显式设置 `INITIAL_ADMIN_PASSWORD`（不使用默认 `fast_cms_123`），初始口令不在仓库、日志或聊天记录中留存
- [ ] 数据库账号最小权限；MySQL 使用独立业务账号
- [ ] 备份与上传目录仅服务用户可读写，备份异地保存
- [ ] 反向代理传递真实 IP；跨机代理才设 `TRUST_PROXY=true`，且只允许代理访问应用端口，避免伪造 `X-Forwarded-For` 绕过限流、污染审计
- [ ] 保留默认限流（`RATE_LIMIT_ENABLED=true`），按业务量校准 `LOGIN_RATE_LIMIT`；密码策略收紧时调大 `security.password_min_length`
- [ ] 多 worker 时使用独立调度器，避免任务重复执行；`APP_WORKERS>1` 且仍用嵌入式调度器时启动会直接失败
- [ ] 多 worker 同时启用 Redis：字典、系统参数、密码策略与限流计数在未启用 Redis 时只存在于单个进程内，其他进程最长滞后一个缓存 TTL
- [ ] 内置「通知消息投递」任务默认暂停，配好渠道后再启用；启用前任务失败不会自动推送，单条记录可在发送记录页手动重试
- [ ] 仅给需要查日志的角色分配 `monitor:login-log:list`（该权限同时决定能否看到他人最后登录 IP）
- [ ] 菜单的 `path` / `redirect` 只接受 `/` 开头的站内路由（带协议、`//` 开头或查询串一律 422），前端渲染 `href` 前还会再过一次同源校验，避免拥有菜单编辑权的账号注入脚本或外跳链接
- [ ] 定期检查登录失败、锁定与操作日志

## 10. 常见问题

| 现象 | 排查 |
|---|---|
| 启动报“数据库迁移版本落后” | 执行 `python -m app.cli db upgrade`；确认 `APP_ENV` 与 `AUTO_MIGRATE` |
| `install.py` 报缺少页面资源 | 源码包不完整（缺 `backend/app/web/templates` 或 `static`）；重新获取完整发布包 |
| `install.py` 报 Python 低于 3.12 | 装了 Miniconda/Anaconda 时用 `python scripts/install.py --use-conda`，脚本会自动选用 conda 里满足 3.12 的环境 |
| 多 worker 首启报 `database is locked` | 已由 `backend/data/bootstrap.lock` 串行化，若仍出现请确认多个实例没有共用同一个 `data` 目录的不同挂载 |
| 账号提示“已锁定”，用户无法登录 | 连续登录失败触发的临时锁定；用户列表会显示 `已锁定`，管理员**重置密码即同时解锁**，无需等窗口结束 |
| `/readyz` 返回 503 | 数据库不可达或迁移版本不一致；查看 `database`/`expected` 字段与启动日志 |
| 页面 404 但 API 正常 | 检查 `ADMIN_BASE` / `PORTAL_BASE` 与访问路径是否一致；后台页面路由由 `app/web/router.py` 的 `PAGES` 决定，未知路径返回 HTML 404 而不是 JSON |
| 登录后立即 401 | Cookie 被 HTTPS/域限制拦截，或 `AUTH_COOKIE_SECURE` 与实际协议不符 |
| 导出、上传或改密返回 429 | 触发窗口限流，按响应 `Retry-After` 重试；网关后的多用户共享出口 IP 时确认 `TRUST_PROXY` 与 `FORWARDED_ALLOW_IPS`，避免限流键塌缩 |
| 登录日志里的 IP 全是 `127.0.0.1` | 代理未传递真实 IP：同机代理检查 nginx 是否发送 `X-Forwarded-For`，跨机代理需设 `TRUST_PROXY=true` |
| 浏览器请求 403 | 权限码未分配或后端数据范围拒绝；见 [认证与权限.md](认证与权限.md) |
| 开启 Redis 后无法启动 | `REDIS_URL` 不可达或未启动 Redis；这是显式启用的预期失败 |
| 任务重复执行 | 同时存在 embedded 与 standalone 调度器；只保留一个调度来源 |
| SQLite `database is locked` | 避免多进程写同一文件；高并发改用 MySQL |
| 上传大文件失败 | 同时调整代理 `client_max_body_size` 与 `UPLOAD_MAX_MB` |
