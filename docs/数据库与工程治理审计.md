## 2. 数据库与迁移专项

### 2.1 模型↔迁移一致性

- **现状**：22 张 `sys_*` 表 + `alembic_version`。`backend/app/db/models.py` 统一 re-export 全部模型；`test_schema_drift.py` 用 `compare_metadata` 守护列级一致性。
- **缺口**：
  1. **索引/唯一约束差异不受守护**（P2-2）。`b7a1c2d3e4f5` 把 `ix_sys_job_code` 改非唯一是靠人工对齐 `schedule/models.py:34`，没有自动校验。
  2. **无 downgrade 验证**（P1-6）。
  3. **迁移文件头 docstring 与 `down_revision` 不符**（P0-3）。
  4. `e3f4a5b6c7d8` 的 `server_default="registry"` 未在后续迁移中移除，MySQL 上 `sys_job.job_type` 会带永久默认值，模型侧却没有 `server_default`（`schedule/models.py:35`），属于隐性 schema 漂移。

### 2.2 索引/约束设计

| 表 | 现状索引 | 评价 |
|---|---|---|
| `sys_user` | `username_normalized`(uq), `dept_id`, `status` | 合理；缺 `email`/`phone` 索引（若做找回/搜索） |
| `sys_job` | `code`(非唯一), `status+next_run_at`, `template_id` | `code` 非唯一导致 `service.py:252` 的唯一预检与库层不一致（P0-1） |
| `sys_job_log` | `job_id+created_at`, `created_at`, `status`, `job_id`, `run_token` | 偏多；`status` 单列索引在 `recover_interrupted_logs` 里被 `status='running'` 用到，可用 |
| `sys_login_log` / `sys_operation_log` | `created_at`, `created_at+user_id`, `username` | 关键词 `LIKE '%kw%'` 无法命中（P1-4） |
| `sys_session` | `refresh_token_hash`, `previous_refresh_token_hash`, `user_id+revoked_at` | `refresh_token_hash` 应为唯一（当前仅 index，`system/models.py:147`），刷新令牌重放检测依赖 `previous_` 字段，建议加唯一约束 |
| `sys_notify_record` | `channel_id`, `event`, `status`, `status+next_retry_at` + `uq(channel_id,event,dedupe_key)` | 幂等设计合理；`_claim`（`notify/service.py:371-407`）逐条 `UPDATE...WHERE status='pending'` 抢占，MySQL 下多实例并发是安全的（靠行锁），但批量小（`NOTIFY_BATCH_SIZE`≤60） |

### 2.3 审计字段与软删除

- **软删除**：全项目零实现（P0-4）。建议至少给 `sys_operation_log`/`sys_login_log`/`sys_job_log`/`sys_notify_record` 增加 `purged_at` 或改归档表，而非 `DELETE`。
- **审计字段**：不统一（P1-5）。建议引入 `AuditColumnsMixin`（`created_by`/`updated_by`/`created_at`/`updated_at`，前两者设 FK `sys_user.id ON DELETE SET NULL`），并对纯配置表明确「无操作人」设计取舍。

### 2.4 数据库方言隔离

- **现状**：`backend/app/db/session.py:25-34` 用 `event.listens_for(engine.sync_engine, "connect")` 统一设置 SQLite PRAGMA（WAL/foreign_keys/busy_timeout/synchronous）；`config.is_sqlite` 只在 `session.py`、`migrate.py`、`cli.py`、`monitor/service.py` 出现，业务模块**未散落方言判断**——这一点做得好。
- **缺口**：
  1. `scripts/mysql_smoke.py` 存在（`docs/history/架构梳理与优化方案.md:516,528-530` 记录了它被新增与改造）；**CI 已补 MySQL 8 job**（`.github/workflows/ci.yml` 的 `mysql` 作业：service 容器 + 建库 → 迁移 → 种子 → 核心集成 → `db downgrade`/`db upgrade` 演练），对应 P1-11。
  2. ~~`monitor/service.py:127` 用二值判断~~（**已修复 P1-11 配套**）：改为 `app/db/session.py` 的 `database_dialect()`，直接返回 `engine.dialect.name`，PostgreSQL 等第三种方言不再被误标为 mysql。
  3. `migrate.py:71-74` 直接 `import sqlite3` 做备份，MySQL 分支在 `cli.py:208,214` 直接抛「请使用 mysqldump」——**MySQL 无备份/恢复自动化**，`docs/部署与升级.md` 也只提 `mysqldump` 手工。

## 7. 重构目标架构与边界

### 7.1 模块分层

```
app/
  core/       配置、鉴权、限流、缓存、日志、序列化、方言适配（保持现状，已是干净内核）
  db/         base(类型/命名约定) session engine migrate  ← 方言差异只允许出现在这里
  modules/<x>/  models · schemas · service · router ·(jobs)
  jobs/       执行器（registry/python_runner/runner/builtin）
  bootstrap/  权限注册表 · 菜单树 · 种子 · 版本表
  web/        Jinja2 模板 + 静态资源（无构建）
```
**边界**：`modules/*` 不得 `import sqlite3`/`pymysql`/方言判断；`core/authz.py` 是唯一的数据范围裁剪入口（现状已达成）；`db/migrate.py` 是唯一的 schema 演进入口。

### 7.2 契约管理
- 单一事实源：`openapi.json` 由 `app.cli export-openapi` 生成，**必须在 CI 中重新生成并 diff**（当前 CI 只生成不校验是否已提交一致）。
- `check_contract.py` 增加：索引/唯一约束与模型比对、`operationId` ↔ 前端调用点命名映射。
- `check_api_coverage.py` 的 `API_PREFIX` 改为读 `settings.api_prefix`。

### 7.3 权限与数据范围
- 保持 `get_data_scope` / `apply_user_scope` / `user_in_scope` / `scope_user_ids` 四件套；
- 引入「资源所有权」列（`owner_user_id`/`owner_dept_id`）后再让配置/内容类资源参与数据范围（`docs/认证与权限.md:209` 已指出当前不裁剪的原因）；
- `Dept.ancestors` 改物化路径 + 长度校验，或引入 `sys_dept_closure(dept_id, ancestor_id, depth)`。

### 7.4 任务执行
- 租约表保留，但把 `acquire_locks` 改为**单事务多行原子申请**（或 MySQL `GET_LOCK` 兜底），消除部分锁残留窗口（P1-8）。
- 增加 `JobRun`（运行实例）表替代散落的 `JobLog.run_token`，统一「一次执行」的生命周期。
- 通知队列 `_claim` 改 `SELECT ... FOR UPDATE SKIP LOCKED`（MySQL 8 支持；SQLite 退化为现有逐行 CAS）。

### 7.5 配置
- `Settings` 保持 pydantic-settings；新增**配置自检命令**（`fastcms doctor --config`）输出有效值与来源（env/.env/默认），供发布复核。
- `.secret` 权限失败时**显式告警**而非静默；增加 `APP_SECRET_KEY` 轮换文档。

### 7.6 迁移
- 每个迁移必须：① `downgrade()` 可执行；② 文件头 docstring 的 `Revises` 与 `down_revision` 一致；③ `server_default` 用完即摘。
- CI 增加矩阵 job：SQLite + MySQL 8，各跑「建库 → `db upgrade` → `seed` → 冒烟 → `db downgrade -1` → `db upgrade`」。

### 7.7 测试
- 每个测试用独立临时库（`tmp_path` + session/function scope），禁用共享 `TEST_DB` 文件（P0-2）。
- `test_schema_drift` 扩展到索引/约束/唯一键比对。
- 引入 `pytest-cov` + 覆盖率阈值（`docs/history/架构梳理与优化方案.md:237,407` 已规划）。

### 7.8 发布流程
- 门禁统一为一份「gate 清单」被 `make check`、CI、`release.py` 共同调用（消除 P0-7）。
- 发布包增加 `manifest.txt` 的**校验命令**（`python scripts/release.py verify <zip>`）。
- 文档新增「回滚演练」章节并要求每次大版本演练一次 downgrade + 备份恢复。

## 9. 风险与验收

### 风险
- **加密存量密钥**（阶段 A-6）若密钥派生方案改动，会导致历史通知渠道无法解密；必须保留旧密钥解密回退窗口。
- **软删除改造**会放大 `sys_*_log` 表体积，需要配套归档/分区策略。
- **MySQL 矩阵**首次接入可能暴露 `batch_alter_table` 在 MySQL 上的兼容问题（`render_as_batch` 仅对 SQLite 开启，见 `migrations/env.py:23,36`），需逐迁移验证。
