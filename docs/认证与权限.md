# 认证与权限

本文说明 Fast CMS 的登录、会话、权限码、角色与数据范围实现。后端判定是最终依据，前端菜单与按钮隐藏只影响体验。

## 1. 权限模型

核心关系：

```text
用户 ──< 用户角色 >── 角色 ──< 角色权限 >── 权限码
  │                    │
  └── 部门              └──< 角色部门 >（custom 数据范围）

菜单/按钮 ── 引用权限码
接口路由 ── 声明权限码（OpenAPI x-permission）
```

- `sys_user`：账号，`username_normalized` 唯一，`is_superuser` 标识超级管理员；
- `sys_role`：角色，`code` 唯一，`data_scope` 决定数据范围，`is_builtin` 保护内置角色；
- `sys_permission`：权限码注册表，只读，支持 `deprecated_at`；
- `sys_menu`：目录、菜单、按钮，按钮必须绑定权限码；
- `sys_dept`：部门树，使用 `ancestors` 路径（形如 `/1/3/`）做下级匹配；
- `sys_role_dept`：仅 `data_scope=custom` 时使用。

## 2. 权限码规范

格式固定为：

```text
{module}:{resource}:{action}
```

示例：`system:user:create`、`monitor:online:kick`、`schedule:job:trigger`、`tool:codegen:generate`。

权限码的单一来源链路：

1. 后端 `app/bootstrap/permissions.py` 声明基线；
2. 内置菜单与按钮引用权限码（`app/bootstrap/menus.py`）；
3. 路由通过 `permission="..."` 声明，框架自动注入依赖并写入 OpenAPI `x-permission`；
4. `python -m app.cli export-openapi` 导出 `openapi.json`；
5. 前端权限来自登录后 `/auth/me` 的实时结果（页面不维护权限清单，后端是唯一真相）；
6. 页面脚本用 `can('system:user:create')` 判断、模板用 `data-perm="system:user:create"` 批量隐藏按钮，`static/js/shell/admin.js` 的路由守卫用同一份 `ROUTE_PERMISSIONS` 表。

新增权限时必须同时更新：

- `bootstrap/permissions.py`；
- 使用该权限的路由或菜单；
- 重新执行 `make contract-check`（会重新导出 OpenAPI 并校验覆盖）。

`make contract-check` 会阻断以下情况：权限码未注册、受保护路由缺少 `x-permission`、权限码从未被 API/菜单使用、菜单引用不存在的权限码、菜单路径没有对应页面或页面缺少模板/脚本。

## 3. 判定规则

```text
允许 = 超级管理员 OR 权限码在用户所有启用角色的权限集合中
```

- 只统计 `status=active` 的角色；
- 忽略 `deprecated_at` 非空的权限码；
- 超级管理员绕过权限码检查，但仍受登录、会话、审计约束；
- 权限码不区分菜单与接口：同一码既可用于按钮显示，也可用于 API 依赖；
- 无权限时统一返回 HTTP 403，业务码 `AUTH_FORBIDDEN`。

后端通过 `protected_router(prefix=..., tags=...)` 创建受保护路由，例如：

```python
router = protected_router(prefix="/system/users", tags=["用户"])

@router.get("", summary="用户列表", permission="system:user:list")
async def list_users(...):
    ...
```

`PermissionAPIRoute` 自动追加 `Depends(require_permission(code))` 与 `x-permission`，避免声明与实际鉴权脱节。

公开接口（无需 access token）只有：登录、刷新、健康检查、就绪检查、版本信息、公开参数。个人中心、会话、心跳、公告用户端接口需要登录但不需要业务权限码。

### 管理后台准入（`system:admin:access`）

后台管理功能采用两级判定：**入口权限**决定能否进入管理后台，**业务权限**决定进入之后能做什么。

```text
能否进入后台 = 拥有 system:admin:access
进入后能做什么 = 各接口声明的业务权限码（或超级管理员）
```

- `app/core/authz.py` 的 `AuthContext.is_admin` 即 `has("system:admin:access")`，`require_admin` 作为路由依赖在缺少该权限时返回 403 `AUTH_FORBIDDEN`（提示“仅管理员可访问管理后台”）；
- 所有管理类路由（系统管理、系统监控、审计、仪表盘、参数、主题、定时任务、代码生成、公告管理端、文件管理）都挂了 `dependencies=[Depends(require_admin)]`，只拥有业务权限码但不能进入后台的账号也无法调用这些接口；
- 用户侧接口不受入口限制：`/auth/*` 个人中心与会话、`/content/notices/published`、`/content/notices/unread-count`、`/content/notices/read-all`、`/content/notices/{id}/published`、`/content/notices/{id}/read` 只需登录；
- `/auth/me` 额外返回 `is_admin`；非管理员的 `menus` 恒为空数组，前端因此不会渲染侧边栏；
- 五个顶级菜单目录（系统管理、系统监控、定时任务、内容管理、工具中心）引用 `system:admin:access`，`/system/depts/options` 与 `/schedule/capabilities` 以该权限码作为路由声明，保证注册表、菜单与契约检查一致；
- 内置 `super_admin` 角色拥有全部权限码，内置 `auditor` 角色在只读权限之外显式包含 `system:admin:access`（只读审计人员仍需要进入后台查看日志）；
- **升级到本版本前已存在的自定义角色不会自动获得该权限**，需要管理员在“角色管理 → 权限”中勾选「访问管理后台」后方可进入后台，这是有意的收紧行为。

## 4. 登录流程

```text
POST /api/v1/auth/login  {username, password}
  → 校验限流、锁定、密码、状态
  → 创建 sys_session（refresh 令牌仅存哈希）
  → 返回 access_token（内存保存） + 写入 HttpOnly refresh Cookie
  → 前端调用 GET /api/v1/auth/me 获取用户、权限、菜单
```

- access token：JWT，默认 15 分钟，携带 `sub`（用户 ID）、`sid`（会话 ID）、`ver`（token 版本）、`iss`、`aud`、`jti`；
- refresh token：随机 256 bit，写入 Cookie `fastcms_refresh`，`HttpOnly`、`SameSite=Lax`，路径 `${API_PREFIX}/auth`（默认 `/api/v1/auth`）；
- Cookie 的 `Secure` 标记默认由环境决定：`APP_ENV` 属于 `dev/development/local/test/pytest` 时关闭（便于明文 HTTP 本地调试），其余环境默认开启；`AUTH_COOKIE_SECURE=true|false` 可显式覆盖，例如生产站点在内网 HTTP 反代后统一终止 TLS 时设 `false` 并配合 `TRUST_PROXY=true`；
- refresh 每次轮换，旧令牌只在“上一次令牌”字段保留用于重用检测；检测到旧令牌再次使用会撤销整个会话；
- 修改密码会递增 `token_version`，并撤销除当前会话外的其他会话；
- 禁用用户、强制下线、管理员重置密码会撤销会话或递增版本，使旧 access token 失效。
- 调整角色、权限或用户部门**不需要**额外撤销会话：`get_current_user` 每个请求都从数据库重新装载权限与数据范围，access token 只承载身份与会话标识，变更在下一次请求即生效。

### 登录失败与锁定

- 用户名连续失败默认 5 次（`AUTH_MAX_FAILED`）后锁定 15 分钟（`AUTH_LOCK_MINUTES`）；
- 登录接口按 IP 限流：窗口内超过 `LOGIN_RATE_LIMIT` 次（默认 30/`LOGIN_RATE_WINDOW` 秒）返回 `AUTH_RATE_LIMITED`（429），`RATE_LIMIT_ENABLED=false` 时全部限流关闭；
- 错误信息不区分“用户不存在”和“密码错误”，统一 `AUTH_INVALID_CREDENTIALS`（401）；
- **不存在用户名也执行一次 Argon2 校验**（`verify_login_password` 使用占位哈希），使“用户不存在/密码错误”的响应时间一致，避免计时侧信道枚举账号；
- 锁定状态只有在**密码验证通过后**才返回 423 `AUTH_ACCOUNT_LOCKED`；先用错误口令试探锁定账号仍得到 401，不会泄露“该账号已锁定”；
- 客户端 IP 默认只取 `request.client.host`。仅当应用部署在可信反向代理之后才设 `TRUST_PROXY=true`，此时改用 `X-Forwarded-For` 首跳；否则客户端可伪造该头绕过登录限流并污染审计日志；
- 所有登录尝试（成功/失败/锁定/限流）写入登录日志，不记录密码。

### 接口限流

`app/core/ratelimit.py` 的 `RATE_RULES` 在中间件层对高频/敏感接口按窗口限流，超限返回 429 `AUTH_RATE_LIMITED` 并带 `Retry-After`：

| 范围 | 默认上限 | 计数键 |
|---|---|---|
| `POST /auth/refresh` | 120 / 60 秒 | IP |
| `POST /auth/change-password` | 5 / 60 秒 | 登录用户 |
| `PUT /auth/profile`、`POST /auth/avatar` | 20 / 60 秒、10 / 300 秒 | 登录用户 |
| `POST /tool/files/upload` | 30 / 60 秒 | 登录用户 |
| 任意 `GET */export` | 10 / 60 秒 | 登录用户 |
| `*/reset-password` | 10 / 60 秒 | 登录用户 |
| `DELETE *-logs`（日志清理） | 10 / 60 秒 | 登录用户 |
| `tool/codegen` 预览/下载、写库生成 | 20 / 60 秒、5 / 300 秒 | 登录用户 |

“登录用户”键取自本地验签的 access token `sub`（无 token 时退化为 IP），因此共享出口 IP 的多个账号不会互相挤占配额。中间件位于 FastAPI 异常处理层之外，超限直接返回 `JSONResponse` 而不抛异常。登录限流仍保留在 `/auth/login` 内部实现，以便区分成功/失败并写登录日志。

内存缓存（`MemoryCache`）按 `CACHE_MAX_ITEMS`（默认 4096）兜底清理过期项并淘汰最早写入的键，防止限流计数、字典与参数缓存随客户端数量无上限增长。

### 密码策略

规则实现于 `app/core/security.py`，最小长度由系统参数驱动：

- 至少 `security.password_min_length` 位（`sys_config` 可调，默认与下限均为 8，读取后写入缓存 `fastcms:password-min-length`，修改参数即时生效）；
- 同时包含字母与数字；
- 不能包含用户名（忽略大小写，而非仅“等于用户名”）；
- 拒绝弱口令黑名单（`WEAK_PASSWORDS`，如 `password1`、`admin123`、`12345678` 等常见组合）；
- 使用 Argon2id 哈希；修改密码必须验证当前密码，新密码不能与当前密码相同。

同一策略在创建用户、管理员重置密码、自助修改密码与 CLI `_reset_password` 四处复用 `validate_password_strength`，避免出现“接口能设弱口令、页面不能”的分裂。前端通过公开参数 `auth.password_min_length`、`auth.password_rule` 拿到策略（`src/utils/passwordPolicy.ts`），表单规则与提示文案与后端保持一致。

### 强制修改密码

管理员创建用户时可通过 `must_change_password=true` 要求首次登录改密。初始 `admin` 只在生产环境（`APP_ENV=prod|production`）带该标记；本地开发与测试使用固定口令 `admin / fast_cms_123` 直接登录，`INITIAL_ADMIN_PASSWORD` 可覆盖，生产环境沿用默认口令会被初始化拦截。

未改密时：

- 仅允许访问 `/auth/me`、`/auth/logout`、`/auth/change-password`、`/auth/heartbeat`、`/auth/profile`、`/auth/refresh`；
- 其他接口返回 403，业务码 `AUTH_PASSWORD_CHANGE_REQUIRED`；
- 前端守卫会跳转 `/account/password`，保存后重新签发 access token。

## 5. 会话与在线状态

`sys_session` 保存：会话 ID（`sid`）、`refresh_token_hash`、`previous_refresh_token_hash`、`expires_at`、`revoked_at`、`last_seen_at`、IP、User-Agent。

- 在线判定：未撤销、未过期、`last_seen_at >= now - 3 分钟` 且用户启用；
- 前端建议每 60 秒调用 `POST /auth/heartbeat`；
- 个人中心可查看“我的登录会话”，撤销指定会话或撤销其他会话；
- 管理员在 `/monitor/online` 可查看所有在线会话并强制下线；
- 刷新、登出、改密、禁用、强制下线均基于数据库会话，无需 Redis。

相关接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/auth/sessions` | 我的会话 |
| DELETE | `/api/v1/auth/sessions/{session_id}` | 撤销指定会话 |
| DELETE | `/api/v1/auth/sessions` | 撤销其他会话 |
| POST | `/api/v1/auth/heartbeat` | 更新在线时间 |
| GET | `/api/v1/monitor/online` | 在线用户（`monitor:online:list`） |
| DELETE | `/api/v1/monitor/online/{session_id}` | 强制下线（`monitor:online:kick`） |

## 6. 角色与数据范围

`sys_role.data_scope` 取值：

| 值 | 含义 | 用户列表过滤 |
|---|---|---|
| `all` | 全部数据 | 不过滤 |
| `dept` | 本部门 | `user.dept_id = 当前用户部门` |
| `dept_and_below` | 本部门及下级 | 部门 `ancestors` 路径匹配 |
| `self` | 仅自己 | `user.id = 当前用户` |
| `custom` | 指定部门 | `user.dept_id IN (角色关联部门)` |

多角色时取并集；超级管理员不受限制。

数据范围的边界是**资源描述的是“人”还是“配置/内容”**：描述人的资源按范围裁剪，描述配置与内容的资源全局可见。

| 资源 | 按数据范围裁剪 | 实现位置与业务码 |
|---|---|---|
| 用户列表及用户操作（改、删、重置密码、分配角色） | 是 | `apply_user_scope` 过滤列表，写操作用 `user_in_scope` 校验目标，越权返回 `SYSTEM_USER_FORBIDDEN` |
| 部门树 `/system/depts`、部门选项 `/system/depts/options` | 是 | `list_depts` 用 `_visible_dept_ids` 只保留范围内部门（含其下级路径命中项）；`create_dept`/`update_dept`/`delete_dept` 校验目标部门与新上级在范围内，否则 `SYSTEM_DEPT_FORBIDDEN`（403） |
| 在线会话 `/monitor/online` | 是 | `scope_user_ids` 生成子查询过滤 `UserSession.user_id` |
| 强制下线 `/monitor/online/{session_id}` | 是 | `user_in_scope` 校验目标用户，越权 `MONITOR_KICK_FORBIDDEN`（403）；下线超级管理员需要超级管理员；自己的会话始终可撤销 |
| 登录日志、操作日志的列表/详情/导出/清理 | 是 | `_log_scope` + `_restrict_to_scope` 按 `user_id` 关联到范围内用户；`user_id` 为空的记录（不存在用户名的爆破尝试、系统写入）始终可见。导出接口与列表共享 `keyword`/`status`/`module`/`success`/`start`/`end` 过滤参数 |
| 文件列表 | 是 | `_allowed_uploader_query` 复用 `scope_user_ids`，按上传人归属过滤 |
| 角色、菜单、字典、系统参数、公告、定时任务 | 否 | 这些是配置与内容资源，`sys_role`、`sys_menu`、`sys_dict_*`、`sys_config`、`sys_notice`、`sys_job` 均无归属列，按部门裁剪需要先引入所有权模型；当前只由各自的业务权限码控制，且必须先有 `system:admin:access` 入口权限 |

数据范围统一由 `app/core/authz.py` 的 `get_data_scope`、`apply_user_scope`、`user_in_scope`、`scope_user_ids` 生成，业务路由不手写过滤条件；`scope_user_ids` 返回 `None` 表示当前身份可见全部数据，避免为超级管理员生成无意义子查询。

### 信息暴露最小化

除数据范围外的三类字段/操作级裁剪：

| 数据 | 规则 |
|---|---|
| `last_login_ip` | 属于登录审计数据，只有拥有 `monitor:login-log:list` 的角色才能在用户列表/详情看到他人的最后登录 IP，其余身份返回 `null`（`LOGIN_IP_PERMISSION`） |
| `/system/roles/options` | 只返回 `id`、`name`、`code`，不携带权限清单，避免下拉选项把角色→权限映射泄露给所有能进入用户页的账号 |
| 审计日志清理 | `user_id` 为空的历史记录多为爆破/攻击流量，`cleanup_login_logs`、`cleanup_operation_logs` 使用 `_restrict_to_scope(include_orphan=False)`，只有超级管理员或 `data_scope=all` 的角色可删除；部门管理员不能销毁自己不拥有的审计证据（读取仍可见，保证可查不可删） |

服务层写操作日志（如用户创建、重置密码、分配角色）通过 `app/core/request_context.py` 的上下文变量补齐 `ip`、`user_agent`、`request_id`，不再依赖 HTTP 中间件才能记录这些字段。

## 7. 防提权与内置保护

普通管理员（非超级管理员）执行管理操作时：

- 只能分配自己已拥有的权限给角色（`SYSTEM_ROLE_ESCALATION`）；
- 只能分配权限与数据范围不超过自身的角色给用户；
- 入口权限 `system:admin:access` 同样受上一条约束：非管理员无法通过分配角色把自己或他人提升为后台管理员；
- 不能创建/操作超级管理员账号；
- 不能授予 `all`、`dept_and_below` 或超出自身范围的 `custom` 数据范围；
- 不能把目标用户放到自己数据范围外的部门；
- 不能新增、修改、删除自己数据范围外的部门，也不能把部门挂到范围外的上级（`SYSTEM_DEPT_FORBIDDEN`）；
- 不能下线自己数据范围外的用户会话（`MONITOR_KICK_FORBIDDEN`），也不能下线超级管理员（除非自身就是超级管理员）；
- `PUT /system/users/{id}` 允许在同一次请求里提交 `role_ids`（不传即保持原样，传空数组即清空），但只有拥有 `system:user:assign-role` 的账号才能改角色，否则返回 403 `SYSTEM_USER_FORBIDDEN`；基础资料与角色在同一事务提交，避免出现“资料已改、角色未改”的半成品状态。

通用保护：

- 不能删除自己、禁用自己、取消自己的超级管理员身份；
- 系统必须保留至少一个超级管理员；
- 内置 `admin` 账号不可删除；
- 内置角色不可删除，`super_admin` 不可停用或修改数据范围；
- 内置菜单不可删除，只能停用；
- 非内置菜单若绑定了权限标识，删除会转为停用（保留权限码，避免角色权限失联），接口用 `disabled` 告知前端；
- 角色仍被用户引用时不可删除；
- 部门存在子部门或用户时不可删除；
- 菜单存在子节点时不可删除，修改上级会检测循环。

## 8. 前端落地

- 会话状态保存在 `static/js/core.js` 的内存里（access token 不落 localStorage），页面外壳状态由 `static/js/shell/admin.js` 维护：`user`、`permissions`、`isSuperuser`、`isAdmin`、`menus`、`publicConfig`；
- 启动时先尝试 refresh 恢复会话，再请求 `/auth/me`；
- 路由守卫顺序：未登录 → 登录页；待改密 → `/account/password`；`isAdmin` 为 false 且目标路径不是 `/account/profile`、`/account/password` → `/403`；最后按 `static/js/shell/admin.js` 的 `ROUTE_PERMISSIONS` 表校验业务权限；
- 非管理员登录后直接提示“当前账号未开通管理后台访问权限，仅可维护个人资料”并跳转 `/account/profile`，侧边栏不渲染菜单；`/403` 页面按其身份显示“返回个人中心”或“返回工作台”；
- 按钮级权限使用模板属性 `data-perm="system:user:create"`（由 `applyPermissions()` 隐藏）或脚本里的 `can("system:user:create")`；角色权限弹窗会说明只有勾选「访问管理后台」才能进入后台；
- 下拉选项等辅助数据也按权限启用请求（例如用户管理页只在拥有 `system:role:list` 时拉取角色选项），避免权限较小的管理员一进页面就收到 403 提示；
- 用户管理编辑弹窗一次提交（单个 `PUT`），不再先改资料再改角色；`role_ids` 仅在拥有 `system:user:assign-role` 时随请求发送，`is_superuser` 仅在自身为超级管理员时发送，超级管理员开关对非超管禁用并给出说明；
- 密码相关表单（新建用户、重置密码、自助改密）的长度与规则来自公开参数 `security.password_min_length`，提示文案与后端策略一致，不在前端硬编码 8 位；
- 页面不维护权限清单，`can()` 只读 `/auth/me` 的返回结果；
- 退出登录调用 `/auth/logout` 撤销会话并清理内存 token。

## 9. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 登录返回 423 | 账号因连续失败被锁定，等待锁定时间或由管理员重置 |
| 登录返回 429 | 当前 IP 登录尝试过多，稍后重试 |
| 导出/上传/改密等接口返回 429 | 触发 `RATE_RULES` 窗口限流，按响应 `Retry-After` 秒数后再试；确需更高频率可调 `RATE_RULES` 或用 `RATE_LIMIT_ENABLED=false` 整体关闭 |
| 接口 401 且 code 为 `AUTH_SESSION_EXPIRED` | 会话过期/被撤销/密码已修改，重新登录 |
| 接口 403 且 code 为 `AUTH_PASSWORD_CHANGE_REQUIRED` | 首次登录未改密，前往 `/account/password` |
| 接口 403 且 code 为 `AUTH_FORBIDDEN` | 角色缺少对应权限码，检查角色权限分配 |
| 登录后只看到个人中心、访问管理页返回“仅管理员可访问管理后台” | 角色未勾选 `system:admin:access`（入口权限），在角色权限分配中勾选「访问管理后台」 |
| 菜单不显示但接口可访问 | 检查菜单状态、权限码与角色权限；后端权限才是最终判定 |
| 新权限码导致契约检查失败 | 同步更新权限注册表、菜单/路由并重新生成前端常量 |
