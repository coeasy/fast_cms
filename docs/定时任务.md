# 定时任务

Fast CMS 的定时任务以数据库为唯一事实来源，APScheduler 只作为执行器。默认使用数据库租约（`sys_job_lock`）做跨进程执行去重，**不依赖 Redis**。

## 1. 运行模型

```text
sys_job（任务定义/状态/参数/触发器）
sys_job_template（可复用模板）
    │  启动或变更时同步
    ▼
APScheduler（MemoryJobStore）
    │  到点触发
    ▼
run_job(job_id)
    ├─ 获取数据库租约 job:{id}
    ├─ registry → 注册表 handler
    └─ python   → 隔离子进程执行脚本
    ▼
sys_job_log（running → success / failed / skipped / interrupted）
```

- 任务定义持久化在 `sys_job`，服务重启后自动重建调度计划；
- APScheduler 使用 MemoryJobStore，不依赖 APScheduler 自己的持久化表；
- `next_run_at` 在重建/重排后回写数据库，便于页面展示；
- 任务分为两类：
  - `registry`：任务函数必须来自 `app/jobs/registry.py` 注册的 `code`，参数由 Pydantic 模型校验；
  - `python`：脚本存储在数据库中，在独立子进程执行，需要独立权限与全局开关；
- 任务模板存储在 `sys_job_template`，用于创建任务时预填配置，不参与执行；
- 任务租约存储在 `sys_job_lock`，按 `job:{job_id}` 维度互斥。

## 2. 调度模式

| `SCHEDULER_MODE` | 行为 | 适用场景 |
|---|---|---|
| `embedded` | FastAPI 启动时运行 AsyncIOScheduler | 单进程、默认开发/单机生产 |
| `standalone` | API 不调度；由 `python -m app.cli scheduler` 独立运行 | 多 API worker、容器独立调度服务 |
| `disabled` | 完全不启动调度器 | 测试、只读节点 |

约束：

- `embedded` 只允许单 worker；检测到 `APP_WORKERS>1` 时启动直接失败，需改为 `standalone` 或 `disabled`；
- 多个调度器实例共享同一数据库时，数据库租约保证**同一任务/同一编码不会并发执行**；重复触发会记录为 `skipped`，不会重复跑业务逻辑；
- 独立调度进程启动时先从数据库读回 `system.timezone`，再按解析出的时区建调度器；每 `SCHEDULER_SYNC_SECONDS`（默认 30 秒）从数据库做**差异同步**：仅在名称、触发器、时区变化时重建对应 APScheduler 任务，避免每轮全量重建导致 `next_run_at` 抖动；
- 重建 `interval` 任务时会把库中的 `next_run_at` 作为触发器的 `start_date`，因此重启、租约清理或差异同步都不会让周期任务重新从“现在 + 一个间隔”开始等待；
- 独立调度进程启动时会根据活跃租约判断并恢复中断日志，而不是把所有 `running` 日志一律标记为中断。

启动独立调度器：

```bash
cd backend
python -m app.cli scheduler
# 或
make scheduler
```

容器中可使用 Compose 的 `scheduler` / `full` profile。

## 3. 触发器

| 类型 | 必填字段 | 说明 |
|---|---|---|
| `cron` | `cron_expr`、`timezone` | 5 段标准 Cron（分 时 日 月 周），按任务时区计算 |
| `interval` | `interval_seconds` | 固定间隔，最小 10 秒，最大 30 天；执行相位锚定在首次计算出的下次执行时间上，重启或重新装载不会把倒计时重置为“从现在起再等一个周期” |
| `date` | `run_at` | 单次执行，接口按 UTC ISO 提交（页面选择的是任务时区下的墙上时间，由前端换算），必须晚于当前时间；执行后自动暂停 |

- 时区解析顺序：任务自身的 `timezone` → `SCHEDULER_TIMEZONE` → 系统时区（系统参数 `system.timezone`，初值取 `APP_TIMEZONE`，默认 `Asia/Shanghai`）；
- `SCHEDULER_TIMEZONE` 默认留空，含义是「任务默认时区跟随系统时区」；新建任务与任务模板未填时区时，落库的就是当时生效的系统时区，之后改系统时区不会追溯改写已有任务；
- 调度器实例本身的时区不可原地修改：`system.timezone` 变更后，进程内调度器会整体重建一次（`resync_timezone`），独立调度进程则在启动时从数据库读回；
- 数据库统一按 UTC 存储，接口输出 ISO 8601 UTC；
- 页面“预览”可查看未来 5 次执行时间；
- 无效 Cron、过去时间等返回 422 与明确业务码；
- 修改触发器配置、暂停后恢复会重新锚定周期：下一次执行时间按“当前时间 + 一个周期”重新计算，这是配置变更的预期行为；
- 任务模板只支持 `cron` / `interval` 两种触发方式。

## 4. 执行语义与去重

### 4.1 数据库租约

每次执行前先申请任务租约：

| lock_key | 作用 |
|---|---|
| `job:{job_id}` | 同一任务记录互斥，防止同一次执行被重复触发 |

- 租约 TTL 为 `max(60, timeout_seconds + 60)` 秒；执行期间每 `max(20, ttl // 3)` 秒续租一次；
- 插入主键冲突时尝试抢占已过期记录，因此跨进程、跨实例、无 Redis 也能去重；
- 获取失败写入 `skipped` 日志，错误信息为“已有同一任务在执行，本次跳过”；该日志表示本轮没有真正执行，下一次执行时间仍按计划推进，不会被推迟；
- 任务编码 `code` 不要求唯一，多个任务复用同一 handler 属于合法配置，因此不按 code 互斥，只按任务记录互斥；
- 执行结束、异常、取消或超时都会释放本人 token 对应的租约，不会误删他人锁；
- 调度器每轮同步会清理过期租约；同主机上 PID 已退出的租约也会被清理，跨主机租约则等待自然过期。

### 4.2 执行与恢复

- 每个任务固定 `max_instances=1`、`coalesce=true`，`misfire_grace_time` 取 `SCHEDULER_MISFIRE_GRACE_SECONDS`（默认 300 秒，设为 0 表示不限宽限、到点必跑一次）；
- 调度 tick 与任务执行相互独立：任务跑得久不会把下一次执行时间推迟到“执行结束之后”，到点仍会触发；
- 由于同一任务只允许一个实例，运行期间到点的 tick 会被丢弃并写入一条 `skipped` 日志（“上一轮任务尚未结束，本次跳过”），`coalesce=true` 保证补跑时只执行一次而不是把积压次数全部跑完；同一任务同一原因的跳过在 60 秒内只记录一条日志，避免短间隔长任务刷屏；
- 调度进程繁忙、事件循环被占用导致超过宽限期时写入 `skipped` 日志（“错过执行时间（调度进程繁忙）”），不会静默丢失；
- 租约互斥（4.1）在 `run_job` 内部生效，写入“已有同一任务在执行，本次跳过”，用于手动触发与调度触发重叠的场景；
- 开始执行即写一条 `running` 日志，结束后更新为 `success` / `failed` / `interrupted`；
- 超时通过 `asyncio.wait_for` 控制，默认 300 秒，可按任务设置；任务超时上限应小于执行间隔，否则中间周期会被跳过；
- 任务输出截断到 32 KB，异常堆栈同样截断；
- 进程重启后：
  - 仍持有活跃租约且 owner 存活的日志保持 `running`；
  - 其余 `running` 日志标记为 `interrupted`，错误为“调度进程重启，任务执行被中断”；
  - 清理过期租约与同主机死进程租约，避免永久占锁；
  - 周期任务按数据库中已有的 `next_run_at` 恢复相位；停机期间错过的周期不补跑，只等下一个到点时间；
- 手动“立即执行”不改变周期计划，只新增一条 `trigger_type=manual` 的日志；
- 每次执行日志记录 `job_type`、`run_token`；Python 任务额外记录脚本 SHA-256（`code_hash`）；
- 默认失败不自动重试，失败信息保留在日志详情中。

## 5. Python 脚本任务

Python 脚本任务属于高危能力，默认只有超级管理员拥有 `schedule:job:code` 权限，并可通过环境变量全局关闭。

### 5.1 全局开关与权限

```env
# 关闭后禁止创建、恢复、触发任何 Python 脚本任务（已有模板仍可保留）
SCHEDULER_PYTHON_ENABLED=true
```

| 操作 | 要求 |
|---|---|
| 创建/更新 Python 任务 | `schedule:job:code` + 全局开关开启 |
| 触发/恢复 Python 任务 | `schedule:job:code` + 全局开关开启 |
| 创建/更新 Python 模板 | `schedule:job:code`（不要求开关开启，便于预先维护） |
| 语法校验 | `schedule:job:code` |

`/api/v1/schedule/capabilities` 返回 `python_enabled` 与 `can_manage_python`，前端据此隐藏或禁用入口。

### 5.2 执行隔离

- 使用 `sys.executable -I -X utf8 -` 启动子进程，脚本经 stdin 传入，不落地到磁盘；
- 工作目录为临时目录，结束后删除；
- 环境变量最小化，仅保留 `PATH`、临时目录、语言设置，以及：
  - `FASTCMS_JOB_ARGS`：任务参数的 JSON 字符串；
  - `FASTCMS_JOB_CODE`：任务编码；
- Windows 使用新进程组，超时/取消时通过 `taskkill /T /F` 清理进程树；POSIX 使用独立会话并 `killpg(SIGKILL)`；
- 编译校验在 API 侧执行，语法错误返回 `SCHEDULE_SCRIPT_INVALID`（含行号）；
- 脚本标准输出与错误输出合并后截断到 32 KB；
- 非 0 退出码标记为 `failed`，错误信息包含退出码与 stderr 摘要。

### 5.3 示例脚本

```python
import json
import os
import sys

args = json.loads(os.environ.get("FASTCMS_JOB_ARGS", "{}"))
print("job args:", args)
print("python", sys.version.split()[0])
```

## 6. 任务模板

任务模板将常用任务配置沉淀为可复用条目，创建任务时可一键预填。

| 字段 | 说明 |
|---|---|
| `code` | 模板唯一编码，仅用于模板管理 |
| `job_type` | `registry` / `python` |
| `handler_code` | Registry 模板必填，指向已注册任务 |
| `script_code` | Python 模板的脚本内容 |
| `args_json` | 默认参数 |
| `trigger_type` / `cron_expr` / `interval_seconds` | 默认触发器 |
| `timezone` / `timeout_seconds` | 默认时区（留空跟随系统时区）与超时 |

- 使用 registry 模板创建任务时，任务 `code` 必须等于模板的 `handler_code`；
- 使用 Python 模板创建任务时，仍需填写全局唯一的任务编码；
- 模板中的字段仅作预填；请求中显式提供的值优先；
- 内置模板不可修改/删除，可复制为自定义模板；
- 内置模板：清理过期会话、清理过期日志、心跳检测、Python 健康检查示例。

## 7. 内置任务

| code | 名称 | 默认调度 | 参数 |
|---|---|---|---|
| `system.cleanup_sessions` | 清理过期会话 | 每天 03:00 | `days`（默认 30） |
| `system.cleanup_logs` | 清理过期日志 | 每天 03:10 | `days`（默认 90） |
| `system.cleanup_files` | 清理未引用文件 | 每周日 04:00，默认暂停 | `days`（默认 30） |
| `system.heartbeat` | 示例心跳任务 | 每 60 秒，默认暂停 | `message` |

内置任务 `is_builtin=true`，不可删除，只能暂停或修改调度。

## 9. 前端页面

- `/schedule/job`：任务列表、创建/编辑、模板预填、暂停/恢复、立即执行、下次执行预览、删除；
- 新建任务时可选择任务模板；registry 模板会锁定任务编码为处理器 code；
- Python 任务提供脚本编辑器与“校验语法”按钮，脚本任务入口受权限与全局开关控制；
- `/schedule/template`：任务模板列表、创建/编辑/复制/删除，“使用”跳转到任务创建并自动预填；
- `/schedule/log`：执行日志列表，详情按需拉取并展示类型、脚本摘要、输出与错误；
- 按钮由 `schedule:*` 权限控制，内置任务/模板隐藏删除按钮。

## 10. 新增注册任务处理器

1. 在 `app/jobs/` 中实现异步函数与参数模型；
2. 在 `register_builtins()`（或新的注册函数）中注册 `JobDefinition`；
3. 重启 API 或独立调度器；
4. 在任务页面选择新的 code 创建任务，或创建对应的任务模板。

示例：

```python
from pydantic import BaseModel, Field
from app.jobs.registry import JobDefinition, register

class SyncArgs(BaseModel):
    batch_size: int = Field(default=100, ge=1, le=1000)

async def sync_handler(args: SyncArgs) -> str:
    return f"batch={args.batch_size}"

register(JobDefinition(
    code="demo.sync",
    name="演示同步",
    description="演示任务",
    args_model=SyncArgs,
    handler=sync_handler,
))
```

处理器必须是可取消的异步函数，不执行长 CPU 阻塞；耗时操作应使用异步 I/O 或 `asyncio.to_thread`。

## 11. 故障排查

| 现象 | 排查 |
|---|---|
| 任务未按时执行 | 检查任务状态是否为 enabled、`next_run_at` 是否为空、调度模式与 worker 数量 |
| 修改后延迟生效 | standalone 模式最多等待一个 `SCHEDULER_SYNC_SECONDS` 周期 |
| 日志出现 `skipped` | 同一任务/编码正在执行，等待其结束；检查是否存在重复调度器 |
| 周期任务“下一次执行时间”每隔一段时间往后退 | 多为上一轮尚未结束导致到点的周期被跳过（`skipped` 日志可见），计划相位本身不会因执行耗时而重置；应调大间隔或缩短任务耗时/超时 |
| 单次执行时间过长后少跑了几次 | `coalesce=true` 的设计行为：积压的周期合并为一次执行；需要每次都跑请让间隔大于任务耗时 |
| 重启后 `interval` 任务的时间点整体后移 | 已修复：装载任务时使用库中 `next_run_at` 作为 `start_date`，仅修改触发器配置或暂停后恢复才重新锚定 |
| 日志 `failed` 且提示超时 | 调大任务超时或优化处理器；Python 任务超时会杀掉进程树 |
| 任务代码未注册（422） | 使用 `/schedule/jobs/definitions` 中存在的 code，或注册新处理器 |
| Python 入口不可用 | 检查 `SCHEDULER_PYTHON_ENABLED`、`schedule:job:code` 权限与 `/schedule/capabilities` |
| 服务重启后任务消失 | 检查是否误用了临时数据库/未挂载数据卷；任务定义在 `sys_job` |
| 多实例重复执行 | 数据库租约已提供互斥；若仍出现并发，检查各实例是否连接同一数据库 |
